# Chezmoi source

This directory is the chezmoi source state, not the application destination.
The repository's `.chezmoiroot` selects it; managed files are applied to the actual user home directory.
This README is excluded by `.chezmoiignore`.

The source contains `.chezmoi.toml.tmpl` to retain the permanent checkout binding when chezmoi configuration is regenerated.
It preserves unrelated TOML values while updating the source and working-tree paths and enforcing native GPG encryption policy.
The source manages global Git identity, OpenPGP commit signing, and the initial branch default through `dot_gitconfig.tmpl`.
Shared data is split under `.chezmoidata/`: `git.yaml` contains the Git identity, `gpg.yaml` contains the encryption recipient and OS-specific executable defaults, and `windows.yaml` lists the Windows host applications.
Chezmoi merges these files into the root data dictionary for managed templates; configuration initialization reads the public GPG data explicitly because that dictionary is not available at that stage.
See the root README for prerequisites and installation-path overrides.
GPG agent modify templates share the partial-file transformation in `.chezmoitemplates/gpg-agent-config`, preserving settings outside `pinentry-program`.
Modify templates use `chezmoi:modify-template` and deliberately have no `.tmpl` suffix.
OS-conditional ignores select the Windows or Unix GPG home.
Scripts live under `.chezmoiscripts/`, which does not create a destination directory.
GPG-home safety guards run on every explicit apply; GPG reload, Windows app installation, personal-app PATH integration, and Windows Native CA actions run only when their rendered contents change.
GitHub and GitLab authentication use ordinary `run_after_40-github-auth` and `run_after_45-gitlab-auth` hooks to repair external keyring state on every explicit apply.
Windows scripts are native `.ps1.tmpl` files, with profile-free interpreter settings generated by `.chezmoi.toml.tmpl`.
The Windows app list includes Chrome, 1Password, 1Password CLI, and system PowerShell; account sign-in and app preferences are not managed.
Keys and trust databases are not source-state entries.

The source also declares personal CLI applications, their generated release pins, and apply-only PATH integration.
Place managed configuration here using chezmoi's source naming conventions.
Use scripts only for actions that cannot be represented as managed files.
Native-CA startup modify templates share `.chezmoitemplates/native-ca-shell` and preserve content outside their marked block.
Optional Bash login files are selected only when they already exist at the destination.
Linux uses an OS-managed `environment.d` file; macOS uses an Aqua login LaunchAgent.
Windows explicit apply invokes the shared registry-provider body in `.chezmoitemplates/native-ca-windows`, changing only the managed user environment value.
These settings do not provision certificates; the root README lists runtime support and activation limits.

PowerShell apply hooks share `.chezmoitemplates/powershell-mise-profile` and `.chezmoitemplates/powershell-mise-profile-install`.
They replace the entire CurrentUserAllHosts profile reported by each applicable runtime, rather than preserving an unmanaged block.
Runtime-resolved paths can lie outside the chezmoi destination, so these are explicit apply actions instead of managed file entries.
The Windows hook invokes both system Windows PowerShell 5.1 and the checkout's mise-declared PowerShell; the Unix hook invokes only the latter.
Both start profile-free and do not activate mise during application.
Preparation and script-excluding apply commands do not install these profiles.

## Windows build tools

The Windows x64-only `run_after_25-windows-build-environment.ps1.tmpl` action
invokes the source checkout's `windows-build` mise task on every explicit apply.
It is intentionally not onchange-only: the VS 2026 stable channel must be updated
and the tracked component selection reconciled on each application.
Bootstrap, dry runs, script-excluding applies, and other host platforms do not
execute it. Failure or a reboot-required installer result stops dependent setup;
the action does not reboot Windows.

Keep task-only SDK/Rust declarations, installer inputs, and the immutable vcpkg
revision in `mise.toml`, with resolved tool versions in `mise.lock`.
`scripts/windows-build-tools.vsconfig` owns the complete latest/v143/v142
ATL/MFC architecture matrix and Windows/.NET Framework prerequisites.
Only Visual Studio machine servicing elevates. .NET SDKs share mise's native
user-local `dotnet-root`; the writable vcpkg checkout lives in
`~/.local/share/dotfiles/vcpkg`.
cargo/rustup respect existing `CARGO_HOME`/`RUSTUP_HOME`, defaulting to
`~/.cargo`/`~/.rustup`, never the source worktree.
Use Windows SDK 10.0.22621.0 for v142 ARM64 projects: SDK 26100 headers use an
intrinsic that the v142 compiler does not provide. Both SDKs are provisioned.

The common managed PowerShell profile prioritizes the existing user-managed
dotnet, cargo, and vcpkg command directories before mise activation on Windows.
Apply installs that profile through the existing runtime-specific profile hooks;
restart the terminal host to inherit updated user environment values.
The integration changes no machine PATH and persists no `RUSTUP_TOOLCHAIN`.
User-wide MSBuild integration selects the managed vcpkg root, replacing any
previous user-wide selection. Projects retain ownership of SDK `global.json`,
target frameworks, C++ toolsets, Rust overrides, manifests, baselines, and triplets;
no shared library set is provisioned.

`tests/smoke_windows_build_environment.py --verify-only` uses temporary actual
projects and an isolated rendering of the managed profile without installing host
tools or applying personal configuration. Project dependency restores require
network access. The dedicated Windows x64 job runs `--provision` only on disposable
GitHub-hosted runners and applies only the aggregate build task, twice.
It proves all requested native builds and ARM64 cross-built PE artifacts; ARM64
execution is outside that host's proof. See the root README for the full matrix,
activation, version-selection, and restart boundaries.

## Secret source

`.secrets/api-tokens.yaml.asc` is encrypted source data, excluded from destination enumeration by `.chezmoiignore`.
The `secrets` partial under `.chezmoitemplates/` returns its decrypted YAML only when a consumer requests it.
Parse that result with `fromYaml` in the consuming template and select the needed field; do not load secrets into global configuration data.
The encrypted payload preserves unrelated mappings and carries managed data under `github.token` and `gitlab` (host, registry, user, and token).
Use `scripts/github-auth.py import` or `scripts/gitlab-auth.py import` from the repository root; the GitLab command also accepts a confidential local connection file.
Shared publication in `scripts/auth_common.py` retains prior ciphertext through final verification before deleting the token input.
The authentication path streams GPG using the validated repository policy; unlike chezmoi's built-in GPG transport, it does not create plaintext temporary files.

The recipient in `.chezmoidata/gpg.yaml` is authoritative during explicit initialization.
The configuration template replaces recipient-affecting options, including inherited symmetric mode and additional recipients.
It uses the shared GPG executable selection, but ignores personal `gpg.conf` options for these calls to prevent implicit extra recipients.
Private-key access remains GPG's responsibility, without source-level hardware checks.

The authentication hooks decrypt only at execution time, never while rendering scripts or preparing a worktree.
The explicit native adapter in `scripts/cli_native.py` matches gh/glab's Windows UTF-8 blobs, Linux Secret Service attributes/collection selection, and macOS Keychain items.
Both GitHub and Gist aliases hold the repository token; existing Gist-specific credentials cannot silently outrank it.
Only account and connection metadata is published locally, and no plaintext managed-token fallback is allowed.
The managed Git template owns the public GitHub/Gist HTTPS helper chains and a generic include for private GitLab settings.
The GitLab apply command generates `.local/share/dotfiles/gitlab.gitconfig` at runtime, so private endpoints never enter tracked templates or bootstrap rendering.
GitLab metadata selects its PAT explicitly and uses glab's native empty-account keyring identity.
Docker/Podman registry login is separate work tracked in issue #25; this source stores its hostname encrypted but does not configure a container client.

## Personal application data

`.chezmoidata/personal-apps.json` owns the `personalApps` declarations: an upstream repository, command name, and target objects with an asset pattern and installation kind.
The optional `source` is `github` by default or `gitlab`; the lock updater resolves GitLab release links and its published checksum manifest.
Use `amd64` for Linux and Windows x64 hosts and `darwin` for macOS; macOS application targets are ARM64 only.
`.chezmoidata/personal-app-lock.json` owns generated `personalAppLocks` with each release tag, URL, SHA-256, and resolved extraction metadata.
Chezmoi merges both JSON files at the data root; filenames do not create namespaces.

`.chezmoiexternals/personal-apps.toml.tmpl` selects raw files for omp and archive members for gh from those records.
It never performs release discovery.
Regenerate pins with `mise exec -- python scripts/update-personal-app-lock.py` from the repository root rather than editing them manually.

The `.chezmoiscripts/run_onchange_after_10-personal-app-path` templates run only during explicit application and render empty on the other OS family.
Windows updates the user PATH; POSIX startup files source `.config/dotfiles/path.sh` without replacing existing profile contents.
PATH actions fingerprint the effective destination; Unix also fingerprints the managed fragment source and effective `ZDOTDIR`.
They do not consume application declarations or release pins, so changes to those data alone do not rerun PATH integration.
Keep executable installation declarative: scripts handle PATH and authentication, not application downloads or extraction.

## T3 Code desktop integration

The desktop app uses native package installation rather than the pinned personal CLI model.
`windows.yaml` adds its WinGet identity; `run_onchange_after_30-install-t3-code.sh.tmpl` retains existing macOS/Ubuntu installations.
The Ubuntu external stages a checksummed `.deb` only when no installed app is recognized.
Its public metadata reader, `scripts/t3-code-release.py`, uses the existing mise-managed Python runtime because chezmoi's typed GitHub release helper omits asset digests.
The apply script installs the staged file and never downloads or extracts packages.

`dot_local/bin` supplies desktop-dependent CLI launchers.
They follow the released Electron/server entrypoint contract and work without the GUI-generated `~/.t3/bin` shim.
Keep their OS/architecture selection aligned with the T3 exclusions in `.chezmoiignore`.
The macOS ignore rule also permits the shared PATH fragment while excluding Linux environment configuration.

`private_dot_t3/private_userdata/modify_private_settings.json` delegates to `t3-code-settings`.
It owns only the omp ACP launch fields and seeds missing presentation fields; unrelated values remain native application state.
Keep the `chezmoi:modify-template` marker, private attributes, and no `.tmpl` suffix.
Invalid JSON or non-object boundaries fail rather than being treated as missing.
Apply with T3 Code closed; filesystem watching is not a lock shared with chezmoi.

`tests/smoke_t3_code.py` applies only the relevant source into temporary state, runs the real bundled CLI, and initializes the managed omp ACP executable.
Its optional desktop provisioning is restricted to disposable GitHub-hosted runners; Windows CI uses the official installer directly, not WinGet acquisition.


## Harness plugin data and partial settings

`.chezmoidata/harness-plugins.json` owns `harnessPlugins` declarations, including upstream repository, stable-tag prefix, native omp identity, and archive exclusions.
`.chezmoidata/harness-plugin-lock.json` owns the generated `harnessPluginLocks` tag and full commit SHA records.
Keep these pins independent of host runtime registries and secret-bearing settings.

`.chezmoiexternals/harness-plugins.toml.tmpl` extracts immutable source archives into dedicated exact directories under `.local/share/dotfiles/harness-plugins`.
The CE declaration excludes alternate-host and site symlink aliases; it does not change the pinned skill content.
The `.chezmoiscripts/run_onchange_after_20-harness-plugins` scripts reconcile native omp registration and cache after source files exist.
They fingerprint the selected CE source/pin, native identity, destination, selected omp asset, and consumed template sources; unrelated platform pins and mutable runtime files are excluded.
Unchanged successful actions are skipped. Native cache/enabled-state drift requires a changed action input or explicit native repair; managed source and YAML still reconcile on every apply.
Marketplace decisions are rendered at execution time through the current chezmoi executable with a hook-free empty config and a disposable state database, so destination state cannot become an onchange dependency or reopen the parent's database lock.
Windows uses a BOM-prefixed `.ps1.tmpl`; UTF-8 data/output files avoid PowerShell 5.1 native-argument JSON quoting and stdout decoding.
Only CE's registration and managed package are reconciled; other plugin records remain native state.
New harness integrations must reuse the repository-owned CE pin through their supported native mechanism; omp commands are not a cross-harness installation interface.

The `private_dot_omp/private_agent/modify_private_config.yml` and `.yaml` targets share the `omp-config` partial.
Conditional ignores select the effective existing YAML file, and the partial updates only the owned semantic value.
Keep the `chezmoi:modify-template` marker and omit `.tmpl` from these filenames.
The private attributes keep configuration files owner-only (`0600`) and their managed parent directories private (`0700`) on POSIX, including unchanged-content reapplication.
The template refuses to create YAML over pending legacy settings migration and propagates parse failures.
This is not a comment-preserving editor or a lock shared with a running omp process.

## Shared user-scope harness instructions

`.chezmoitemplates/agent-instructions` is the single editable source for user-scope instructions.
Add shared Markdown below the common template comment and omp-specific Markdown inside its `harness == "omp"` branch.
The template receives `harness` and `chezmoi`, so OS-dependent content can also use `chezmoi.os`.
Conditions run during chezmoi rendering; agents receive only common content and their matching branch.
Keep paragraph boundaries when editing the template rather than trimming preceding Markdown with branch actions.

`private_dot_omp/private_agent/private_empty_AGENTS.md.tmpl` supplies the `omp` identifier and deploys to `~/.omp/agent/AGENTS.md`.
The `private_` and `empty_` attributes preserve an owner-only file even while the shared source renders empty.
The committed source currently contains only template comments and an empty branch, with no instruction policies.
Edit the shared source, not the generated destination.
Explicit apply replaces local destination content with the repository result, including an empty result; it does not merge or migrate personal instructions.
Bootstrap only enumerates the source and does not apply it.

Every managed harness, including future additions, must use this shared source.
Onboard a harness by adding a thin template adapter at its documented native user-scope path, passing its identifier and the chezmoi context.
Add a matching conditional region only when that harness needs its own content, and follow the harness's existing platform eligibility.
Verify common inclusion, foreign-branch exclusion, and native discovery in a disposable home without copying the common body.
Do not create destinations for unmanaged harnesses.
Onboarding also requires user-scope Compound Engineering integration under the [harness plugin integration rules](../AGENTS.md#harness-plugin-integration).
Reuse the plugin declaration and lock above, keep installation within explicit apply, and verify native CE skill discovery and invocation in a disposable home on each eligible platform.

The current deployment covers omp's standard default profile, not relocated agent directories or named profiles.
In [omp v18.16.0](https://github.com/can1357/oh-my-pi/blob/v18.16.0/docs/context-files.md), a non-empty native user file takes precedence over other user-context conventions.
Main sessions and advisors receive it; task subagents exclude files named `AGENTS.md`.
An empty file contributes no context.
For smoke proof, use temporary markers and inspect a fresh native session with `/extensions` and `/dump`, or RPC `get_state`'s assembled `systemPrompt`; no model turn is needed.
Remove the markers afterward and keep the committed output empty until real instructions are added.


## Script lifecycle

Use scripts only when managed files cannot represent the action.
Put new scripts directly under `.chezmoiscripts/`; do not leave duplicate entry points at the source root.

- Use ordinary `run_before_` for checks of current host state that must protect every apply.
- Use `run_onchange_` for actions driven by source configuration or data.
- Use `run_once_` only when each unique rendered version must run once, rather than after every change from the last successful version.
- Keep every script idempotent and propagate failures; an unsuccessful onchange action remains eligible on the next apply.

Preserve `before_` and `after_` semantics.
Use consistently padded numeric prefixes within a phase, as in `run_before_10-check-gpg-home.ps1.tmpl` and `run_onchange_before_20-install-windows-apps.ps1.tmpl`.
Keep OS conditions outside the entire output so unsupported scripts render empty.

### Dependency signatures

Declare dependencies as hash comments in the rendered script.
The script body itself is already tracked by chezmoi; add signatures for consumed files and templates whose changes would otherwise be invisible.
Include explicit data signatures even when the same values already appear in the body.

```gotemplate
# file gpg-agent-config sha256: {{ include ".chezmoitemplates/gpg-agent-config" | sha256sum }}
# data windows.apps sha256: {{ .windows.apps | toJson | sha256sum }}
```

These are separate examples: each script declares only the inputs it consumes.
Hash selected effective values after OS selection and configuration overrides, not entire chezmoidata files or the global data dictionary.
For example, GPG reload uses effective program and pinentry settings, not the encryption recipient or another OS's defaults.
Serialize data deterministically with `toJson` before `sha256sum`; YAML formatting and comments do not affect data signatures.
Include consumed shared templates and target wrappers when their changes affect the action.
Do not hash mutable destination contents, timestamps, or prior execution results.

### Windows execution

Use `.ps1.tmpl`, not cmd wrappers or encoded inline commands.
Emit a UTF-8 BOM with `{{ "\ufeff" -}}` inside the Windows condition so Windows PowerShell 5.1 reads non-ASCII literals correctly.
Keep scripts compatible with Windows PowerShell 5.1 for first application without pwsh.
Configuration initialization selects the built-in Windows PowerShell executable by absolute path and supplies profile-free, noninteractive arguments.
This remains available outside mise and before system pwsh is installed; the scripts also support direct execution under pwsh.
Regenerate existing configuration before adopting these scripts, as described in the root README.

### Repeat application

Unchanged successful actions are skipped, but safety checks still run.
Unchanged actions do not restore manually removed Windows host apps, personal-app PATH entries or profile source lines, or externally changed Windows Native CA registry values.
Renaming a script or changing its extension can cause an initial execution under its new identity; do not reset unrelated chezmoi state during migration.
