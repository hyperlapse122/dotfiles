Grounding Context

The repository manages Apple silicon macOS and NVIDIA NixOS. The observed machines have 64GiB unified memory and an RTX 3060 with 12,288MiB VRAM respectively. These are hardware facts; no model inference ran.

The user selected the omp Judge port, then made the official Decisions API the public authority. All its functionality remains in scope through the initial judge entry point, subject to the selected model's support. Additional entry points are to become follow-up GitHub issues at implementation handoff. Worker routing, task splitting, CE workflow consumers and harness plugins are later work.

omp has a shared typed judgment layer, a native System One transport, and an eval helper. Its helper renames the public API's noul probability to bool; this convenience alias does not define the new public API. Its auto-parallel example scores item roles and pairwise coupling before code assembles groups, but the session receives a suggestion or prompt hint. Those consumers illustrate reuse and are outside this port.

OpenRouter's operation includes four question primitives, structured instructions and criteria, asset references, supported media, provider preferences, request metadata, typed answers, refusals, usage and response metadata. The selected model controls capability. The API also defines unsupported-request errors.

Recommendation: begin the local adapter work with Clef-Flash 9B and retain Clef 27B as a larger comparison. Use a selected OpenRouter model such as Jev for box, or Gemini Decision 1 for its supported documents and media. This is a coverage recommendation, not a measured quality ranking.

The RTX 3060 cannot hold the full Clef-Flash BF16 release in its VRAM. A third-party project reports INT8 plus partial CPU offload on a different 12GB NVIDIA card; that is a candidate implementation path, not this host's result. Korean judgment quality and latency on both machines remain unmeasured.

Qwen3.8 and Gemma 4 are useful generative comparisons, but ordinary chat loading does not execute a native decision head. They are not drop-in replacements for Clef or the Decisions API.

Ranked Ideas

Five directions remain after the original 36 raw ideas, consolidation, critique, and the user's scope refinements. They can be combined in the selected foundation. Confidence expresses confidence in the direction's fit, not model accuracy.

I1. Port omp Judge behind the public Decisions API contract

Port boundary and reuseConfidence 94%Complexity Medium
Description
Use omp's reusable judgment layer as the implementation starting point. Make the public Decisions API definitions the authority for requests, answers and names, including noul; omp's eval-specific bool alias does not become the public contract. Keep the coding session, role chain and workflow consumers outside the port.
Basis
direct: The user chose the omp Judge port and then required close adherence to service API definitions. external: OpenRouter Decisions reference, TypeSafe System One reference, and the pinned omp judgment sources.
Rationale
Existing clients can recognize the decision contract while the project reuses a concrete implementation boundary.
Downsides
omp is an implementation reference, not a complete standalone service; its harness dependencies and intentional API differences need a bounded extraction.

I2. Keep IPC and human CLI on one judgment surface

IPC and human terminal clientsConfidence 94%Complexity Medium
Description
Expose judge through IPC for programmatic consumers and a terminal CLI for people. Both use the same Decisions request and answer semantics. Additional entry points become GitHub follow-up issues at implementation handoff; harness plugins and task-specific routing stay outside this change.
Basis
direct: The user requires a human-only CLI, harness IPC, a generic Judge foundation, and later GitHub issues for the remaining entry points.
Rationale
The foundation can be used directly before any Claude Code or Codex plugin exists.
Downsides
IPC lifecycle and the client protocol still need implementation planning. An omp in-process bridge is prior art, not an existing IPC daemon.

I3. Preserve the contract across MLX, CUDA and OpenRouter

Model and backend coverageConfidence 76%Complexity High
Description
Use MLX on Apple silicon macOS, CUDA on NVIDIA NixOS, and OpenRouter elsewhere. Start local model selection with Clef-Flash 9B; compare Clef 27B where memory permits. Implement the decision head as well as the backbone, and let the selected model's actual capabilities determine which requests it can answer.
Basis
direct: The platform split and model-specific support are user choices. external: Cloudflare Clef model cards, the dedicated MLX conversion, and the OpenRouter Decisions listings.
Rationale
A common API can retain each backend's real behavior without forcing a different model or remote route.
Downsides
The observed RTX 3060 has 12GiB VRAM, so full BF16 residency is unsuitable. Quantization or partial host offload is a candidate path; this host's inference, media fit and Korean quality remain unmeasured.

I4. Carry the full typed request and result through judge

Generic judgment semanticsConfidence 93%Complexity Medium
Description
Cover the complete documented Decisions operation: mixed named questions, noul, choice, score and box; structured instructions and criteria; per-question refusal; model identity, usage and optional result metadata. Preserve required and optional fields according to the API definition. Each feature is available only when the selected model supports it.
Basis
direct: The user explicitly expanded scope to every Decisions API feature. external: OpenRouter's DecisionsRequest and DecisionsResponse schemas, its endpoint reference, and TypeSafe primitives.
Rationale
judge is the first entry point, not a reason to reduce the API to a small custom subset.
Downsides
API coverage does not make all models equivalent. Optional fields, capability errors and provider-specific behavior must not be replaced by fabricated common values.

I5. Keep media and provider controls in the API's own forms

Multilingual and media fidelityConfidence 78%Complexity High
Description
Accept the documented media and asset-reference forms, provider preferences and request metadata through judge. Cover images, audio, video and documents when the selected model supports them, preserving model-specific placement and limits. The same surface accepts Korean, English and mixed-language content.
Basis
external: OpenRouter's Multimodal Decisions guide and endpoint schema define media parts, asset references and provider-dependent capabilities; TypeSafe documents its image and Box conventions.
Rationale
Future consumers can use service-native request forms instead of learning a second media schema for the local port.
Downsides
Clef Flash, Jev and Gemini Decision 1 expose different capabilities. A compatible envelope does not establish equal model quality or visibility into provider-side truncation.
