# OpenAI Context Cap - Plan

## Goal Capsule

- **Objective:** Give the owner a conservative context window for repository-configured OpenAI models in Pi and OpenCode.
- **Means:** Apply the cost policy before rendering model settings (KTD1).
- **Authority:** The Product Contract records the scope confirmed for [#267](https://github.com/hyperlapse122/dotfiles/issues/267).
- **Execution profile:** One pull request. The implementer verifies both generated settings paths; the owner retains the merge decision.
- **Stop conditions:** None at launch.

## Product Contract

### Summary

Cap the OpenAI context windows declared in the generated Pi and OpenCode settings.

### Problem Frame

OpenAI [charges long-context rates](https://developers.openai.com/api/docs/pricing?context-length=long) above 272,000 input tokens. Upstream catalog windows describe model capacity, not the budget the owner wants the harnesses to use.

### Requirements

- R1. Set each rendered OpenAI model's context window to the smaller of its catalog value and the integer `272000`.
- R2. Preserve the source snapshot and all other model settings, including output limits.

### Scope Boundaries

- Other providers, including OpenCode Go, and models supplied only by the harnesses' own catalogs are unchanged.
- Codex, WebSocket transport, and request-time input enforcement are outside this change.

## Planning Contract

### Key Technical Decisions

- KTD1. **Apply one shared transform before rendering.** Both harnesses consume the OpenAI snapshot in the same row shape. Normalize its context field once for both renderers, and keep Pi's selection of missing models unchanged. (session-settled: user-approved — chosen over editing the snapshot or imposing a runtime limit: the cap is a setting, not upstream metadata or a request gate.) Governs R1, R2.

## Implementation Units

### U1. Cap rendered OpenAI model settings

- **Goal:** Both generated settings paths use the same OpenAI cap.
- **Requirements:** R1, R2, KTD1.
- **Dependencies:** None.
- **Files:** Create a shared OpenAI catalog loader in `home/h82/agents/openai-models.nix`; update `home/h82/agents/pi.nix`, `home/h82/agents/opencode.nix`, `tests/pi-runtime.py`, and `tests/opencode.nix`.
- **Approach:** Feed the transformed list into Pi's existing `models.json` renderer and OpenCode's model settings mapping; do not change either catalog watcher.
- **Patterns to follow:** Pi's generated `models.json` and OpenCode's activation test in a scratch home.
- **Test scenarios:**
  - Generated Pi rows and activated OpenCode entries for the declared `gpt-6.2-sol` report `272000` for a snapshot window of `1050000`, with the output limit unchanged.
  - A source window below `272000` remains unchanged when passed through the shared transformation.
  - Existing checks still verify Pi's built-in catalog records and OpenCode's other provider settings remain unchanged.
- **Verification:** Observe the capped values in settings generated by the two modules without sending an API request.

## Verification Contract

Run the existing `pi` and `opencode` flake checks. Check the shared transform with a smaller model window if the live snapshot has no smaller entry.

## Definition of Done

- Both generated settings paths satisfy R1 and R2 without runtime changes or edits to catalog snapshots.
- The two relevant flake checks pass, with no experimental code left in the change.
