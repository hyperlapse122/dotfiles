# AGENTS.md

This is the chezmoi **source state** for `github.com/hyperlapse122/dotfiles`. Edit this checkout, never deployed `$HOME`; apply only when the user asks for deployment. The common guardrails in `.chezmoitemplates/agents-instructions.tmpl` (composed per harness into each agent wrapper) are binding; this file is the repository supplement and may add stricter local rules.

## Source layout and attributes

Chezmoi source names encode targets: `dot_foo` -> `~/.foo`, `*.tmpl` is rendered, `private_` is 0600, `readonly_` is 0444, `executable_` is executable, `encrypted_*.asc` is gpg ciphertext, `.chezmoiscripts/run_once_*` runs once ever, `.chezmoiscripts/run_onchange_*` reruns when rendered content changes, `.chezmoiscripts/run_after_*` runs every apply, `.chezmoidata` is data, `.chezmoitemplates` is shared template code, `.chezmoiexternals` is fetched tooling, and `.chezmoiignore` is templated exclusion. Dot-prefixed source paths are internal; non-dot metadata (`AGENTS.md`, `LICENSE`, `opencode.json`) MUST be listed in the root `.chezmoiignore`. `crates/` and `packages/` are source-only build trees.

Edit source files, not deployed files. The source directory itself is the only valid source context; nested worktrees cause recursive data errors, so checks MUST use `--source "$PWD"`. Never commit secrets.

## Apply lifecycle and script tree

Prefer `run_onchange_before_`/`run_onchange_after_` with a comment-only dependency fingerprint over unconditional `run_after_`. Keep bare `run_after_` only when live state must be retried on every apply. Fingerprint raw source content, including unresolved `op://` refs, never rendered secrets or build output. The shared `.chezmoitemplates/fingerprint.tmpl` contract is:

```gotemplate
{{ $sourceDir := .chezmoi.sourceDir -}}
{{ includeTemplate "fingerprint.tmpl" (dict "sourceDir" $sourceDir "globs" (list "path/to/source" "other/**")) }}
```

The partial hashes file content, uses `(stat .).isDir` to skip directories/output directories, and MUST NOT hash a rendered secret. A script with no external dependency hashes only its own rendered content; document that explicitly. A clean exit-0 skip is recorded as successful and will not retry until a fingerprint changes or `chezmoi apply --force` is used; retain `run_after_` only when that retry behavior is essential.

Never add teardown/revert scripts. Delete managed source, use `.chezmoidata/system.yaml` `removed:`, or document a one-time manual reversal. Numeric `.chezmoiscripts/` directories establish phase order; existing `run_*` naming and numeric ordering may be extended, and renaming an onchange script reruns it once per host.

## Host facts, gates, and system configuration

`.chezmoidata/facts.yaml` is the sole host-identity registry: each fact has a type, `hook`/safe template/builtin probe, gates, and fail-safe `whenFalse`. Hook facts are written once per chezmoi command by `.install-prerequisites.sh`; template facts come from `.chezmoitemplates/facts.tmpl`. The hook's `is_container`/`is_devbox` predicate and `facts.tmpl` predicate MUST remain byte-for-byte lockstep: a real container is `/run/.containerenv` or `/.dockerenv` without `/run/.toolboxenv`; distrobox/toolbox is treated as the host.

Gate grammar is `<fact>`, `!<fact>`, or `<fact>.<value>`; YAML values beginning `!` MUST be quoted. `facts-validate.tmpl` rejects unknown facts, missing probes, invalid comparisons, malformed desktop values, and undeclared emitted facts. Consumers use only `facts.tmpl`, `facts-sh.tmpl`, and `facts-gate.sh.tmpl`, never the cache. Every fact is render-time and fail-safe: false MUST skip rather than grant. `FORCE_NVIDIA` is an installer-only override, never a fact or system-file gate; `INSTALL_SYSTEM_CONFIG_FORCE` layers only on the headless guard. `stat` is required before absolute `include`; `glob` does not traverse symlinks; never use template `output` for a fact probe. Runtime scripts call shared `fact_gate()` and MUST NOT duplicate gate logic.

`system/linux/etc/**` mirrors `/etc`; `.chezmoidata/system.yaml` owns mode, gate, check, distro-scoped `removed:`, and reload behavior. Edit the manifest and tree, not installers. `install-system-10-files`, `20-host`, and `30-network` have independent onchange triggers. Reload only changed services; Bluetooth restarts only when Bluetooth files differ. Network changes can restart firewalld, resolved, NetworkManager, and Tailscale. GDM greeter fingerprint login MUST remain disabled while in-session fingerprint remains available. Polkit may add `pam_fprintd` only when the Debian `common-auth` conjunction is true; MUST NOT use `pam-auth-update` or a `common-auth` integration for fingerprint support, because it would re-enable greeter fingerprint authentication and break the GDM/Fedora polkit boundary. Sudo remains password-only. Fcitx5 is the KDE/GNOME input method; the GNOME autostart entry MUST NOT add `X-GNOME-Autostart-Phase`. TPM2 uses the shared dracut/systemd-cryptenroll backend and blank/missing credentials skip. Plymouth remains distro-native; SDDM Breeze is gated on its installed theme.

## Agent surfaces and ownership

All agent data is in `.chezmoidata/agents.yaml`. The managed harness set is omp. MCP declarations are transport-neutral and feed omp. `op://` strings resolve only at render. OAuth entries stay headerless for native stores. Figma authorization is on demand through `figma-auth omp`; never commit tokens.

External skills come from `agents.skills.external` -> `.chezmoiexternals/ai-agents.toml` -> `~/.agents/skills/<name>`; keep the exact isolated subtree and no pin-bump workflow. GitHub-sourced skills (`agent-browser`, `improve`, `i-have-adhd`) ship as archive externals extracting the `skills/<name>/` subtree. GitLab-sourced skills (`glab`, `glab-stack`) are raw single-file externals (`type = "file"` on `<name>/SKILL.md`) pinned to the glab release via `.chezmoitemplates/glab-release-ref.tmpl`, which `.chezmoiexternals/vcs.toml`'s glab binary also consumes. Locally-authored personal skills (unpublished, e.g. `daily-report`) are managed directly under `dot_agents/skills/<name>/` and deploy to `~/.agents/skills/<name>`. `dot_agents/skills/` is harness-neutral and is omp's sole managed skills source.

Compound-engineering is one versioned local archive owned by the neutral `agents.marketplaces` registry; omp consumes it. OMP consumes a dedicated bundled mxm4-haptic marketplace plugin from `~/.local/share/omp-plugins`; its self-contained extension imports the TypeScript client, uses OMP's pi-compatible event API, and depends on the cross-platform per-user daemon. Linux uses systemd and macOS uses launchd. Eligible-host build, installation, manager, and readiness failures are fatal; runtime event-delivery failures stay silent and never block a turn.

The mxm4-haptic phase-60 provisioners are `run_after_build-mxm4-haptic.sh.tmpl`, not onchange scripts. Component fingerprints and stamps keep plugin and daemon builds conditional. The every-apply run repairs live systemd or launchd drift without rebuilding unchanged artifacts, then verifies the exact managed endpoint between two running-state checks. Both halves resolve their own build toolchain because chezmoi inherits the invoking shell's PATH, which on a freshly provisioned host has never activated mise: an activated `vp`/`node`/`cargo` wins, otherwise the command runs through `mise exec` from the repository directory that owns the pin, and a command that neither PATH nor mise can supply is a fatal preflight failure. The plugin build installs the workspace dependencies first because the member's Vite+ config imports vite-plus from `packages/node_modules`. `systemd-analyze --user verify` MUST NOT run in preflight: it resolves `ExecStart` against the filesystem, so on a first apply it rejects a valid managed unit before the install that would satisfy it and deadlocks the host; the units are verified after the install and before the first manager mutation instead. Keep the provisioning fixtures transactional and isolated; they MUST prove unchanged convergence, selective rebuilds, manager drift repair, fatal build/install/manager/readiness boundaries, the mise fallback, and first-apply convergence on a host where nothing is installed yet — which requires the fixture's `systemd-analyze` stub to model that `ExecStart` filesystem resolution.

An agent config file moves to per-key assertion when its vendor writes it during normal use and stays managed-readonly otherwise. omp's `config.yml` is on the assertion side. It is NOT a chezmoi target because omp rewrites it through `/model`, `/settings`, and first-run setup. `run_after_config-omp-settings.sh.tmpl` asserts each declared `agents.omp.settings` path into it on every apply and leaves every undeclared path to omp. A declared record-typed path is owned wholesale because `omp config set` replaces a record and rejects a path inside one. Declared omp settings MUST stay credential-free because that CLI receives values as process arguments. Credentials are declared under `agents.omp.auth.env` and reconciled as a closed set into its private `.env`; OAuth stays in `agent.db`. Retiring the old config target deliberately left the deployed file in place, so it has no `.chezmoiremove` line or `remove_` source. omp's `models.yml`, MCP file, and instructions stay managed-readonly. `~/.omp/agent/mcp.json` remains managed-readonly as a dated exception (2026-07-29) until per-key assertion covers a list-shaped target.

Repo-scoped agent tooling is a separate category from those user-scoped skills. `.agents/skills/<name>/SKILL.md` at the repository root would be a PROJECT skill for agents working in this checkout, discovered by omp's native `agents` provider (`enableAgentsProject`, oh-my-pi `docs/skills.md`). Such a path is dot-prefixed, so chezmoi treats it as internal source and never deploys it, and it MUST NOT be confused with `dot_agents/skills/<name>/`, the user-scoped personal-skill source that DOES deploy to `~/.agents/skills/<name>`. No project skill exists today: the model-policy procedure that used to live here was retired once its checkable half became render-time and CI failures. Model policy is therefore governed by the data and its gates, not by a skill — see the omp paragraph above and `.chezmoitemplates/omp-settings-validate.tmpl`.

OMP keeps the Codex-user and Claude-user/project compatibility skill providers disabled so they do not duplicate the canonical `~/.agents/skills/` and repository `.agents/skills/` roots. Its structural-search and computer-control tools stay explicitly enabled in `agents.omp.settings`; do not rely on upstream defaults for either capability.

`agents.omp.settings.disabledProviders` is the provider availability gate, and it is load-bearing rather than cosmetic: `openrouter` remains disabled while its key stays provisioned, and the retired `opencode-go` and `opencode-zen` providers stay temporarily disabled while an existing host's unmanaged `OPENCODE_API_KEY=` line is removed. Their selectors, model override, and managed key declaration are gone; delete the stale dotenv line and both temporary guard entries together. `retry.fallbackChains` was never that gate — retry walks declared chains only — but omp's catalog-wide scans (built-in `priority.json` role chains with bare patterns, the text-only-model vision fallback, the smol/slow finders, and `providers.imageOrder`'s built-in tail) rank by incidental catalog order. `disabledProviders` applies before any credential check, so it is the only setting that removes a backend from every one of those paths; the cost is that a disabled provider also leaves `/model`. Consequence for model policy: a disabled provider disappears from `omp models --json`, which is the catalog the settings provisioner checks every declared selector and model-oriented chain key against, so no role, subagent override, or chain hop may name a provider on this list.

Model placement is evidence-driven, and the evidence is the Artificial Analysis Intelligence Index v4.1.1 and Agentic Index, 11 Aug 2026 snapshot. Three tiers carry every seat. The ceiling and the main loop are one model id, `anthropic/claude-opus-5` — `slow` at `:max`, `default` at `:high`. `default` is deliberately NOT `:xhigh`: that step buys 2 points of Agentic Index (58 against 56) and 2 of Intelligence Index (63 against 61) for a third more of everything that is actually scarce on a subscription — 31k against 21k output tokens and 6.4 against 4.3 minutes per index task. `defaultThinkingLevel` tracks the same value so a hand-picked `/model` inherits it. The light tier is `openai-codex/gpt-5.6-luna` and carries `smol`, `commit`, `advisor`, and the `scout` subagent, which fans out up to 32 at a time: Luna scores Agentic 47 at $0.05 and 1.8 minutes per task, so it beats both Gemini Flash tiers (41 and 40, at $0.56 and $0.69) on every axis at once and the light tier is not a Google tier. Background work (`tiny`) stays on `google-antigravity/gemini-3.1-flash-lite` and declares no chain, because retry chains are session-turn only and titles/memory/auto-thinking never walk one. Claude Sonnet 5 is never a primary — its Agentic 50 only matches Opus 5 at `medium` while spending 72k output tokens and 10.2 minutes per task — so it stays enabled as an escape hatch and appears once, as the light tier's Anthropic anchor of last resort.

`enabledModels` narrows Anthropic to the two Claude 5 selectors rather than `anthropic/*`, which closes `priority.json`'s bare patterns (`haiku`, `opus-4.5`, `pro`) at the model level the way `disabledProviders` closes them at the provider level; the accepted cost is that a new Anthropic model needs a data edit before `/model` can see it. `retry.fallbackChains` stays keyed on each tier primary's exact `provider/model-id`, with `default` as the floor for a hand-picked model no key names. A chain key MUST NOT name a model that appears only as a HOP: omp resolves a model-oriented key before the role key, so keying one would hijack recovery for every tier whose chain passes through that model. Each chain leaves its own provider on the first hop, because usage-aware fallback makes a same-provider hop useless when the plan cap is what failed. The ceiling's first hop is `kimi-code/k3:max` and the plain `k3` id is load-bearing: a fallback fires mid-session, so the hop must hold the context the failing model held, and only `k3` is 1M — `k3-256k` would overflow on arrival. K3 is the strongest non-Anthropic option available here (Agentic 54, free on the coding plan) and also the slowest at 9.6 minutes per task, which is exactly why it is a recovery hop and never a primary.

Managed instruction targets are one file per harness, named for the native filename: `AGENTS.md` and `APPEND_SYSTEM.md` for omp (`dot_omp/private_agent/`). Deleting a managed source stops management but does not prune an already-deployed target; pruning is a separate explicit decision.

`dot_config/tmux/tmux.conf` is the repository's only tmux target, and it exists for omp's inline images inside aoe-managed sessions. Its `allow-passthrough on` and its `set-environment -g PI_FORCE_IMAGE_PROTOCOL kitty` are a PAIR: tmux carries no Kitty-graphics handling, so passthrough is what stops it discarding omp's graphics escape, and the forced protocol is what turns on the Unicode placeholders that let tmux own the image cells — with only one of the two, images either never appear or die on the first redraw. The protocol value MUST NOT move to `dot_config/environment.d/` (a systemd user-environment entry would force the Kitty protocol in bare Kitty, editor terminals, and ssh, where it is wrong) and MUST NOT move to `agents.omp.auth.env`, which is a credential surface. Passthrough stays at `on` and MUST NOT be widened to `all`, which would also permit invisible panes; the accepted residual risk is that a visible pane can send arbitrary escape sequences to Kitty, bounded only by Kitty's remote-control API staying disabled. Verification is `.ci/test-tmux-kitty-passthrough.sh`, which drives an isolated tmux server on a scratch-scoped `-S` socket, asserts the forced protocol from inside a pane rather than through `show-environment -t` (a session listing does not show a global), and proves the transport by asserting the passthrough payload reaches a pty client with the setting on and does not with it off; pixels stay a manual Kitty check.

One trap is worth stating because it makes the tmux fix look unnecessary: tmux forwards a BARE Kitty graphics APC regardless of `allow-passthrough` and gates only the DCS-wrapped form, and `kitten icat` falls back to the bare form. So icat still draws images inside tmux with passthrough off, while omp — which wraps every graphics emission whenever `TMUX` is set — draws nothing. MUST NOT use `kitten icat` as the probe for this behavior; the committed test probes the wrapped form for exactly that reason.

Deploying that target has a second-order cost the file itself does not show: every aoe `[tmux]` setting defaults to `auto`, and `auto` means "step aside for the user's own tmux config". `status_bar` defers on the mere EXISTENCE of `~/.tmux.conf`, `$XDG_CONFIG_HOME/tmux/tmux.conf`, or `~/.config/tmux/tmux.conf`, so shipping this file at all made aoe UNSET its own `status*` session options and every aoe session fell back to tmux's stock green bar; `clipboard` defers when the config sets `set-clipboard` OR `allow-passthrough`, and ours sets the latter, so aoe silently stopped writing `set -s set-clipboard on` and OSC 52 from a wrapped agent died inside tmux. `.chezmoidata/agents.yaml` therefore declares `agents.aoe."config.toml".tmux` with `status_bar: enabled` and `clipboard: enabled`, reconciled into aoe's live `config.toml` by `run_after_config-aoe.sh.tmpl`. `mouse` stays undeclared because its `auto` keys on the option NAME rather than file existence, and this config never sets `mouse`. Both applications are per session and neither is retroactive: aoe paints the bar on create and attach, and appends the clipboard options to `new-session`, so already-running sessions keep whatever they were created with. The standing rule: any option added to `dot_config/tmux/tmux.conf` MUST first be checked against aoe's managed set (`status*`, `mouse`, `set-clipboard`, `allow-passthrough`), because adding one turns an aoe feature into a no-op and the symptom is a missing feature, never an error.

Disclose any onchange side effects, especially network/service restarts; the first apply that reruns `install-system-30-network` MUST be performed from a local console, not SSH/Tailscale.

`git diff --check`, `git status`, and a diff limited to the requested scope are required. `chezmoi archive --exclude=encrypted,externals,scripts` may compare extracted target trees, but archive bytes are not comparable by mtime and the archive omits scripts; compare rendered scripts separately and state that blind spot. If local rendering is unavailable, use CI artifacts from `.github/workflows/render-dotfiles.yml` and state the limitation. ## Secrets and encrypted state

Secrets resolve through a live `onepasswordRead` of their `op://` reference at render time, with no cache; the private-key import (`.chezmoiscripts/80-keys/run_once_before_import-gpg-key.sh.tmpl`) bootstraps the GPG key used for `encrypted_` files. The sole sanctioned repository ciphertext is `dot_config/garden/encrypted_readonly_garden.yaml.asc` (GPG); edit the garden via the wrapper (`chezmoi edit ~/.config/garden/garden.yaml`), never commit plaintext. Host LUKS/MOK prompts are AES-encrypted with a key only in the user keyring; read consumers fail soft when unavailable, and only the nonblank prompt path may create a key. Never infer that desktop-mediated `op read` is unavailable from a failed interactive `op whoami`. GitLab PAT setup is data-driven; `auth-glab` remains OAuth fallback.

Keep `rust-analyzer` external plus rustup component, use `/usr/bin/python3` for system scripts, and preserve npm/Bun/Yarn/pnpm hardening.

External release resolution lives in the generated `.chezmoidata/releases.json` lock, so a source-state read performs no network I/O; the migration plan was [`docs/plans/2026-07-27-001-refactor-static-release-artifact-lock-plan.md`](docs/plans/2026-07-27-001-refactor-static-release-artifact-lock-plan.md). The lock is machine-generated by `packages/release-lock` and MUST NOT be hand-edited — add a tool to that package's registry instead. `.github/workflows/refresh-release-lock.yml` re-resolves it hourly via `cli.ts --out`, which overlays the resolution onto the committed lock and commits to the default branch only when an entry actually changed — a source that fails to resolve keeps its last committed entry, and the run still fails. Per-platform URLs and checksums come from the GitHub release API's per-asset `digest`, so the refresh never downloads an artifact to hash it. A declared target whose asset the release does not publish is a hard error, never a silent skip; that strictness is what caught `buf` naming its linux arm64 build `aarch64` while darwin and windows use `arm64`. A target upstream genuinely does not build is declared in `emulatedPlatforms`, served by the amd64 artifact under emulation, and marked `emulated: true` in the lock — so an `x86_64` URL under an `arm64` key is deliberate, not a bug. The lock is authoritative: every externals file, shared template, and version-consuming script reads versions, URLs, and digests through `.chezmoitemplates/release-lock-ref.tmpl`, and no template or script may resolve a release at render time (`gitHub*` builtins, `curl`, `git ls-remote`).
