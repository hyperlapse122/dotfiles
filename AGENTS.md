# AGENTS.md

This is the repository supplement for `github.com/hyperlapse122/dotfiles` checkout source state only. Edit this checkout, never deployed `$HOME`; apply only when the user asks for deployment. The common machine-wide user instructions are defined in `.chezmoitemplates/agents-instructions.tmpl` (which renders to each harness's user-scoped instruction file); edit that template when modifying global instructions. This file defines repository-specific Chezmoi attributes, script lifecycles, host fact gates, system manifests, and verification workflows.

## Source layout and attributes

Chezmoi source names encode targets: `dot_foo` -> `~/.foo`, `*.tmpl` is rendered, `private_` is 0600, `readonly_` is 0444, `executable_` is executable, `encrypted_*.asc` is gpg ciphertext, `.chezmoiscripts/run_once_*` runs once ever, `.chezmoiscripts/run_onchange_*` reruns when rendered content changes, `.chezmoiscripts/run_after_*` runs every apply, `.chezmoidata` is data, `.chezmoitemplates` is shared template code, `.chezmoiexternals` is fetched tooling, and `.chezmoiignore` is templated exclusion. Dot-prefixed source paths are internal; non-dot metadata (`AGENTS.md`, `LICENSE`) MUST be listed in the root `.chezmoiignore`. `crates/` and `packages/` are source-only build trees. `docs/` is repo-meta and never deployed: `docs/plans/` holds work plans, and `docs/solutions/` holds documented solutions to past problems (bugs, practices, workflow patterns) filed by category with YAML frontmatter (`module`, `component`, `problem_type`, `tags`) — relevant when implementing or debugging in an area one of them already covers. `CONCEPTS.md` at the repo root holds the shared domain vocabulary (entities, named processes, status concepts) — relevant when orienting to the codebase or discussing domain concepts.

Edit source files, not deployed files. The source directory itself is the only valid source context; nested worktrees cause recursive data errors, so checks MUST use `--source "$PWD"`. Never commit secrets.

## Apply lifecycle and script tree

Prefer `run_onchange_before_`/`run_onchange_after_` with a comment-only dependency fingerprint over unconditional `run_after_`. Keep bare `run_after_` only when live state must be retried on every apply. Fingerprint raw source content, including unresolved `op://` refs, never rendered secrets or build output. The shared `.chezmoitemplates/fingerprint.tmpl` contract is:

```gotemplate
{{ $sourceDir := .chezmoi.sourceDir -}}
{{ includeTemplate "fingerprint.tmpl" (dict "sourceDir" $sourceDir "globs" (list "path/to/source" "other/**")) }}
```

The partial hashes file content, uses `(stat .).isDir` to skip directories/output directories, and MUST NOT hash a rendered secret. A script with no external dependency hashes only its own rendered content; document that explicitly. A clean exit-0 skip is recorded as successful and will not retry until a fingerprint changes or `chezmoi apply --force` is used; retain `run_after_` only when that retry behavior is essential.
Script early exits MUST declare one of four skip directions: `harmless` (this host will never satisfy the condition, so not acting is correct and final), `transient-tolerable` (an eligible host is missing a precondition and failing here cannot block later chezmoi phases — with one settled exception, `sudo-elevation-guard`, whose 21 consumers do block later phases because a host that needs root and cannot get it has not converged, and whose exit-0 predecessor recorded twelve unprovisioned scripts as successful runs; do not copy that exception to a new site), `transient-blocking` (an eligible host is missing a precondition, but failing here would abort later phases, so it exits 0 behind a declared capability probe instead), or `operator-blocking` (an eligible host is blocked by a real, clearable condition that only an operator can clear and that no two-valued render-time probe can observe — a conflicting NVIDIA driver branch, a repository set that cannot be asked what it offers; it exits 0 so later phases survive, KEEPS its state record so `dotfiles-skips` goes on reporting an unconverged host, forbids a probe, and names both the operator action and the `chezmoi state delete-bucket --bucket=scriptState` re-run in its message, because nothing changes the rendered content when the condition clears). `transient-blocking` is preferred wherever a probe exists: a capability probe is resolved by reviewed shell in `.install-prerequisites.sh`, which runs before the source state and cannot read `.chezmoidata`, so `operator-blocking` is for conditions whose definition lives in that data and only for those — a probe that COULD exist is a probe to add. Script early exits MUST use `.chezmoitemplates/skip.sh.tmpl` declarations across its four call forms (`skip_here`, `skip_step`, `done_here`, `not_applicable`), verified by `.ci/check-skip-declarations.sh`. Run `dotfiles-skips` to list outstanding `transient-tolerable` and `transient-blocking` skips without inspecting apply scrollback; it only reads recorded state, never probes capabilities or hosts and never mutates anything. Retiring a record is the hook's job, not the reader's: `prune_stale_skip_records` in `.install-prerequisites.sh` already holds the command's capability verdicts, and on a command that RUNS SCRIPTS (`apply`, `update`, `init`) it removes every `transient-tolerable` record (the script retries on each apply and rewrites it if it still fails) and every `transient-blocking` record whose named probe now reads `available` (the fingerprint has changed, so that same command re-runs the script). `operator-blocking` records are never pruned — nothing re-runs their script — and a record the pruner cannot parse is left to be reported. Without this a wait-only site outlived its own condition forever, because a record is otherwise cleared only by a later declaration carrying the same `script`/`site` pair and a wait has no success-path twin. Bare `exit 0` or `return 0` on conditional script paths is prohibited.


Never add teardown/revert scripts. Delete managed source, use `.chezmoidata/system.yaml` `removed:`, declare a plugin in `agents.<harness>.pluginsRemoved`, or document a one-time manual reversal. A `.chezmoiremove` entry may also prune a runtime-created path chezmoi never deployed; `.agents/skills/ce-*` and `.local/state/unmanaged-repo-guard` are the standing cases. Numeric `.chezmoiscripts/` directories establish phase order; existing `run_*` naming and numeric ordering may be extended, and renaming an onchange script reruns it once per host.

Package installation is owned modularly by feature scripts in `.chezmoiscripts/30-components/` and base installers in `.chezmoiscripts/20-base/`. ## Host facts, gates, and system configuration

`.chezmoidata/facts.yaml` is the sole host-identity registry: each fact has a type, `hook`/safe template/builtin probe, gates, and fail-safe `whenFalse`. Hook facts are written once per chezmoi command by `.install-prerequisites.sh`; template facts come from `.chezmoitemplates/facts.tmpl`. The hook's `is_container`/`is_devbox` predicate and `facts.tmpl` predicate MUST remain byte-for-byte lockstep: a real container is `/run/.containerenv` or `/.dockerenv` without `/run/.toolboxenv`; distrobox/toolbox is treated as the host. `jetson` is a template fact. It probes `/etc/nv_tegra_release`. `sharedHost` is a template fact. Its gate is true when `/etc/dotfiles-shared-host` exists, `jetson` is true, or `.chezmoi.username` contains `@`.

Gate grammar is `<fact>`, `!<fact>`, or `<fact>.<value>`; YAML values beginning `!` MUST be quoted. `facts-validate.tmpl` rejects unknown facts, missing probes, invalid comparisons, malformed desktop values, and undeclared emitted facts. Consumers use only `facts.tmpl`, `facts-sh.tmpl`, and `facts-gate.sh.tmpl`, never the cache. Every fact is render-time and fail-safe: false MUST skip rather than grant. `FORCE_NVIDIA` is an installer-only override, never a fact or system-file gate; `INSTALL_SYSTEM_CONFIG_FORCE` layers only on the headless guard. `stat` is required before absolute `include`; `glob` does not traverse symlinks; never use template `output` for a fact probe. Runtime scripts call shared `fact_gate()` and MUST NOT duplicate gate logic.

`system/linux/etc/**` mirrors `/etc`; `.chezmoidata/system.yaml` owns mode, gate, check, distro-scoped `removed:`, and reload behavior. Edit the manifest and tree, not installers. The modular `install-system-*` installers have independent onchange triggers. Reload only changed services; Bluetooth restarts only when Bluetooth files differ. Network changes can reload firewalld. The 30-network installer defers its explicit activation of resolved, NetworkManager, and Tailscale until manual restart or reboot. The login greeter MUST remain password-only on every managed host while in-session fingerprint remains available; on GDM that is the locked `enable-fingerprint-authentication=false` dconf key, and on any greeter authenticating through `password-auth` it is the fact that no sanctioned fingerprint mechanism writes that stack. On Debian-shaped hosts, polkit may add `pam_fprintd` only when the `common-auth` conjunction is true; MUST NOT use `pam-auth-update` or a `common-auth` integration for fingerprint support, because it would re-enable greeter fingerprint authentication and break the GDM/Fedora polkit boundary. On Fedora the fingerprint factor is enabled only through `authselect`, never by writing PAM files. That feature writes `system-auth`, and EVERY service that includes that stack in its auth phase gains the factor — verified on a live Fedora 44 host, those are `sudo`, `polkit-1`, `su`, `login`, `vlock`, `chsh`, `chfn`, `config-util`, `crond`, `kcheckpass` and `kscreensaver`. So **`sudo` accepts a fingerprint on a Fedora host with the feature enabled**, and so do `su`, the console `login`, and the Plasma lock screen. That whole set is the accepted scope, a deliberate amendment of the former sudo-is-password-only rule, taken because Fedora offers no sanctioned way to give polkit the factor without also giving it to the rest of the stack; stock `authselect` has no feature that separates them, so withholding the factor from the console `login` would mean withholding it from every Fedora host. The enumeration is host-verified rather than exhaustive: it was read off one host's installed packages, and another host may include `system-auth` in more services. The greeter guarantee is the one boundary the installer enforces rather than accepts, and it fails closed: `greeter_would_gain_fingerprint` resolves the greeter's own stack, and a display manager it does not recognize — or a stack it cannot resolve at all — WITHHOLDS the feature instead of assuming it safe. Password authentication remains accepted everywhere; the fingerprint is an additional factor, never a replacement for the greeter's. Fcitx5 is the KDE/GNOME input method; the GNOME autostart entry MUST NOT add `X-GNOME-Autostart-Phase`. TPM2 uses the shared dracut/systemd-cryptenroll backend and blank/missing credentials skip. Plymouth remains distro-native; SDDM Breeze is gated on its installed theme. On Ubuntu, a username with `@` is authd-managed. The login-shell script uses `authctl user set-shell` only when that exact subcommand exists. Otherwise, it makes a schema-checked `sqlite3` update to the authd database. Never use Python. Never restart the authd daemon.

## Agent surfaces and ownership

All agent data is in `.chezmoidata/agents.yaml`. The managed harness set comprises `claude` (Claude Code), `agy` (Google Antigravity CLI), `codex` (OpenAI Codex CLI), and `omp` (oh-my-pi). MCP declarations in `agents.mcp.servers` are transport-neutral and render into universal `~/.mcp.json`, the harness-specific `~/.gemini/config/mcp_config.json` and `~/.omp/agent/mcp.json`, and the `mcp_servers` tables of `~/.codex/config.toml`, with 1Password `op://` references resolved at apply time. `.chezmoitemplates/agent-mcp-servers-json.tmpl` is the one place the harness set is enumerated at render time; it fails on an unknown id rather than emitting an empty set. A server removed from the inventory is not pruned from `config.toml`; the Codex reconciler only adds and updates. OAuth entries stay headerless for native stores. A stdio server's optional `env` map is forwarded by the universal renderer, the Codex reconciler and omp's renderer; the Antigravity renderer still drops it, which is a known gap filed separately rather than a deliberate asymmetry. omp merges a per-server `env` over the inherited environment, so a value declared there reaches the server process and is written verbatim into `~/.omp/agent/mcp.json` — a plaintext credential does not belong in that field, and no renderer resolves `op://` inside it. Figma authorization is on demand through each harness's own OAuth flow; never commit tokens.

External skills come from `agents.skills.external` -> `.chezmoiexternals/ai-agents.toml` -> `~/.agents/skills/<name>`; keep the exact isolated subtree and no pin-bump workflow. GitHub-sourced skills (`agent-browser`, `improve`, `i-have-adhd`, `composition-patterns`, etc.) ship as archive externals extracting the `skills/<name>/` subtree. GitLab-sourced skills (`glab`, `glab-stack`) are raw single-file externals (`type = "file"` on `<name>/SKILL.md`) pinned to the glab release via `.chezmoitemplates/glab-release-ref.tmpl`, which `.chezmoiexternals/vcs.toml`'s glab binary also consumes. Locally-authored personal skills (unpublished) are managed directly under `dot_agents/skills/<name>/` and deploy to `~/.agents/skills/<name>`. `dot_agents/skills/` is harness-neutral; chezmoi deploys symbolic links `~/.claude/skills`, `~/.gemini/skills`, and `~/.codex/skills` pointing to `~/.agents/skills` to ensure unified skill discovery across all harnesses. A GitHub entry's in-repo subtree is `skillPath`, defaulting to the `skills/<name>/` nearly every source repo uses; `stripComponents` is derived from it (the archive's own top directory plus each segment) and the include anchors on it, so the two cannot drift apart. `android-cli` is the entry that needs its own: `android/skills` files it under `devtools/android-cli/`. That skill is external rather than a byproduct of provisioning because `android init` — whose ONLY effect is installing it — writes it into the global skills directory of every agent it detects, and all three of those are the symlinks above, so one call overwrote the managed `~/.agents/skills/android-cli` three times over with unpinned bytes from the CLI bundle, invisibly to chezmoi. `.chezmoiscripts/00-tools/run_onchange_after_android-sdk.sh.tmpl` therefore MUST NOT call `android init` (or `android skills add`/`update`); `android sdk install` needs neither. `.ci/test-android-skill-ownership.sh` runs the rendered script against a stub CLI to hold both halves.

The neutral `agents.marketplaces` registry carries two kinds. `localArchive` is a versioned download, and compound-engineering is one such archive that `claude`, `agy`, and `codex` each consume through their own reconciler. `localDir` is a tree chezmoi deploys rather than downloads, so it declares `path` (resolved against `$HOME`) instead of `source`, `externalPath` and a version selector; `dotfiles-claude-plugin` is the only one, and it is Claude-only. Codex discovers it through the chezmoi-owned personal marketplace `~/.agents/plugins/marketplace.json`, which resolves a `./`-relative plugin path against `$HOME` and not against the manifest's own directory, whose `name` is `agents.codex.personalMarketplace` and whose plugin paths are `./.agents/plugins/<registry key>` symlinks to the pinned archive, so a version bump moves the symlink target and `run_onchange_after_update-codex-plugins.sh.tmpl` runs `codex plugin add` for each declared row. The `codex-wrapper` source unit publishes `codex` and the external unit `codex` publishes `codex-bin`, so `codex exec` is metered through tokscale while every other subcommand reaches the real binary directly. `agents.<harness>.plugins` and `agents.<harness>.pluginsRemoved` declare the per-harness install and removal sets. `.chezmoitemplates/agent-plugin-rows.tmpl` validates every row against that registry — the exactly `{name, marketplace}` shape, the name charset, the duplicate rejection, and the os/container/jetson gates — and resolves each kind's source path; it is harness-agnostic and carries no per-harness branch. The eligible set is a render-time constant in both updaters, so an empty set renders a notice and no loop rather than a runtime skip.

Claude Code consumes a marketplace directory of either kind (`.claude-plugin/marketplace.json`, with the plugin's own `.claude-plugin/plugin.json` beside it; the Claude reconciler preflights both and the marketplace root doubles as the plugin root). Its `plugin marketplace add` is idempotent and rewrites a changed path in place, so a version bump needs no removal first, but its plugin cache is keyed by version and `plugin install` is a no-op once any version is present: `plugin update` is what re-resolves a bumped segment. `plugin enable` on an already-enabled plugin exits non-zero, and that one message is the only failure the updater treats as converged. Claude Code records both the marketplace declaration and the enabled set in `~/.claude/settings.json`, so an interactive `/plugin` change and the reconciler converge on the same file. `run_after_config-claude-settings.sh.tmpl` owns the LEAF, not the record: each `agents.claude.settings` key is a dot-separated path and only that leaf is written, so an undeclared key and the other members of an enclosing record both survive — the marketplace and enabled-plugin keys among them. Removing a path from the declaration stops the assertion but restores nothing. `hooks` (aoe), `enabledPlugins` and `extraKnownMarketplaces` (install-claude-plugins) are rejected at RENDER time by `.chezmoitemplates/claude-settings-validate.tmpl`, not merely avoided by convention; an empty declaration renders a notice and no assertion loop. The declaration is authoritative, so a value changed through the interface is reverted on the next apply and a value meant to stay adjustable is left undeclared — `theme`, `editorMode` and `verbose` deliberately are. Permission policy is the third undeclared category, and its surface is bounded rather than open: `permissions.defaultMode` is the ONLY `permissions.*` path a leaf declaration can express, and it is deliberately left undeclared. `permissions.allow`, `permissions.deny` and `permissions.ask` are lists, so asserting one would replace the whole list and drop every entry a user or a plugin contributed, and owning single entries would need a path syntax for list membership that the grammar does not have — that is a settled scope boundary, not a gap waiting on a mechanism. Because a permission grant would otherwise enter through the same data edit as a notification toggle, `claude-settings-validate.tmpl` screens for RISK as well as ownership: a path under a security-sensitive prefix, or one of the security-sensitive exact keys, is accepted only when its full path is on that partial's reviewed allowlist, so declaring one is a reviewed change to the template rather than a data edit. `skipDangerousModePermissionPrompt` is on that allowlist and stays globally pinned on every managed host, accepted rather than host-gated: `agents.claude.settings` has no `gate:` grammar, every managed host is the same single operator's own workstation, and adding per-key gating to the declaration is its own mechanism. Note also that Claude Code's precedence chain puts project-scope settings above user-scope ones, so a user-scope declaration is not a project-wide guarantee. Nothing validates that a declared path names a real Claude Code setting; no machine-readable settings schema is published, so a typo is asserted and reported as success while the product ignores it. Convergence writes nothing at all, and every cannot-assert path (missing `jq`, a malformed target, an ancestor holding a scalar or array) reports on stderr rather than exiting silently. An unwritable ancestor suppresses ONLY its own leaf: the declared paths are independent leaves with no invariant tying them together, so the writable ones are asserted, the blocked ones are named on stderr, and the damaged ancestor is left exactly as found — an all-or-nothing abort would have left the `DISABLE_AUTOUPDATER` pin unwritten behind one unrelated damaged key, with a green apply. Verification is `.ci/test-claude-settings-reconcile.sh`.

Because `hooks` is rejected at render time, a Claude Code hook this checkout owns ships as a PLUGIN instead: `dot_local/share/dotfiles-claude-plugin/` is a `localDir` marketplace whose `hooks/hooks.json` registers a `SessionStart` hook, and it is the standing home for this checkout's Claude Code hooks, agents and commands. Two coupled mechanisms make an edit to it reach a session, and both are required. Claude Code serves the COPY under `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, never the deployed source, and `plugin install` is a no-op at any version, so `plugin.json.tmpl` derives `version` from a digest of the WHOLE tree — anything narrower leaves a later `commands/` or `agents/` file deployed and never served. And the tree is a fingerprint input of `run_onchange_after_update-claude-plugins.sh.tmpl`, so the edit re-triggers the script that performs the install. `claude plugin update` re-resolves on any version DIFFERENCE, not only an increase, so a content digest that sorts backwards still propagates. Verification is `.ci/test-claude-team-hook.sh` for the hook's own behavior and the propagation and preflight cases in `.ci/test-claude-agy-plugin-reconcile.sh`.

`agy` has no marketplace registry: `agy plugin install <path>` takes an agent-plugins bundle directory and identifies a plugin by name alone. The bundle manifest it wants is the archive's ROOT `plugin.json`, which upstream ships and which its own `.agy/plugin.json -> ../plugin.json` symlink claims as the bundle manifest. `run_onchange_after_update-agy-plugins.sh.tmpl` installs the marketplace source directly, fails closed when the root manifest is absent or names a different plugin, and removes any bundle staged under `~/.local/share/agy-plugin-bundles/` by the previous shape before re-pointing the install.

`omp` wants the opposite of `agy` from the same archive, so the two do not share a copy. With the root `plugin.json` present, omp classifies the tree as an agent-plugins package and rejects every SKILL.md carrying Claude Code or Codex frontmatter keys, dropping 30 of 33 skills (`cb30ed4`). `agents.marketplaces` therefore declares a second `localArchive` authority, `compound-engineering-omp`, identical to the first except that its `exclude` also drops the archive's root `plugin.json`; the `*/` prefix matches only the archive's own top directory, so nested manifests inside skills survive. Both authorities share one `versionSource`, so the two copies always resolve the same version segment, and `run_after_compound-engineering-overlays.sh.tmpl` walks every compound-engineering authority so both receive the same ce-sweep references. omp identifies an installed plugin as `<name>@<marketplace>` and keeps a registered marketplace pointed at its recorded source, so `run_onchange_after_update-omp-plugins.sh.tmpl` re-points each row (marketplace remove, add, `install --force`, enable) rather than updating in place, and refuses a source carrying a root `plugin.json`. The re-point is recoverable rather than destructive: the reconciler reads the source currently registered for the marketplace id from `omp plugin marketplace list` (a `Configured Marketplaces:` header then indented `  <id>  <source>` rows; `--json` is accepted and ignored), skips the remove-and-add when it already matches, and on a failed add, install or enable restores the previous registration before it dies — removing the replacement first, because omp holds one registration per id, and naming both failures when the restore itself fails. The removal loop is the one part that does not yet work: it builds its uninstall id from the registry key while the install path builds it from the source manifest's `name`, and those differ in the current data (`compound-engineering-omp` against `compound-engineering-plugin`), so a declared removal hands omp an id it does not know. That mismatch is filed separately; the test covers the loop's shape and call order and deliberately asserts nothing about the id. Verification is `.ci/test-omp-plugin-reconcile.sh`.

`~/.claude.json` is deliberately UNMANAGED. It was a `readonly_` chezmoi target holding `{}`, and Claude Code rewrites it on every start (install method, first-start version, machine and user id, OAuth account, migration flags), so every apply reported `.claude.json has changed since chezmoi last wrote it`. The file is live tool state, not configuration this repository has an opinion about. Deleting the source stops management but leaves the already-deployed 0444 copy, and there is deliberately no `.chezmoiremove` entry — pruning it would delete the user's real Claude Code state.
An agent config file moves to per-key assertion when its vendor writes it during normal use and stays managed-readonly otherwise. Claude Code's `~/.claude/settings.json` is the assertion case. It is NOT a chezmoi target because Claude Code, aoe, and the plugin installer all write it during normal use. `run_after_config-claude-settings.sh.tmpl` asserts each declared `agents.claude.settings` leaf into it on every apply and leaves every undeclared path alone, so a declared path is authoritative and a UI change to it is reverted on the next apply. `hooks`, `enabledPlugins`, and `extraKnownMarketplaces` belong to other writers and are rejected at render time by `.chezmoitemplates/claude-settings-validate.tmpl`. Values under `env` reach the tool as strings, so an unquoted scalar renders as a JSON number and is ignored. Codex's `~/.codex/config.toml` is the second assertion case: `run_after_config-codex-settings.sh.tmpl` composes the declared `agents.codex.settings` leaves, the `mcp_servers` tables from `agents.mcp.servers`, and one leaf under `hooks` into one object and hands it to `settings-reconcile`, which changes only declared values but re-serializes the whole file, so Codex's own `projects`, `hooks`, `plugins`, and `marketplaces` tables and any `codex mcp add` result survive while comments and hand formatting in `config.toml` do not; `.chezmoitemplates/codex-settings-validate.tmpl` rejects those namespaces and `mcp_servers` at render time and allowlists the approval and sandbox posture keys. That one `hooks` leaf is the trusted_hash for this checkout's own Codex hook, computed by `.chezmoitemplates/codex-hook-trust.tmpl` from the plugin's rendered `hooks.json`: Codex refuses a third-party plugin hook until a trusted_hash for it exists in the user config, so without the leaf the hook this repository ships never runs and the failure is silent. It is declared by the script, not through `agents.codex.settings`, exactly as `mcp_servers` is, so the validate template's prohibition on that key stands unchanged. The record attests the hook DECLARATION only — the hook's script and the payload files it reads change with no re-trust — and its key carries no plugin-version segment, so a version bump does not invalidate it; adding a handler before it in the same event would, because the key's group and handler indices are positional. Verification is `.ci/test-codex-settings-reconcile.sh`. `run_before_guard-codex-skills.sh.tmpl` refuses the apply while `~/.codex/skills` is a real directory holding files, because chezmoi replaces it with the `~/.agents/skills` symlink by deleting it; `.ci/test-codex-skills-guard.sh` covers it. The Android CLI is the mirror image of that hazard — an outside writer into the managed skills tree rather than chezmoi deleting an outside directory — and is handled by not running its writer at all (see the skills paragraph above). Antigravity declares no settings leaves; `dot_gemini/config/mcp_config.json` and both harnesses' instruction files stay managed-readonly.

Repo-scoped agent tooling is a separate category from those user-scoped skills. `.agents/skills/<name>/SKILL.md` at the repository root would be a PROJECT skill for agents working in this checkout. Such a path is dot-prefixed, so chezmoi treats it as internal source and never deploys it, and it MUST NOT be confused with `dot_agents/skills/<name>/`, the user-scoped personal-skill source that DOES deploy to `~/.agents/skills/<name>`.

Model placement is declared in `agents.omp.settings` under one rule: usage is subscription-based, so the scarce resources are quota and latency, never per-token price. Every role runs `google-antigravity/gemini-3.8-flash:high`; `tiny` is the single exception at `google-antigravity/gemini-3.1-flash-lite:minimal`, because a background seat on the main model spends the quota that is actually scarce. The role NAMES are omp's own schema, so the set stays whole rather than trimmed to the ones in use. Pinning role values alone would leave `/model` free to reach an unapproved provider and an undeclared key survives the next apply, so `enabledModels` and `disabledProviders` close the selectable set alongside the roles. `startup.setupWizard: false`, `setupVersion: 1` and `symbolPreset: nerd` are one non-model exception: a first-run wizard blocks non-interactive use and writes config that competes with these assertions. `completion.notify`, `error.notify` and `ask.notify` are the other, all pinned to the string `"off"`: omp runs here only as an orchestration subagent, so a desktop popup per finished turn is noise, and those three are the whole notification surface of the pinned omp — the rest of its own `Notifications` UI group is a timeout and a terminal recap. `error.notify` already defaults to off and is declared anyway, because an undeclared key survives the next apply and declaring is what pins it. The cost is that a human driving omp interactively gets no popup for a waiting `ask`, and the enumeration is tied to the pinned version, so an omp bump must re-check for a new `*.notify` key. The values are enum tokens, not booleans; `.ci/test-omp-settings-reconcile.sh` holds their JSON type and value, because go-yaml already reads unquoted `off` as a string and quoting alone proves nothing. Two non-model groups join them. `astGrep.enabled: true` is declared because the omp arm of `.chezmoitemplates/agents-instructions.tmpl` names `ast_grep`, which the pinned build ships disabled; the key gates only that tool, since `astEdit.enabled` already defaults on. Twelve `skills.*` and `commands.*` switches pin the discovery scope. Five close project scope — `skills.enableAgentsProject`, `skills.enableClaudeProject`, `skills.enablePiProject`, `commands.enableClaudeProject` and `commands.enableOpencodeProject` — so a `SKILL.md` or a `.claude/commands/*.md` in a dispatched checkout never reaches the agent as a skill or a command. That is not isolation from the checkout: omp still loads a project's own `AGENTS.md` and `CLAUDE.md`, which the shared instruction core names as the binding local supplement, and no omp setting gates them. Four already-`false` user-scope twins are declared for the same reason `error.notify` is. The last three — `skills.enabled`, `skills.enableAgentsUser`, `skills.enablePiUser` — are pinned ON, because the managed `~/.agents/skills` tree is what this harness exists to use and an undeclared switch is one `/settings` toggle away from blanking it with no apply that restores it. The cost is a deliberate asymmetry: an omp worker dispatched into this repository cannot see its own committed `.agents/skills` and `.claude/skills` trees while claude and codex in the same worktree still read them, and nothing distinguishes a first-party checkout from an arbitrary one at settings-assertion time.

`run_after_config-omp-settings.sh.tmpl` asserts those leaves into `~/.omp/agent/config.yml`, which is NOT a chezmoi target — omp rewrites it through `/model`, `/settings`, and first-run setup, so a managed-readonly target produced permanent drift. `run_after_` rather than `run_onchange_`: a live vendor edit changes no chezmoi source fingerprint, so an onchange script would record a clean skip and never re-assert an overwritten value. The catalog probe FAILS OPEN — an unauthenticated provider returns a partial catalog with exit 0, so only a provider the catalog speaks for can prove a selector absent, and a selector it does cover but does not serve fails the apply by name. Convergence is read-then-compare, so a converged host writes nothing; a declared path omp does not report at all is a typo and fails loudly. Both omp reads are bounded without GNU `timeout`, which BSD/macOS hosts do not ship. An absent `omp` or `jq` fails OPEN, and the message says the declared settings were NOT asserted. Failing loudly was considered and rejected on evidence: `65-commands` exits 0 without a reconciler binary and swallows every reconcile failure, so omp can be legitimately absent at this phase; this script is `run_after_` and runs on every apply; and chezmoi stops at the first script error, so a `die` here would permanently strand `80-keys` and `90-src`, which have nothing to do with omp. `update-omp-plugins` dies on the same preconditions without that cost because it is `run_onchange_` and only runs when its fingerprint changes. The sibling `run_after_config-claude-settings.sh.tmpl` fails open for the same reason. What the skip must not do is read as convergence, so the disclaimer in the message is the contract `.ci/test-omp-settings-reconcile.sh` holds. `.chezmoitemplates/omp-settings-validate.tmpl` rejects another writer's namespaces at render time and proves every declared selector names a provider the allowlist admits. Verification is `.ci/test-omp-settings-reconcile.sh`.
Managed instruction targets are one file per harness, named for the native filename: `CLAUDE.md` for Claude Code (`dot_claude/`), `AGENTS.md` for Antigravity (`dot_gemini/`), `AGENTS.md` for Codex (`dot_codex/`), and `AGENTS.md` for oh-my-pi (`dot_omp/private_agent/`). All four render `.chezmoitemplates/agents-instructions.tmpl`. Each wrapper passes its harness id (`claude`, `agy`, `codex`, `omp`) and the Chezmoi context as `ctx`. Both harness branches carry an else arm, so an unknown id fails the render instead of emitting an empty paragraph a deployed file would carry silently. This file MUST use Chezmoi's template engine for conditional instructions. Select OS-specific text with `.ctx.chezmoi.os` gates, so only the applicable instruction reaches the agent; do not leave OS selection to prose such as "On Linux". Select harness-specific text with `.harness`. For a given OS, all four renders MUST match outside the paragraphs that start with `This harness is ` or `This harness runs `, and outside omp's delimited orchestration payload block. That block is the one permitted divergence: omp exposes no injection point that can vary by session role, so the everyone-payload rides in its instruction file instead of a hook. `.ci/test-agent-instructions.sh` extracts the block by its `<!-- omp-orchestration-payload:begin -->` / `:end` delimiters, fails when either is missing or repeated, compares the four cores with it removed, and separately compares the extracted block against a standalone render of `orchestration-everyone.tmpl`, so the exception cannot widen into arbitrary text. The `This harness is ` paragraph carries each harness's native file tools and Claude Code's delegation carve-out; it is asserted by substring needles AND compared whole against `.ci/fixtures/agent-instructions/harness-is-<harness>.txt`, which holds every such line for that harness in order (Claude renders two). The `This harness runs ` paragraph carries that harness's model-family tuning; it names a model family and never a model id or point release, and is compared whole against `.ci/fixtures/agent-instructions/harness-runs-<harness>.txt`. The two shared-body autonomy paragraphs — the `lfg` autopilot override and the workflow-required-step rule — are likewise compared whole, per harness and on both OS branches, against `.ci/fixtures/agent-instructions/lfg-autonomy.txt` and `.ci/fixtures/agent-instructions/workflow-required-autonomy.txt`, and the second MUST render exactly two lines below the first because its own text refers to that neighbour. Rewording any fixture-backed paragraph means updating its fixture in the same commit. `.ci/test-agent-instructions.sh` checks harness isolation, shared text, every fixture above, and the Linux and non-Linux OS branches; a contradicting sentence added elsewhere in the shared body is outside what any fixture can catch and stays a review obligation. Deleting a managed source stops management but does not prune an already-deployed target; pruning is a separate explicit decision.

## Verification (never deploy live `$HOME`)

The default check uses a per-user scratch directory, stub `op`, empty config, throwaway destination, and `--source "$PWD"`. Those four are mandatory for EVERY test or validation run, not a default an agent may drop for a quick check.

An agent MUST NOT invoke the real `op`, and MUST NOT let a render reach it. A live `op` read opens the operator's 1Password session, can prompt the desktop, and puts a real secret into rendered output the agent then prints, diffs, or writes to a scratch file. Shadowing the binary is not enough on its own: the check's `PATH` MUST name the stub directory and the system directories only (`"$scratch/bin:/usr/bin:/bin"`), never the inherited `$PATH`, so no code path can fall through to the real binary; resolve `chezmoi` to an absolute path first (`command -v chezmoi`, which zsh accepts and `type -P` does not) because that `PATH` no longer finds it. The stub must return newline-free secrets when parsing rendered JSON/TOML. `.ci/lib/render-gate-helpers.sh` already implements this contract in `render()` — a CI gate MUST use it rather than hand-roll the invocation.

The render MUST read this checkout and write nothing real: `--source "$PWD"` (never a nested worktree, never the deployed source) and a throwaway `--destination` under the scratch directory, never `$HOME`. Render every changed template/script through `chezmoi execute-template`; scripts are not targets and MUST be compared as rendered text on both sides. Disclose any onchange side effects, especially network/service restarts; the first apply that reruns `install-system-30-network` MUST be performed from a local console, not SSH/Tailscale.

`git diff --check`, `git status`, and a diff limited to the requested scope are required. `chezmoi archive --exclude=encrypted,externals,scripts` may compare extracted target trees, but archive bytes are not comparable by mtime and the archive omits scripts; compare rendered scripts separately and state that blind spot. If local rendering is unavailable, use CI artifacts from `.github/workflows/render-dotfiles.yml` and state the limitation.

```sh
scratch="$HOME/.cache/agent-scratch/chezmoi-op-stub"
mkdir -p "$scratch/bin" "$scratch/target"
: > "$scratch/empty.toml"
printf '#!/usr/bin/env bash\ncase "${1-}" in whoami) printf dummy@example.invalid;; *) printf dummy-secret;; esac\n' > "$scratch/bin/op"
chmod 700 "$scratch/bin/op"
chezmoi_bin=$(command -v chezmoi)
env PATH="$scratch/bin:/usr/bin:/bin" "$chezmoi_bin" --config "$scratch/empty.toml" --source "$PWD" --destination "$scratch/target" execute-template < .chezmoiscripts/70-agents/run_after_config-claude-settings.sh.tmpl
```

## Secrets and encrypted state

Secrets resolve through a live `onepasswordRead` of their `op://` reference at render time, with no cache; the private-key import (`.chezmoiscripts/80-keys/run_once_before_import-gpg-key.sh.tmpl`) bootstraps the GPG key used for `encrypted_` files. The sole sanctioned repository ciphertext is `dot_config/garden/encrypted_readonly_garden.yaml.asc` (GPG); edit the garden via the wrapper (`chezmoi edit ~/.config/garden/garden.yaml`), never commit plaintext. Host LUKS/MOK prompts are AES-encrypted with a key only in the user keyring; read consumers fail soft when unavailable, and only the nonblank prompt path may create a key. Never infer that desktop-mediated `op read` is unavailable from a failed interactive `op whoami`. GitLab PAT setup is data-driven; `auth-glab` remains OAuth fallback.

## Single source of truth

Edit data, not generated scripts or rendered targets:

| Data | Consumers |
|---|---|
| `.chezmoidata/commands.yaml` | repository-owned command manifest, producer classes, safety profiles, modes, and legacy migration evidence |
| `.chezmoidata/facts.yaml` | host identity, `gate:`/`gates:` decisions, probes and fail-safe direction |
| `.chezmoidata/fonts.yaml` | font archives, families, sizes and fallbacks for KDE/GNOME/fcitx/VSCodium/kitty |
| `.chezmoidata/vscodium.yaml` | additive VSCodium extension installer |
| `.chezmoidata/networking.yaml` | Wi-Fi importer, DNS defaults/overrides, unresolved-ref fingerprint |
| `.chezmoidata/kde.yaml`, `.chezmoidata/gnome.yaml` | desktop manifests and tunables |
| `.chezmoidata/agents.yaml` | MCPs, skills, neutral marketplaces, per-harness (`claude`, `agy`, `codex`) plugin install/removal declarations, Claude Code settings leaves (`agents.claude.settings`), and Codex settings leaves plus personal marketplace name (`agents.codex`) |
| `.chezmoidata/system.yaml` | `/etc` manifest gates/modes/checks/removals |
| `.chezmoidata/releases.json` | external tool versions plus per-platform asset URL and digest (`sha256`, or `sha512` where the source publishes only that); generated by `packages/release-lock`, never hand-edited; consumers read it only through `.chezmoitemplates/release-lock-ref.tmpl` |
| `.chezmoitemplates/agents-instructions.tmpl` | common user-scoped instruction core, rendered to each harness's instruction file |
| `dot_config/garden/encrypted_readonly_garden.yaml.asc` | private `~/.config/garden/garden.yaml` registry (GPG) |

Standalone release CLIs belong in grouped `.chezmoiexternals/{ai-agents,dev-tools,vcs,k8s,system,fonts}.toml`; language runtimes/registry backends belong in mise, with `bun` the single exception — it ships one self-contained GitHub-release binary, so it is delivered as an external against a committed version and sha256 instead of a mise `latest` whose lockfile this repository does not carry, and `bunx` is that same binary extracted under a second name because bun dispatches on `argv[0]`. Keep `rust-analyzer` external plus rustup component, use `/usr/bin/python3` for system scripts, and preserve npm/Bun/Yarn/pnpm hardening. A release artifact that REWRITES ITS OWN TREE is the one thing an external MUST NOT deliver, and the Flutter SDK is the standing case: an archive external makes every extracted file part of the target state, while the tool rewrites `.git/objects/info/commit-graph` and deletes and regenerates `version` and `bin/cache/flutter.version.json` on ordinary use, so the next apply asks to overwrite a file that changed since chezmoi wrote it and fails headless on `/dev/tty`. Excluding `.git` does not rescue it — `bin/internal/shared.sh` runs `git -C $FLUTTER_ROOT rev-parse HEAD` on every invocation and aborts without it. Such a tool is installed by its phase script (`.chezmoiscripts/00-tools/run_onchange_after_flutter.sh.tmpl`), which still reads the same lock through `release-lock-ref.tmpl` and verifies the recorded `sha256`, so the no-render-time-resolution rule below is unaffected.

External release resolution lives in the generated `.chezmoidata/releases.json` lock, so a source-state read performs no network I/O; the migration plan was [`docs/plans/2026-07-27-001-refactor-static-release-artifact-lock-plan.md`](docs/plans/2026-07-27-001-refactor-static-release-artifact-lock-plan.md). The lock is machine-generated by `packages/release-lock` and MUST NOT be hand-edited — add a tool to that package's registry instead. `.github/workflows/refresh-release-lock.yml` re-resolves it hourly via `cli.ts --out`, which overlays the resolution onto the committed lock and commits to the default branch only when an entry actually changed — a source that fails to resolve keeps its last committed entry, and the run still fails. For a `githubRelease` entry, per-platform URLs and checksums come from the release API's per-asset `digest`, so the refresh never downloads that artifact to hash it; the `android` vendor, whose upstream publishes no digest for artifacts this repository does verify, downloads its binaries to hash them instead. A declared target whose asset the release does not publish is a hard error, never a silent skip; that strictness is what caught `buf` naming its linux arm64 build `aarch64` while darwin and windows use `arm64`. A target upstream genuinely does not build is declared in `emulatedPlatforms`, served by the amd64 artifact under emulation, and marked `emulated: true` in the lock — so an `x86_64` URL under an `arm64` key is deliberate, not a bug. The lock is authoritative: every externals file, shared template, and version-consuming script reads versions, URLs, and digests through `.chezmoitemplates/release-lock-ref.tmpl`, and no template or script may resolve a release at render time (`gitHub*` builtins, `curl`, `git ls-remote`). `onePassword` is a `vendorManifest` vendor. It reads its version from the vendor RSS feed. Its artifact digest is null. `antigravity` is a `vendorManifest` vendor too, but it publishes only a sha512, so its tool `agy` records a `sha512` with a null `sha256`. `.ci/check-release-lock-digests.sh` therefore accepts either digest and rejects an artifact carrying neither; `refresh-release-lock.yml` and `ci.yml` both run it, so a lock change is gated before merge and not only by the hourly refresh. That gate also rejects an artifact URL carrying a `latest` path segment, because `android` is the vendor whose spec `source` is a moving path. The `source` and the recorded artifact URLs are not the same address: the resolver reads `.../android/cli/latest` only to discover the current version, and records `.../android/cli/<version>/...` for every artifact. `latest` is served with `max-age=0` over bytes that change beneath it, so a lock that recorded it left any host whose chezmoi HTTP cache held the superseded body failing every apply on a SHA256 mismatch that no later refresh could clear. Accepting a sha512 carries a consumer-side obligation: an artifact the gate passes on its sha512 must be consumed by an external that declares `checksum.sha512`, as `.chezmoiexternals/ai-agents.toml` does for `agy`.

Two vendored tools would otherwise fetch their own builds, so the lock is not the only thing that has to hold. Claude Code is the one that needs an explicit switch: `DISABLE_AUTOUPDATER=1` is declared twice, in `dot_config/environment.d/60-development.conf` for Linux and as the `env.DISABLE_AUTOUPDATER` leaf in `agents.claude.settings` for macOS, where that directory is not deployed. Both must keep the same value, and a Claude Code version moves only through a `.chezmoidata/releases.json` bump. This turns off the background updater alone — a deliberate `claude update` still works, and taking that away would need `DISABLE_UPDATES` instead. Verification is `.ci/test-claude-settings-reconcile.sh`, whose env-record type check is what stops the settings leaf being written as a JSON number the tool ignores. `.chezmoidata/agents.yaml` (`agents.claude.settings`) also pins `cleanupPeriodDays`, which turns transcript retention off so Tokscale keeps aggregating past the 30-day default; the price is that `~/.claude`'s `projects/`, `tasks/`, `shell-snapshots/`, `backups/` and tool-result files never shrink again, and the guard that keeps this leaf a JSON number — quoting it makes Claude Code reject the file and fall back to 30 days — lives in the same reconcile test. Orca IDE is the second, and it needs no switch at all: the app reads `resources/package-type` from its own tree and an `rpm` or `deb` marker makes its updater non-automatic by construction (`automatic: false, reason: manual-service-update-required`), where the AppImage build's `non-root` marker is what turns `autoInstallOnAppQuit` on. Installing the RPM is therefore the whole mechanism — do not add an environment variable for it. The app may still offer a package it asks the user to install by hand; that is a prompt, not a replacement, and a host moved above the lock that way re-converges once the lock overtakes that version, rather than being reverted.

## OS, desktop, and containers

Branch templates on `.chezmoi.os`; Fedora and Ubuntu 24.04 arm64 on a Jetson are managed Linux targets. Ubuntu support is only for the Jetson hardware profile. KDE/GNOME scripts use the desktop fact and soft-skip missing runtime/session tools. GNOME remains stock except data-driven listed exceptions, fonts, fcitx5, and password-only GDM. Do not turn runtime tool presence into a host fact.

A real container is `/run/.containerenv` or `/.dockerenv` without `/run/.toolboxenv`; the `facts.tmpl` and `.install-prerequisites.sh` `is_container`/`is_devbox` predicates MUST stay in lockstep. Containers skip package/system/auth/desktop provisioning, garden, and the GPG key, but keep CLI dotfiles, `00-tools`, and compound-engineering. No package installation occurs in a container. Change container skips only in the single gated `.chezmoiignore` block, never by editing scripts. `OP_SERVICE_ACCOUNT_TOKEN` is the CI secret path.
