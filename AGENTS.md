# Repository Guidelines

## Project structure

This flake configures personal machines, one per directory under `hosts/`. The NixOS host today is `MS-7D91-VM`, a VMware Workstation guest on the MS-7D91 PC, which runs Windows and lends the guest its Gpg4win agent through a TCP relay on an isolated VMware network, and the daily driver is a MacBook Pro macOS host. Non-NixOS Linux hosts on x86_64-linux or aarch64-linux are also in scope: they get the same user environment without the desktop. macOS hosts on aarch64-darwin are in scope too: they get the same user environment through nix-darwin, plus the GUI apps through Homebrew. Preserve the default Plasma desktop on NixOS hosts. Desktop configuration on non-NixOS Linux hosts, desktop customization, and coding-agent settings are outside the migration.

- `flake.nix`: host discovery, checks, and development tools. Every directory under `hosts/` is a host named by the directory. A directory without `host.nix` is a NixOS host: `mkHost` builds a production `<host>` and a `<host>-bootstrap` output under `nixosConfigurations` and sets `networking.hostName` from the name. A directory with `host.nix` is the kind its `kind` field names, which `lib/hosts.nix` reads. `kind = "linux"` is a non-NixOS Linux host: `lib/linux-host.nix` builds `homeConfigurations.<host>` and `systemConfigs.<host>`, each with a `<host>-bootstrap` twin. `kind = "darwin"` is a macOS host: `lib/darwin-host.nix` builds `darwinConfigurations.<host>` and `<host>-bootstrap`, nix-darwin systems with Home Manager and nix-homebrew inside.
- `hosts/<host>/`: one machine. A NixOS host has its hardware (`hardware.nix`), disk layout (`disko.nix`), and traits (`default.nix`). A non-NixOS host has `host.nix` (`{ kind = "linux"; system = "x86_64-linux"; }` or `"aarch64-linux"`) and a `default.nix` that sets its account (`my.user.name`, `my.user.home`) and traits. A macOS host has `host.nix` (`{ kind = "darwin"; system = "aarch64-darwin"; }`; Intel Macs are not supported) and the same kind of `default.nix`, with `my.user.home` under `/Users`. [Adding a host](docs/adding-a-host.md) walks through all three.
- `lib/`: `hosts.nix` splits the host directories by kind. `linux-host.nix` assembles a non-NixOS host into its standalone Home Manager and system-manager outputs, and `darwin-host.nix` assembles a macOS host into its nix-darwin system. The flake and the checks' fixture hosts both use them.
- `modules/shared/`: `host.nix` declares the host options every assembly imports: `my.bootstrap`, `my.hostName`, `my.kind`, `my.user.name`, `my.user.home`, and every trait's `enable` option. `darwin-apps.nix` maps every NixOS-only package to a macOS cask, a Nix package, or a reason to leave it out, and the `darwin-config` check fails on a package without a decision.
- `modules/nixos/`: system modules by subsystem -- `hardware/` (YubiKey), `system/` (base, boot, boot splash, sysctl/cleanup, nix-ld, agent-browser runtime deps, secrets), `desktop/` (Plasma/SDDM, fonts), `services/` (Podman, the rootless minikube cluster, printing, Tailscale, Proton VPN, systemd-resolved, the WiFiman Desktop daemon, the card-authenticated SSH server). Every NixOS host gets the one shared profile, `modules/nixos/profile.nix`, which `mkHost` imports: it imports every NixOS module and sets shared defaults with `lib.mkDefault`. There is no domain-level `default.nix` and no per-host import list. Hosts differ only through traits, the `my.*.enable` options that default to `false` (`my.gpgAgentRelay`, `my.sshServer`, `my.t3.cli`, `my.t3.desktop`), and through per-host values the host file sets. Hardware-specific modules stay inert until a host enables their trait. Modules, Home Manager (through `config.my.*`, never `osConfig`), and checks branch on traits, `my.kind`, and `my.bootstrap`, never on a host name; the `host-name-guard` check fails when a host directory name or a fixture host name under `tests/fixtures/hosts/` appears in `flake.nix`, `lib/`, `modules/`, `home/`, `tests/`, `scripts/`, `packages/`, or `.github/workflows/`.
- `modules/darwin/`: the system layer of a macOS host. Every macOS host gets `modules/darwin/profile.nix`, which imports `nix.nix` (nix-darwin owns `nix.conf` with the shared settings and `auto-optimise-store` off), `host-marker.nix` (`/etc/nix-config-host`), `defaults.nix` (macOS system defaults other than the Dock; today only automatic appearance), `dock.nix` (the Dock: one shared ordered list of pinned apps, with a host's `my.dock.hostApps` between ChatGPT and Discord and T3 Code only with `my.t3.desktop`, Downloads as the one right-side folder, recent apps hidden, tile size 32, every other Dock key left to the user; each apply replaces the pinned apps), `homebrew.nix` (nix-homebrew installs Homebrew; the casks come from `modules/shared/darwin-apps.nix`, cleanup `"none"`), `xcode.nix` (a root step after Homebrew that installs or upgrades Xcode from the Mac App Store with `mas` and never fails the apply), `app-store.nix` (a root step after the Xcode step that installs or upgrades KakaoTalk, then Flighty, from the Mac App Store the same way), `retired-casks.nix` (a root step after the App Store app step that uninstalls each cask the configuration no longer installs, today `grok-bot` and `orca`, through `brew uninstall --cask --force` as the primary user, never with `--zap`, then untaps `stablyai/orca`, tells an absent cask from a failed `brew list`, and never fails the apply), `tls-inspection-ca.nix` (with the `my.tlsInspectionCa` trait, `preActivation` decrypts `secrets/hosts/<host>/tls-inspection-ca.yaml` with the host identity into `/etc/ssl/nix-config/`, beside a bundle of this generation's roots plus that CA, aborting the apply when it cannot; shells, nix-daemon, and a login agent for GUI apps name the bundle in the six standard CA variables; a `postActivation` step adds SSL-only macOS admin trust when it is missing and never fails the apply), `network-recovery.nix` (with the `my.networkRecovery` trait, a root launch daemon runs `packages/network-recovery.nix` every 5 seconds; after a network change that leaves the Mac offline it flushes DNS, reconnects a connected Tailscale as the console user, then turns the default route's network service off and on, logging to `/var/log/network-recovery.log`), and `fonts.nix` (the shared font list).
- `modules/system-manager/`: the system layer of a non-NixOS host, applied through system-manager. It runs pcscd with the ccid reader drivers, takes over `/etc/nix/nix.conf`, and writes `/etc/nix-config-host`. It never writes files the distribution owns, such as `/etc/passwd`, `/etc/group`, `/etc/shadow`, `/etc/subuid`, `/etc/subgid`, or `/etc/shells`.
- `home/h82/`: Home Manager domains include `agents/`, `desktop/`, `dev/`, `security/`, and `shell/`. Active coding agents are Claude Code, Codex, OMP, and Antigravity. Antigravity's CLI (`agy`) and newest ACP runtime are on `PATH`, and T3 Code's `antigravity` instance runs the ACP release its pinned T3 Code embeds through an absolute `binaryPath` (`gemini.nix` merges the Antigravity settings and disables Gemini CLI `autoMemory`). `omp.nix` owns common writable documents through the reconciler and installs the OMP `architect`, `writer`, and `designer` agents; OMP runs only `synthetic` and `openrouter` models, `omp-roles.nix` assigns Synthetic models to every role and subagent, and `omp-declarations.nix` and `omp-declarations.py` render complete Synthetic/OpenRouter catalogs. `synthetic-models.nix` tracks GLM-5.3 at `max` for catalog watching; native Codex subscription models have no local definitions. Shared instructions reach Claude Code, Codex, OMP, and the Antigravity CLI (as `~/.gemini/config/rules` files), with the shared role vocabulary, per-harness tables, and the T3 Code routing table; Antigravity ACP sessions load no global instructions. Native skill roots and complete pinned CE assets reach all four harnesses, and so do the published design and stack skills `pinned-skills.nix` installs unchanged from the pins in `pinned-skills-pin.nix`, the local `design-lenses` wrapper around impeccable's lens references, and the local `ux-flows` skill; the shared instructions' UI and UX section routes work to them, and `tanstack-intent.nix` puts TanStack Intent's `intent` CLI on `PATH`. `usage.nix` installs `agent-usage` for cross-provider usage checks. `fff.nix` installs `fff-mcp`, and `fff-server.nix` gives the store-path command every harness registers as its `fff` MCP server: Claude Code (`~/.claude.json`), Codex, OMP, the Antigravity CLI (`~/.gemini/config/mcp_config.json`), and Grok Build (`~/.grok/config.toml`). OMP in ACP mode (T3 Code's OMP instance) and the Antigravity ACP runtime take MCP servers only from T3 Code's per-session request, so they get none, and the shared instructions' File I/O section tells agents to search with fff first. Claude Code's environment tier sets `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1`, which a macOS login agent also publishes to GUI apps, so bypass-permissions sessions skip the dangerous-rm prompt; any `PermissionRequest` hook or Bash, Edit, or Read ask or deny rule voids it. `retire-orca.nix` removes the retired Orca app's agent hooks, Claude status line, and state directories at activation. Pi/OpenCode provisioning is retired, its T3 entries stay disabled, and old state stays untouched. Settings tiers and activation reassertion follow `CONCEPTS.md`. Imports gate on `hostKind`; other logic reads `config.my.kind`.
- `scripts/`: authentication/rebuild helpers, OMP reconciliation, package updaters, and shared catalog tools. `omp-release` maintains the native OMP pin; `npm-release` maintains shared `acpx`; `antigravity-cli-release` and `antigravity-acp-release` keep the `PATH` Antigravity CLI and ACP runtime at Google's newest complete releases, and `t3code-release` writes T3 Code's ACP pin from the table its release embeds. `model-catalogs.yml` refreshes both complete snapshots every 30 minutes and verifies `omp-settings`, `omp-models-load`, and `synthetic-models` before publishing. `packages/` contains these tools and the shared instruction renderer.
- `tests/`: Python, shell, NixOS VM, and fixture checks. OMP package, restoration, catalog loading, headless tools, ACP, and release maintenance have dedicated checks; both maintenance workflows have sandboxed reconciliation tests. Protocol evidence does not prove actual T3 orchestration, authenticated requests, or native ARM/Darwin execution; report live hardware and authenticated runtime checks separately from repository checks.
- `.compound-engineering/artifacts/solutions/`: documented solutions to past problems (bugs, best practices, workflow patterns), organized by category (`best-practices/`, `boot-issues/`, `integration-issues/`, `logic-errors/`) with YAML frontmatter (`module`, `tags`, `problem_type`).
- `CONCEPTS.md`: shared domain vocabulary (verification, hosts, generations, coding-agent configuration); relevant when orienting to the repository or reading a learning that uses its terms.

The [implementation plan](.compound-engineering/artifacts/plans/2026-09-21-0149-feat-thinkpad-nixos-declarative-environment-plan.md) and [desktop plan](.compound-engineering/artifacts/plans/2026-09-22-1646-feat-ms-7d91-desktop-nixos-plan.md) record migration scope. The [host-generic composition plan](.compound-engineering/artifacts/plans/2026-09-28-0203-refactor-host-generic-composition-plan.md) records the shared profile, traits, and host discovery. The [non-NixOS Linux hosts plan](.compound-engineering/artifacts/plans/2026-09-30-2331-feat-non-nixos-linux-hosts-plan.md) records the second host kind, and the [macOS hosts plan](.compound-engineering/artifacts/plans/2026-10-07-1651-feat-macos-darwin-hosts-plan.md) the third. The [macOS Podman and minikube plan](.compound-engineering/artifacts/plans/2026-10-08-1724-feat-macos-podman-minikube-plan.md) replaces that plan's OrbStack runtime.

This repository changes experimentally and often on the user's own machines, so decisions recorded only in earlier plans, brainstorms, or learnings do not bind new work and the current request prevails.

## Build and development commands

- `nix develop`: enter the development shell.
- `nix fmt`: format Nix files with `nixfmt-tree`.
- `nix fmt -- --ci`: check formatting without edits.
- `nix flake check`: run declared checks. NixOS VM tests are not among them.
- `nix build --no-link .#vmChecks.all`: build every NixOS VM test; needs `/dev/kvm`. Build one with `.#vmChecks.<name>`.
- Pre-commit hook: `.githooks/pre-commit` runs `mise run lint-staged-markdown` to lint staged Markdown with `markdownlint-cli2`. The T3 Code `Setup` script enables it automatically; on other checkouts, run `mise trust && mise install`, then enable it with `git config core.hooksPath .githooks`. Skip it for a single commit with `git commit --no-verify`.

Before each push, run `git diff --check`, lint changed Markdown, run `nix fmt -- --ci` where the flake exposes a formatter (`formatter.aarch64-darwin` is absent, so macOS leaves formatting to Linux CI's `fmt` job), and run relevant checks that the local platform supports. Classify the complete branch diff from the PR merge-base, not just the last commit (`scripts/ci-docs-only-paths` marks a PR docs-only only when every changed path sits under `docs/`, `.compound-engineering/artifacts/`, or root-level `*.md`). Record local results and checks deferred to CI separately. A missing builder or unavailable output is pending evidence, never a pass, and does not by itself block publishing for CI.

Inert documentation, plans, and sweep state need no unrelated host or VM builds. When documentation is an input to a declared check (for example, `agent-instructions` reads `AGENTS.md` and `CONCEPTS.md`), that affected consumer check must still pass before readiness, even if docs-only CI skips it; obtain the result on a supported builder and record the revision. Runtime instructions and configuration require verification of their affected behavior even when their paths match CI's docs-only filter. Before declaring a PR ready, require successful current-head CI and all required platform evidence: for changes beyond inert documentation/state, flake evaluation, all declared checks, VM tests, and every production/bootstrap host output. CI may supply this evidence after push; if its path filter skips required checks, obtain them on supported builders before readiness. Report hardware checks separately; builds and VM tests do not prove hardware behavior.

For full verification on supported builders, list the outputs, then build each (run the VM command from Linux, never as a native Darwin output):

```sh
nix build --no-link .#vmChecks.all
nix eval .#nixosConfigurations --apply builtins.attrNames
for host in $(nix eval --raw .#nixosConfigurations --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#nixosConfigurations.$host.config.system.build.toplevel"
done
for host in $(nix eval --raw .#homeConfigurations --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#homeConfigurations.$host.activationPackage"
done
for host in $(nix eval --raw .#systemConfigs --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#systemConfigs.$host"
done
for host in $(nix eval --raw .#darwinConfigurations --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#darwinConfigurations.$host.system"
done
```

`homeConfigurations` and `systemConfigs` stay empty until `hosts/` holds a non-NixOS host, and `darwinConfigurations` until it holds a macOS host. `nix flake check` builds the x86_64 fixture hosts. An aarch64 output builds only on an aarch64 builder; CI builds those on its arm runners. A macOS output, and `checks.aarch64-darwin.darwin-outputs`, which builds the macOS fixture, build only on a macOS builder; off a Mac, leave them to CI's `build-darwin` job.

## Coding style and naming

Write all repository documentation in English, including READMEs, guides, plans, and captured learnings. Preserve exact commands, identifiers, and link targets. Any change to a routing table or the model roster in `home/h82/agents/instructions/instructions.md.tmpl` must update `docs/agent-routing.md` in the same change.

Use two-space Nix indentation and let `nix fmt` control layout. Keep each module focused on one concern. Follow existing lowercase hyphenated module and helper names. Remove redundant comments, but keep comments that explain non-obvious constraints. Keep nixpkgs on unstable and change `flake.lock` intentionally.

## Testing guidelines

Add regression checks beside related tests and register new checks in `flake.nix`. Register a NixOS VM test in `tests/vm-checks.nix`, not under `checks`, so `nix flake check` stays fast; the `vm-checks-guard` check fails otherwise, and CI builds each VM test in its own `vm-checks` job. CI's `flake-check` job only evaluates (`nix flake check --no-build`); the `check-shards` jobs build the checks, one per entry of `checkShards` from `tests/check-shards.nix`, and `check-shards-guard` fails when a check is in no shard. Add a check that reads a host generation to `hostClosureChecks` in `flake.nix` so it builds in the `hosts` shard; reproduce a shard with `nix build --no-link .#checkShards.<name>`. The `build-darwin` job builds every `darwinConfigurations.<host>.system` and every `checks.aarch64-darwin` entry on a `macos-15` runner; `darwin-config` evaluates the macOS fixture on Linux under `checks.x86_64-linux`. Use fake tokens, PINs, and test keys. VM checks require Linux with `/dev/kvm` access and disposable disks. Report hardware verification separately from VM evidence.

Keep one primary owner per contract at the strongest materialized boundary. Put binary and wrapper sanity checks in a package's `doInstallCheck` or `postInstallCheck` rather than separate per-platform flake checks; consolidate single-concern package presence tables and keep one workflow check per `.github/workflows/*.yml` file, extracting step scripts structurally with `yq` and `jq` rather than scraping prose comments. Exercise packaged scripts with `PATH` stubs instead of adding zero-caller command-override environment variables, injection parameters, or test-only `options.my.*` options. Read materialized outputs (`tests/lib/etc-file.nix`, `home-files`, enabled `launchd.agents` and `xdg.dataFile` entries) rather than raw `.source` attributes, execute `home.activation` blocks in a scratch `HOME` rather than grepping their text, and sweep `.drv` closures when adding or widening a check so `hostClosureChecks` matches actual host and Home Manager closures.

**Claude Code version bumps.** Claude Code is pinned in `packages/claude-code-manifest.json`, which `claude-code-release` rewrites and the dependency workflow commits as `chore(packages): bump claude-code to <version>`. The routing tables set Claude efforts for delegated roles, so a release-note check covers only defaults no routing table sets: the Claude Code session default (where `opus` is left undeclared because Opus 5.5 defaults to `medium`) and the T3 new-thread default effort if a release changes Opus 5.5's meaning of `medium`. Before a bump merges, check the release notes of the new version for those defaults. When the workflow pushes a verified bump straight to `main`, read the release notes on that bump commit before the next `nr switch` and tell the user what changed.

## Commit and pull request guidelines

Use lowercase Conventional Commit subjects, matching the history's `feat(nixos):` and `chore:` prefixes. Write imperative, specific subjects, preferably under 50 characters and never over 72. PRs should describe behavior changes, link relevant issues, and report check and build results.

- Assess every finding that a review, verification, or check step of any Compound Engineering skill reports about the work the workflow produces or changes, including testing gaps and residual risks.
- A verdict that chooses among alternatives, such as an adoption grade or candidate verdict, is not a finding.
- Apply substantiated defects and requirement violations in the same change, regardless of severity, confidence labels, or which list contains them. A skill's recommendation to defer or dismiss a finding does not replace your assessment.
- Judge each finding against the actual code, requirements, supported behavior, and concrete failure path or improvement. Consider impact, likelihood, and implementation and maintenance cost.
- Reject a finding when evidence shows its facts are wrong, it requires assumptions outside supported behavior, or it depends on a speculative failure chain without a credible execution path.
- Reject preference-only suggestions with no basis in project rules, clarity, or maintainability, and refactoring suggestions with no concrete benefit.
- Reject added complexity for a vanishingly unlikely edge case only when the expected harm does not justify the implementation and maintenance cost; record the failure scenario, likelihood evidence, impact, and cost.
- Rarity alone does not justify rejecting a credible security or data-loss defect, and a reproducer is not required when code analysis establishes the failure path. Investigate uncertain claims before deciding; lack of evidence is not proof that a defect is impossible.
- Do not dismiss a substantiated problem merely because it is outside the diff, low impact, or costly to fix. Choose the least costly adequate fix, including changes outside the diff when needed, and explain material trade-offs.
- Assess findings yourself without asking for routine approval to reject them, and record each rejection with its evidence or concrete reason.
- Leave a substantiated finding unapplied when every fix would weaken a safety check, the user declined its fix, its fix awaits a user decision, or no change in this repository can fix it.
- List unapplied findings under an `Unapplied review findings` heading in the pull request body, or in the final report when there is no pull request. Start each entry with one of these tags and its evidence or reason: `verified wrong`, `unsupported scenario`, `preference only`, `no concrete benefit`, `disproportionate complexity`, `weakens a safety check`, `declined by you`, `awaits your decision`, or `no fix in this repository`. Omit the section when there are none.
- A fix that would reverse a decision the user made, a brainstorm Scope Boundary or `session-settled` entry included, is asked in every run with a person present, autonomous runs included, and listed as `awaits your decision` in a run with no person present. In this repository, this covers only decisions made in the current task, including that task's brainstorm Scope Boundaries and `session-settled` entries; decisions recorded only in earlier artifacts are not asked about.
- When any other fix needs a user decision, such as a product or scope change, ask in an interactive run; in an autonomous run, apply the recommended fix and report it.
- When the user asked only for a review, report the assessed findings and ask once whether to apply all substantiated fixes.
- Report what you applied and rejected in the pull request body and the final report.

When watching a pull request from a local session, judge readiness on check evidence rather than on a quiet period. No automated reviewer runs here; `check.yml` is the only workflow on pull requests and reports as checks, so the settle window here is zero. When `ce-babysit-pr`'s own watcher runs, arm it with `--settle-seconds 0`; this supersedes that skill's instruction not to pass `--settle-seconds` on the ordinary arm. When T3 Code's watch wakes you instead, start no settle-window wait beside it; the evidence rule below still decides readiness. Evidence counts only when every workflow that runs on pull requests has a run registered against the current head and every such run is terminal. Jobs a run skips by design, such as the Nix jobs on a docs-only change, are part of that run's result, not missing evidence. Nothing else relaxes: outstanding threads, comments, `needs-human`, and the base and branch-currency blockers keep their current force. While evidence is incomplete, do not declare readiness and do not re-arm at a shorter window.

## Security and lifecycle constraints

Never evaluate or build with real plaintext credentials. Ordinary rebuilds use the local age identity; on the NixOS host the root filesystem is unencrypted, and Windows-side disk encryption (BitLocker or VMware VM encryption) protects it. On a non-NixOS host, they use the user-owned identity at `~/.config/nix-config/age/key.txt`, which the distribution's disk encryption protects; a macOS host keeps it at the same path, protected by FileVault. YubiKey use is for initial recovery, Git signing, and decrypting the bootstrap identities for SOPS work; three cards carry the same key, each with its own PIN. Publish gh/glab files only after successful decryption and keep them writable by their user. Report failures without printing tokens.

Re-encrypt and edit SOPS files yourself, on any host, without sudo. From the repository root, set `SOPS_AGE_KEY_CMD` to decrypt every `secrets/bootstrap/*/age-key.asc` with `gpg --batch --no-tty --decrypt`; one card opens every host's identity, so together they reach every file in `.sops.yaml`. Then run `sops updatekeys -y <file>` to re-encrypt, or pipe a JSON-encoded value into `sops set --value-stdin <file> '["<key>"]'` to change one value. Do not use `sops edit`, which opens an interactive editor, or `sops decrypt` to the terminal. [Adding a host](docs/adding-a-host.md#add-the-recipient-to-sopsyaml-and-re-encrypt) has the exact key command.

Do not partition or format the developer's host, enroll firmware or TPM keys, or run `nixos-rebuild switch` or `nr switch` as validation. Hardware installation requires an explicit instruction.
