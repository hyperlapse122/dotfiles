# AGENTS.md

This is the repository supplement for `github.com/hyperlapse122/dotfiles` checkout source state only. Edit this checkout, never deployed `$HOME`; apply only when the user asks for deployment. The common machine-wide user instructions are defined in `home/.chezmoitemplates/agents-instructions.tmpl` (which renders to each harness's user-scoped instruction file); edit that template when modifying global instructions. This file defines repository-specific Chezmoi attributes, script lifecycles, host fact gates, system manifests, and verification workflows.

## Source layout and attributes

The chezmoi source state lives under `home/` behind `.chezmoiroot`. Chezmoi source names encode targets: `dot_foo` -> `~/.foo`, `*.tmpl` is rendered, `private_` is 0600, `readonly_` is 0444, `executable_` is executable, `encrypted_*.asc` is gpg ciphertext, `home/.chezmoiscripts/run_once_*` runs once ever, `home/.chezmoiscripts/run_onchange_*` reruns when rendered content changes, `home/.chezmoiscripts/run_after_*` runs every apply, `home/.chezmoidata` is data, `home/.chezmoitemplates` is shared template code, `home/.chezmoiexternals` is fetched tooling, and `home/.chezmoiignore` is templated exclusion. Dot-prefixed source paths are internal; repository infrastructure lives outside `home/`, and the boundary gate (`.ci/test-top-level-deployment-boundary.sh`) enforces the source root. `crates/` and `packages/` are source-only build trees. `docs/` is repo-meta and never deployed: `docs/plans/` holds work plans, and `docs/solutions/` holds documented solutions to past problems (bugs, practices, workflow patterns) filed by category with YAML frontmatter (`module`, `component`, `problem_type`, `tags`) — relevant when implementing or debugging in an area one of them already covers. `CONCEPTS.md` at the repo root holds the shared domain vocabulary (entities, named processes, status concepts) — relevant when orienting to the codebase or discussing domain concepts.

Edit source files, not deployed files. The source directory itself is the only valid source context; nested worktrees cause recursive data errors, so checks MUST use `--source "$PWD"`. Never commit secrets.

## Apply lifecycle and script tree

Prefer `run_onchange_before_`/`run_onchange_after_` with a comment-only dependency fingerprint over unconditional `run_after_`. Keep bare `run_after_` only when live state must be retried on every apply. Fingerprint raw source content, including unresolved `op://` refs, never rendered secrets or build output. The shared `home/.chezmoitemplates/fingerprint.tmpl` contract is:

```gotemplate
{{ $sourceDir := .chezmoi.sourceDir -}}
{{ includeTemplate "fingerprint.tmpl" (dict "sourceDir" $sourceDir "globs" (list "path/to/source" "other/**")) }}
```

A glob that reaches OUTSIDE the deployed tree (`system/`, `packages/`, `crates/`, `firmware/`, `mise.toml`) resolves its base through `home/.chezmoitemplates/repo-root.tmpl` instead of `.chezmoi.sourceDir`, so the emitted `system/...`/`packages/...` lines stay unaffected by where the chezmoi source directory sits:

```gotemplate
{{ $repoRoot := includeTemplate "repo-root.tmpl" $sourceDir -}}
{{ includeTemplate "fingerprint.tmpl" (dict "sourceDir" $repoRoot "globs" (list "system/linux/etc/**")) }}
```

The partial hashes file content, uses `(stat .).isDir` to skip directories/output directories, and MUST NOT hash a rendered secret. A script with no external dependency hashes only its own rendered content; document that explicitly. A clean exit-0 skip is recorded as successful and will not retry until a fingerprint changes or `chezmoi apply --force` is used; retain `run_after_` only when that retry behavior is essential.
Script early exits MUST declare one of four skip directions: `harmless` (this host will never satisfy the condition, so not acting is correct and final), `transient-tolerable` (an eligible host is missing a precondition and failing here cannot block later chezmoi phases — with one settled exception, `sudo-elevation-guard`, whose 21 consumers do block later phases because a host that needs root and cannot get it has not converged, and whose exit-0 predecessor recorded twelve unprovisioned scripts as successful runs; do not copy that exception to a new site), `transient-blocking` (an eligible host is missing a precondition, but failing here would abort later phases, so it exits 0 behind a declared capability probe instead), or `operator-blocking` (an eligible host is blocked by a real, clearable condition that only an operator can clear and that no two-valued render-time probe can observe — a conflicting NVIDIA driver branch, a repository set that cannot be asked what it offers; it exits 0 so later phases survive, KEEPS its state record so `dotfiles-skips` goes on reporting an unconverged host, forbids a probe, and names both the operator action and the `chezmoi state delete-bucket --bucket=entryState` re-run in its message (`entryState` holds `run_onchange_` state; `scriptState` gates only `run_once_` scripts), because nothing changes the rendered content when the condition clears). `transient-blocking` is preferred wherever a probe exists: a capability probe is resolved by reviewed shell in `.install-prerequisites.sh`, which runs before the source state and cannot read `home/.chezmoidata`, so `operator-blocking` is for conditions whose definition lives in that data and only for those — a probe that COULD exist is a probe to add. Script early exits MUST use `home/.chezmoitemplates/skip.sh.tmpl` declarations across its four call forms (`skip_here`, `skip_step`, `done_here`, `not_applicable`), verified by `.ci/check-skip-declarations.sh`. The CI audit matrix `.ci/skip-declaration-site-matrix.yaml` freezes the historical R5 boundary for `run_onchange_`/`run_once_` scripts; post-freeze `run_after_` scripts are excluded from the matrix by lifecycle. Run `dotfiles-skips` to list outstanding `transient-tolerable`, `transient-blocking` and `operator-blocking` skips without inspecting apply scrollback; it only reads recorded state, never probes capabilities or hosts and never mutates anything. Retiring a record is the hook's job, not the reader's: `prune_stale_skip_records` in `.install-prerequisites.sh` already holds the command's capability verdicts, and on a command that RUNS SCRIPTS (`apply`, `update`, `init`) it removes every `transient-tolerable` record (the script retries on each apply and rewrites it if it still fails) and every `transient-blocking` record whose named probe now reads `available` (the fingerprint has changed, so that same command re-runs the script). `operator-blocking` records are never pruned — nothing re-runs their script — and a record the pruner cannot parse is left to be reported. Without this a wait-only site outlived its own condition forever, because a record is otherwise cleared only by a later declaration carrying the same `script`/`site` pair and a wait has no success-path twin. Bare `exit 0` or `return 0` on conditional script paths is prohibited. When render-time host facts alone decide a script's whole-script skip, `home/.chezmoiignore` excludes that script from deployment on the hosts where the skip would fire (`# BEGIN inapplicable-script-exclusions` … `# END inapplicable-script-exclusions`), dropping the former deploy-everywhere-and-self-select property while keeping the runtime guard as a second line. `headless-guard` is exempt and stays deployed because `INSTALL_SYSTEM_CONFIG_FORCE=1` overrides it per run, and runtime-state skips (such as CPU vendor or tool presence) remain runtime skips. `.ci/test-chezmoiignore-script-paths.sh` enforces parity between fact-skip exclusions and guard consumers. Because chezmoi preserves a `run_onchange_` script's recorded run-state while ignored, returning to an earlier host state (such as swapping desktops or unsharing a host) does not re-run returning scripts automatically; re-run them with `chezmoi apply --force` or delete the state bucket with `chezmoi state delete-bucket --bucket=entryState` (which re-runs every onchange script including network configuration, requiring a local console). A `transient-blocking` or `operator-blocking` skip record left by a script that later becomes excluded stays in `dotfiles-skips` until deleted by hand, because an ignored script never runs to clear its record.


Never add teardown/revert scripts. Delete managed source, use `home/.chezmoidata/system.yaml` `removed:`, declare a plugin in `agents.<harness>.pluginsRemoved`, or document a one-time manual reversal. A `home/.chezmoiremove` entry may also prune a runtime-created path chezmoi never deployed; `.agents/skills/ce-*` and `.local/state/unmanaged-repo-guard` are the standing cases. Numeric `home/.chezmoiscripts/` directories establish phase order; existing `run_*` naming and numeric ordering may be extended, and renaming an onchange script reruns it once per host.

A command store generation is named by an identity hashed from the unit's SOURCES, and the store records nothing about which bytes it was minted from, so a mint that runs before its producer does is indistinguishable from a converged one. The `00-tools` activation pass therefore runs `reconcile-all --defer-producer build`: it MUST NOT mint a generation for a unit `60-build` has not built yet, or the previous build's binary lands under the current identity, `65-commands` reads that completion marker and copies nothing, and the identity never moves again to trigger a repair. A deferred unit whose identity already has a completed generation is still activated, because linking one mints nothing, and nothing between `00-tools` and `65-commands` consumes a build-produced command. The second guard is in the reconciler: a completed generation whose staging path is NEWER than its own `.complete` marker was minted before the artifact it claims to hold, so it is re-minted from staging and swapped in with two renames (an in-place rewrite fails `ETXTBSY` against a running binary). That covers a build script that skipped on a host missing its toolchain, which the deferral alone does not. Verification is `packages/command-reconcile/test/reconcile.test.ts`.

Package installation is owned modularly by feature scripts in `home/.chezmoiscripts/30-components/` and base installers in `home/.chezmoiscripts/20-base/`. Package installation scripts MUST always inspect which packages are not yet installed (e.g. `rpm -q` on Fedora, `dpkg-query -W` on Ubuntu, `brew list` on macOS, `dotnet tool list -g` for global .NET tools) and only install missing packages, never blindly passing all declared packages to the package manager unconditionally. A failed install MUST NOT abort the apply and MUST NOT be hidden behind `|| true`: after the attempt the installer re-runs that same inspection, and when a declared package is still missing it prints the missing set with the by-hand install command, then leaves through a `skip_step` declaration that keeps its record (`operator-blocking`, or `transient-blocking` when a registry probe observes the verdict itself), and its success path removes that record. Repository setup (key import, COPR, repository bootstrap, metadata refresh) stays tolerant, because the verdict reports its effect. The devtools, apps, .NET, tailscale, flatpaks, podman, desktop-IME and base installers follow this policy today.

## Host facts, gates, and system configuration

`home/.chezmoidata/facts.yaml` is the sole host-identity registry: each fact has a type, `hook`/safe template/builtin probe, gates, and fail-safe `whenFalse`. Hook facts are written once per chezmoi command by `.install-prerequisites.sh`; template facts come from `home/.chezmoitemplates/facts.tmpl`. The hook's `is_container`/`is_devbox` predicate and `facts.tmpl` predicate MUST remain byte-for-byte lockstep: a real container is `/run/.containerenv` or `/.dockerenv` without `/run/.toolboxenv`; distrobox/toolbox is treated as the host. `jetson` is a template fact. It probes `/etc/nv_tegra_release`. `sharedHost` is a template fact. Its gate is true when `/etc/dotfiles-shared-host` exists, `jetson` is true, or `.chezmoi.username` contains `@`.

Gate grammar is `<fact>`, `!<fact>`, or `<fact>.<value>`; YAML values beginning `!` MUST be quoted. `facts-validate.tmpl` rejects unknown facts, missing probes, invalid comparisons, malformed desktop values, and undeclared emitted facts. Consumers use only `facts.tmpl`, `facts-sh.tmpl`, and `facts-gate.sh.tmpl`, never the cache. Every fact is render-time and fail-safe: false MUST skip rather than grant. A whole-script skip decided purely by render-time facts is also a `.chezmoiignore` exclusion, checked by `.ci/test-chezmoiignore-script-paths.sh`. `FORCE_NVIDIA` is an installer-only override, never a fact or system-file gate; `INSTALL_SYSTEM_CONFIG_FORCE` layers only on the headless guard. `stat` is required before absolute `include`; `glob` does not traverse symlinks; never use template `output` for a fact probe. Runtime scripts call shared `fact_gate()` and MUST NOT duplicate gate logic.

`system/linux/etc/**` mirrors `/etc`; `home/.chezmoidata/system.yaml` owns mode, gate, check, distro-scoped `removed:`, and reload behavior. Edit the manifest and tree, not installers. The modular `install-system-*` installers have independent onchange triggers. Reload only changed services; Bluetooth restarts only when Bluetooth files differ. Network changes can reload firewalld. The 30-network installer defers its explicit activation of resolved, NetworkManager, and Tailscale until manual restart or reboot. The login greeter MUST remain password-only on every managed host while in-session fingerprint remains available; on GDM that is the locked `enable-fingerprint-authentication=false` dconf key, and on any greeter authenticating through `password-auth` it is the fact that no sanctioned fingerprint mechanism writes that stack. On Debian-shaped hosts, polkit may add `pam_fprintd` only when the `common-auth` conjunction is true; MUST NOT use `pam-auth-update` or a `common-auth` integration for fingerprint support, because it would re-enable greeter fingerprint authentication and break the GDM/Fedora polkit boundary. On Fedora the fingerprint factor is enabled only through `authselect`, never by writing PAM files. That feature writes `system-auth`, and EVERY service that includes that stack in its auth phase gains the factor — verified on a live Fedora 44 host, those are `sudo`, `polkit-1`, `su`, `login`, `vlock`, `chsh`, `chfn`, `config-util`, `crond`, `kcheckpass` and `kscreensaver`. So **`sudo` accepts a fingerprint on a Fedora host with the feature enabled**, and so do `su`, the console `login`, and the Plasma lock screen. That whole set is the accepted scope, a deliberate amendment of the former sudo-is-password-only rule, taken because Fedora offers no sanctioned way to give polkit the factor without also giving it to the rest of the stack; stock `authselect` has no feature that separates them, so withholding the factor from the console `login` would mean withholding it from every Fedora host. The enumeration is host-verified rather than exhaustive: it was read off one host's installed packages, and another host may include `system-auth` in more services. The greeter guarantee is the one boundary the installer enforces rather than accepts, and it fails closed: `greeter_would_gain_fingerprint` resolves the greeter's own stack, and a display manager it does not recognize — or a stack it cannot resolve at all — WITHHOLDS the feature instead of assuming it safe. Password authentication remains accepted everywhere; the fingerprint is an additional factor, never a replacement for the greeter's. The face factor (Howdy, `install-system-34-face-auth`, gated on the declared `irCamera` fact) follows the same rule with one refinement: stock authselect has no face feature, so the installer derives a custom profile `custom/face-auth` from the stock `local` one — every file a symlink back to the base except `system-auth`, which gains one `pam_howdy.so {include if "with-howdy"}` line ahead of the fingerprint one, and `README` — and selects it with the host's existing feature set plus `with-howdy`. That is still authselect writing every PAM file; a script MUST NOT write `/etc/pam.d` or `/etc/authselect/system-auth` itself. The factor therefore reaches exactly the fingerprint's system-auth set, and two members cannot use it: `pam_howdy` runs the recogniser as the calling process's user, so polkitd (user `polkitd`, `policykit_t`) falls through to the next module, and the Plasma lock screen authenticates through `password-auth`, which the profile never touches — deliberately, because kscreenlocker starts its PAM conversation the moment the screen locks and a face factor there unlocks the screen for whoever just locked it. The greeter check is the shared `home/.chezmoitemplates/pam-greeter-guard.sh.tmpl` predicate (`greeter_would_gain_module`), bound per module and per profile by each installer, and withholds on the same unknowns. Howdy's dlib dependency comes from the `starfish/howdy-beta` COPR because Fedora 44 ships no `python3-dlib`; the IR emitter enabler is the upstream systemd tarball from the release lock. Its per-camera configuration is a fact about the camera model, so a captured file lives under `system/linux/etc/linux-enable-ir-emitter/` named for the v4l by-path device exactly as the tool wrote it, and the installer lands it before the emitter unit starts; only a file carrying a `status: start` instruction counts, because a failed `configure` leaves idle/disable residue behind. The upstream `configure` dialogue fails on this camera with "Impossible to reset the instruction", and the working control (unit 7, selector 6, `1 3 2 0 0 0 0 0 0`) was written by hand and verified by the greyscale frame brightness alternating bright/dark once `run` applied it. The face enrollment is biometric and stays a manual per-user step the installer reports rather than performs. Fcitx5 is the KDE/GNOME input method; the GNOME autostart entry MUST NOT add `X-GNOME-Autostart-Phase`. TPM2 uses the shared dracut/systemd-cryptenroll backend and blank/missing credentials skip. Plymouth remains distro-native; SDDM Breeze is gated on its installed theme. On Ubuntu, a username with `@` is authd-managed. The login-shell script uses `authctl user set-shell` only when that exact subcommand exists. Otherwise, it makes a schema-checked `sqlite3` update to the authd database. Never use Python. Never restart the authd daemon.
`system/linux/selinux/*.cil` holds the host's SELinux modules, outside the `/etc` mirror so an edit there does not move the `etc` fingerprint. `home/.chezmoiscripts/00-tools/run_onchange_before_00-selinux-policies.sh.tmpl` installs every one of them with `sudo semodule -X 400 -i`, and phase 00 `before` is deliberate: a module that describes what a later phase does must reach the kernel before that phase runs (issue #374). The set is SUPPRESSION ONLY — `dontaudit` rules against denials that managed work provokes and that nothing needs granted. A module here MUST NOT declare a type, label a file, or carry an `allow` rule: that is the protection boundary [`docs/plans/2026-09-07-1203-chore-remove-custom-selinux-policy-plan.md`](docs/plans/2026-09-07-1203-chore-remove-custom-selinux-policy-plan.md) retired, and re-entering it would bring back the relabel pass, the stale-domain re-exec warning, and the repair paths that only `chezmoi_t` could run. A suppression module needs none of those, because installing one changes what the kernel audits and never what it permits. A rule naming a type the base policy does not ship MUST sit in a CIL `(optional ...)` block: `pasta_t` comes from `passt-selinux`, which phase `30-components` installs, so an unwrapped reference fails to resolve at `semodule -i` on a host that does not have it yet — and because the installer runs first, under `set -euo pipefail`, that failure aborts every apply before the phase that would supply the type, permanently. An `optional` block is dropped when a symbol in it does not resolve, so the module installs and starts suppressing once the package arrives. Elevation is acquired INSIDE the `selinuxenabled`/`semodule` test rather than above it, for the same reason the script is first: the sudo guard renders a top-level ladder that exits 1 when no rung succeeds, and at phase 00 that aborts the whole apply on a host with nothing here to do. Adding a module is therefore a data-and-source change plus one CI obligation: the installer is a `sudo-elevation-guard` and `shared-host-guard` consumer, so a NEW installer script — not a new `.cil` file — moves the frozen fan-outs in `.ci/skip-declaration-site-matrix.yaml`, `.ci/check-skip-declarations.sh`, and `.ci/test-capability-cache.sh` together.

## Agent surfaces and ownership

All agent data is in `home/.chezmoidata/agents.yaml`. The managed harness set comprises `claude` (Claude Code), `codex` (OpenAI Codex CLI), and `omp` (oh-my-pi). MCP declarations in `agents.mcp.servers` are transport-neutral and render into universal `~/.mcp.json`, `~/.omp/agent/mcp.json`, and the `mcp_servers` tables of `~/.codex/config.toml`, with 1Password `op://` references resolved at apply time. `home/.chezmoitemplates/agent-mcp-servers-json.tmpl` is the one place the harness set is enumerated at render time; it fails on an unknown id rather than emitting an empty set. A server removed from the inventory is not pruned from `config.toml`; the Codex reconciler only adds and updates. OAuth entries stay headerless for native stores. A stdio server's optional `env` map is forwarded by the universal renderer, the Codex reconciler and omp's renderer. omp merges a per-server `env` over the inherited environment, so a value declared there reaches the server process and is written verbatim into `~/.omp/agent/mcp.json` — a plaintext credential does not belong in that field, and no renderer resolves `op://` inside it. Figma authorization is on demand. The zero-argument `figma-auth` command stores only omp's Figma OAuth record in `~/.omp/agent/agent.db`, accepts schema 6 or 7, and preserves unrelated records. Other harnesses use their native OAuth flow. Never commit tokens.

External skills come from `agents.skills.external` -> `home/.chezmoiexternals/ai-agents.toml` -> `~/.agents/skills/<name>`; keep the exact isolated subtree and no pin-bump workflow. GitHub-sourced skills (`agent-browser`, `improve`, `i-have-adhd`, `composition-patterns`, etc.) ship as archive externals extracting the `skills/<name>/` subtree. GitLab-sourced skills (`glab`, `glab-stack`) are raw single-file externals (`type = "file"` on `<name>/SKILL.md`) pinned to the glab release via `home/.chezmoitemplates/glab-release-ref.tmpl`, which `home/.chezmoiexternals/vcs.toml`'s glab binary also consumes. Locally-authored personal skills (unpublished) are managed directly under `home/dot_agents/skills/<name>/` and deploy to `~/.agents/skills/<name>`. `home/dot_agents/skills/` is harness-neutral; chezmoi deploys symbolic links `~/.claude/skills` and `~/.codex/skills` pointing to `~/.agents/skills` to ensure unified skill discovery across all harnesses. A GitHub entry's in-repo subtree is `skillPath`, defaulting to the `skills/<name>/` nearly every source repo uses; `stripComponents` is derived from it (the archive's own top directory plus each segment) and the include anchors on it, so the two cannot drift apart. `android-cli` is the entry that needs its own: `android/skills` files it under `devtools/android-cli/`. That skill is external rather than a byproduct of provisioning because `android init` — whose ONLY effect is installing it — writes it into the global skills directory of every agent it detects, and both of those are the symlinks above, so one call overwrote the managed `~/.agents/skills/android-cli` three times over with unpinned bytes from the CLI bundle, invisibly to chezmoi. `home/.chezmoiscripts/00-tools/run_onchange_after_android-sdk.sh.tmpl` therefore MUST NOT call `android init` (or `android skills add`/`update`); `android sdk install` needs neither. `.ci/test-android-skill-ownership.sh` runs the rendered script against a stub CLI to hold both halves.

The neutral `agents.marketplaces` registry carries two kinds. `localArchive` is a versioned download, and compound-engineering is one such archive that `claude` and `codex` each consume through their own reconciler. `localDir` is a tree chezmoi deploys rather than downloads, so it declares `path` (resolved against `$HOME`) instead of `source`, `externalPath` and a version selector; `dotfiles-claude-plugin` is the only one, and it is Claude-only. Codex discovers it through the chezmoi-owned personal marketplace `~/.agents/plugins/marketplace.json`, which resolves a `./`-relative plugin path against `$HOME` and not against the manifest's own directory, whose `name` is `agents.codex.personalMarketplace` and whose plugin paths are `./.agents/plugins/<registry key>` symlinks to the pinned archive, so a version bump moves the symlink target and `run_onchange_after_update-codex-plugins.sh.tmpl` runs `codex plugin add` for each declared row. `agents.<harness>.plugins` and `agents.<harness>.pluginsRemoved` declare the per-harness install and removal sets. `home/.chezmoitemplates/agent-plugin-rows.tmpl` validates every row against that registry — the exactly `{name, marketplace}` shape, the name charset, the duplicate rejection, and the os/container/jetson gates — and resolves each kind's source path; it is harness-agnostic and carries no per-harness branch. The eligible set is a render-time constant in both updaters, so an empty set renders a notice and no loop rather than a runtime skip.

Claude Code consumes a marketplace directory of either kind (`.claude-plugin/marketplace.json`, with the plugin's own `.claude-plugin/plugin.json` beside it; the Claude reconciler preflights both and the marketplace root doubles as the plugin root). Its `plugin marketplace add` is idempotent and rewrites a changed path in place, so a version bump needs no removal first, but its plugin cache is keyed by version and `plugin install` is a no-op once any version is present: `plugin update` is what re-resolves a bumped segment. `plugin enable` on an already-enabled plugin exits non-zero, and that one message is the only failure the updater treats as converged. Claude Code records both the marketplace declaration and the enabled set in `~/.claude/settings.json`, so an interactive `/plugin` change and the reconciler converge on the same file. `run_after_config-claude-settings.sh.tmpl` owns the LEAF, not the record: each `agents.claude.settings` key is a dot-separated path and only that leaf is written, so an undeclared key and the other members of an enclosing record both survive — the marketplace and enabled-plugin keys among them. Removing a path from the declaration stops the assertion but restores nothing. `hooks` (aoe), `enabledPlugins` and `extraKnownMarketplaces` (install-claude-plugins) are rejected at RENDER time by `home/.chezmoitemplates/claude-settings-validate.tmpl`, not merely avoided by convention; an empty declaration renders a notice and no assertion loop. The declaration is authoritative, so a value changed through the interface is reverted on the next apply and a value meant to stay adjustable is left undeclared — `theme`, `editorMode` and `verbose` deliberately are. Permission policy is the third undeclared category, and its surface is bounded rather than open: `permissions.defaultMode` is the ONLY `permissions.*` path a leaf declaration can express, and it is deliberately left undeclared. `permissions.allow`, `permissions.deny` and `permissions.ask` are lists, so asserting one would replace the whole list and drop every entry a user or a plugin contributed, and owning single entries would need a path syntax for list membership that the grammar does not have — that is a settled scope boundary, not a gap waiting on a mechanism. Because a permission grant would otherwise enter through the same data edit as a notification toggle, `home/.chezmoitemplates/claude-settings-validate.tmpl` screens for RISK as well as ownership: a path under a security-sensitive prefix, or one of the security-sensitive exact keys, is accepted only when its full path is on that partial's reviewed allowlist, so declaring one is a reviewed change to the template rather than a data edit. `skipDangerousModePermissionPrompt` is on that allowlist and stays globally pinned on every managed host, accepted rather than host-gated: `agents.claude.settings` has no `gate:` grammar, every managed host is the same single operator's own workstation, and adding per-key gating to the declaration is its own mechanism. Note also that Claude Code's precedence chain puts project-scope settings above user-scope ones, so a user-scope declaration is not a project-wide guarantee. Nothing validates that a declared path names a real Claude Code setting; no machine-readable settings schema is published, so a typo is asserted and reported as success while the product ignores it. Convergence writes nothing at all, and every cannot-assert path (missing `jq`, a malformed target, an ancestor holding a scalar or array) reports on stderr rather than exiting silently. An unwritable ancestor suppresses ONLY its own leaf: the declared paths are independent leaves with no invariant tying them together, so the writable ones are asserted, the blocked ones are named on stderr, and the damaged ancestor is left exactly as found — an all-or-nothing abort would have left the `DISABLE_AUTOUPDATER` pin unwritten behind one unrelated damaged key, with a green apply. ## Garden registry and `~/src` provisioning

This repository owns the garden registry and the apply-time provisioning of `~/src`. The user-scoped instruction core (`home/.chezmoitemplates/agents-instructions.tmpl`) keeps only the `~/src` layout rule and the worktree ownership rules and points here; every registry and provisioning detail lives in this section.

Edit the garden with `chezmoi edit ~/.config/garden/garden.yaml`, or decrypt/encrypt `home/dot_config/garden/encrypted_readonly_garden.yaml.asc` non-interactively, then apply. The deployed target is the 0444 plaintext `~/.config/garden/garden.yaml`. Never commit plaintext. The registry is its own only copy, so verify the round trip BEFORE overwriting the source: decrypt the freshly re-encrypted file again, confirm it parses and that both the tree count and the recipient key-id set are unchanged, and only then move it over the source.

On apply, `home/.chezmoiscripts/90-src/` runs the bootstrap automatically whenever the manifest changes — grow-all then the `setup-upstream` bootstrap — and a separate every-apply script registers every grown tree with Orca, so a manifest edit is normally self-provisioning (and fails the apply if a grow, bootstrap, or registration fails). The commands below are the same idempotent bootstrap, for first-host/manual or debug use:

```sh
garden grow <name>
garden cmd <name> setup-upstream
```

`garden grow` accepts multiple queries; `garden cmd` takes exactly one query, then command names. Use `'@*'` (or another glob carrying the `@` tree prefix) for many trees. A bare `'*'` resolves against gardens and groups BEFORE trees, so once the registry declares a `groups:` entry it matches that group and silently covers only its members — which is why `run_onchange_after_reconcile-garden.sh.tmpl` calls `grow '@*'` and `cmd '@*' setup-upstream`. Always prefix a wildcard with `@`. Grow creates the plain repo checkout with shallow history (`--depth 1`, `single-branch: false`) by default; run `garden cmd <name> unshallow` (or `'@*'`) to retrieve full history on demand for active development, rebasing, or log audits. `setup-upstream` ensures remote origin/HEAD is configured.

Orca registration is not a garden command: the apply-time script derives each project's Orca identity from the same remote url the layout rule reads, and sets the display name and the `~/.local/share/worktrees` base path. It is ADDITIVE ONLY — a project Orca already knows is left exactly as it is, so a rename or a deletion made in the Orca UI survives the next apply. Orca sidebar groups come from the registry's own `groups:` block: each declared group becomes an Orca project group of the same name, and the group name is the human product name, not the namespace segment (`ExamVue 365 Flow`, not `365flow`). Membership is declared, never derived from the path — a namespace holding several trees is not a group until the registry says so. Grouping is the one best-effort step: it is carried out over an internal Orca RPC surface, so it warns and leaves registration green rather than failing the apply. A project the operator has already filed under some group is never re-filed.

`src-audit` is read-only: missing tree => grow on demand; broken tree => grow; unmanaged => surface, never delete. A branch whose pull lacks tracking => rerun `setup-upstream` (audit does not check upstreams). It reports garden drift only; it does not audit Orca registration.

Standalone release CLIs belong in grouped `home/.chezmoiexternals/{ai-agents,dev-tools,vcs,k8s,system,fonts}.toml`; language runtimes/registry backends belong in mise, with `bun` the single exception — it ships one self-contained GitHub-release binary, so it is delivered as an external against a committed version and sha256 instead of a mise `latest` whose lockfile this repository does not carry, and `bunx` is that same binary extracted under a second name because bun dispatches on `argv[0]`. Keep `rust-analyzer` external plus rustup component, use `/usr/bin/python3` for system scripts, and preserve npm/Bun/Yarn/pnpm hardening. A release artifact that REWRITES ITS OWN TREE is the one thing an external MUST NOT deliver, and the Flutter SDK is the standing case: an archive external makes every extracted file part of the target state, while the tool rewrites `.git/objects/info/commit-graph` and deletes and regenerates `version` and `bin/cache/flutter.version.json` on ordinary use, so the next apply asks to overwrite a file that changed since chezmoi wrote it and fails headless on `/dev/tty`. Excluding `.git` does not rescue it — `bin/internal/shared.sh` runs `git -C $FLUTTER_ROOT rev-parse HEAD` on every invocation and aborts without it. Such a tool is installed by its phase script (`home/.chezmoiscripts/00-tools/run_onchange_after_flutter.sh.tmpl`), which still reads the same lock through `home/.chezmoitemplates/release-lock-ref.tmpl` and verifies the recorded `sha256`, so the no-render-time-resolution rule below is unaffected.

External release resolution lives in the generated `home/.chezmoidata/releases.json` lock, so a source-state read performs no network I/O; the migration plan was [`docs/plans/2026-07-27-001-refactor-static-release-artifact-lock-plan.md`](docs/plans/2026-07-27-001-refactor-static-release-artifact-lock-plan.md). The lock is machine-generated by `packages/release-lock` and MUST NOT be hand-edited — add a tool to that package's registry instead. `.github/workflows/refresh-release-lock.yml` re-resolves it hourly via `cli.ts --out`, which overlays the resolution onto the committed lock and commits to the default branch only when an entry actually changed — a source that fails to resolve keeps its last committed entry, and the run still fails. `cli.ts --prune-retired` removes unregistered tools from an existing lock without resolving or changing retained entries. For a reviewed single-tool change, `cli.ts --only <registered-tool>` resolves only that registry entry and preserves every unselected entry; it composes with `--out` or `--stdout`, while the hourly full refresh stays unchanged. For a `githubRelease` entry, per-platform URLs and checksums come from the release API's per-asset `digest`, so the refresh never downloads that artifact to hash it; the `android` vendor, whose upstream publishes no digest for artifacts this repository does verify, downloads its binaries to hash them instead. A declared target whose asset the release does not publish is a hard error, never a silent skip; that strictness is what caught `buf` naming its linux arm64 build `aarch64` while darwin and windows use `arm64`. A target upstream genuinely does not build is declared in `emulatedPlatforms`, served by the amd64 artifact under emulation, and marked `emulated: true` in the lock — so an `x86_64` URL under an `arm64` key is deliberate, not a bug. The lock is authoritative: every externals file, shared template, and version-consuming script reads versions, URLs, and digests through `home/.chezmoitemplates/release-lock-ref.tmpl`, and no template or script may resolve a release at render time (`gitHub*` builtins, `curl`, `git ls-remote`). `onePassword` is a `vendorManifest` vendor. It reads its version from the vendor RSS feed. Its artifact digest is null. The `antigravity` vendor resolver publishes only SHA-512. The retired `agy` tool is no longer in the registry. `.ci/check-release-lock-digests.sh` therefore accepts either digest and rejects an artifact carrying neither; `refresh-release-lock.yml` and `ci.yml` both run it, so a lock change is gated before merge and not only by the hourly refresh. That gate also rejects an artifact URL carrying a `latest` path segment, because `android` is the vendor whose spec `source` is a moving path. The `source` and the recorded artifact URLs are not the same address: the resolver reads `.../android/cli/latest` only to discover the current version, and records `.../android/cli/<version>/...` for every artifact. `latest` is served with `max-age=0` over bytes that change beneath it, so a lock that recorded it left any host whose chezmoi HTTP cache held the superseded body failing every apply on a SHA256 mismatch that no later refresh could clear. Accepting a sha512 carries a consumer-side obligation: an artifact the gate passes on its sha512 must be consumed by an external that declares `checksum.sha512`.

During the hourly lock refresh in `.github/workflows/refresh-release-lock.yml`, `.ci/ce-overlay-lock-hold.sh` validates candidate Compound Engineering releases against the overlay patches using `.ci/check-ce-overlay-patches.sh`. If the patches do not survive the candidate release, the script puts the committed Compound Engineering entry back using `bun run packages/release-lock/src/cli.ts --restore-tool compound-engineering --from <committed-lock> --out <lock>`. This holds back the Compound Engineering pin while allowing all other resolved tool updates in the refresh to commit and push. Restoring only the single tool entry prevents discarding unrelated tool updates. If the patches survive, `base.json` is stamped with the candidate tag and the bump lands. If the gate or the driver itself fails with a status other than valid, invalid, or unavailable (for example a tool is missing), the script rolls the stamp back, restores the entry the same way, and reports class `tooling-failure` with no rebase candidate; the rest of the refresh still commits and pushes, and the job then fails on its last step so the owner sees it. `.ci/ce-overlay-lock-hold.sh resolve-latest` is the one place that resolves the newest Compound Engineering release for `.github/workflows/rebase-ce-overlays.yml`, and `.ci/ce-overlay-classify-run.sh` (covered by `.ci/test-ce-overlay-classify-run.sh`) is the record job's mapping from job outcomes to a failure class.

Automated rebase pull requests and merging require five owner prerequisites. The preflight job checks P1 to P4 and prints one result line, `result=failed class=configuration missing=P<n> detail=<reason>`, plus a `P<n>: ...` line on stderr; the tracking issue lists the missing numbers. Search a failed run log for `missing=P<n>`.
- **P1 (`CE_REBASE_TOKEN`)**: Fine-grained personal access token with `Contents: read and write` and `Pull requests: read and write`, scoped to this repository only, with no bypass permission. Store it as a secret of the environment `ce-overlay-rebase` (P5), never as a repository secret. Failure signal: stderr `P1: the secret CE_REBASE_TOKEN is empty or not set` with `missing=P1 detail=token-missing`, or `missing=P1 detail=unauthorized` when the API answers HTTP 401. A tracking issue opens.
- **P2 (repository setting "Allow auto-merge": on)**: Enabled in GitHub repository settings. Failure signal: `missing=P2 detail=auto-merge-off` in preflight, or `missing=P2 detail=auto-merge-failed` when the pull request is opened. A tracking issue opens; rebase pull requests never merge directly without auto-merge.
- **P3 (branch ruleset on `main`)**: Ruleset on `main` requiring the status check `Final delivery` bound to the GitHub Actions source, "Require branches to be up to date before merging" enabled, and a bypass list containing only the P4 App in `Always` mode. Failure signal: `missing=P3` in preflight with `detail=check-missing`, `detail=check-unbound`, `detail=up-to-date-off`, or `detail=bypass` (the `CE_REBASE_TOKEN` identity can bypass the ruleset); or `result=push-rejected class=configuration missing=P3` when a marker or lock push is refused because the P4 App is not on the bypass list.
  - **P3 repository-wide cost**: A GitHub ruleset applies to the entire branch rather than a PR prefix. Requiring branches to be up to date before merging means that every commit pushed to `main` — including hourly lock refreshes (which push 1 to 6 times daily) and marker updates — invalidates every open pull request in the repository. Every open PR must merge `main` and re-run CI before it can merge. The repository owner accepts this cost when enabling P3.
- **P4 (GitHub App for direct pushes)**: An App installed on this repository with `Contents: read and write`, configured via variable or secret `CE_LOCK_APP_ID` and secret `CE_LOCK_APP_PRIVATE_KEY`, both stored in the environment `ce-overlay-rebase` (P5), never at repository level. Failure signal: `missing=P4 detail=app-missing` in preflight. Without the App, direct lock job pushes to `main` fall back to `GITHUB_TOKEN`, and under P3 they are rejected without the bypass.
- **P5 (deployment environment `ce-overlay-rebase`)**: An environment of that name with the deployment-branch policy "Selected branches and tags" that allows only the default branch (`main`), no required reviewers, and no wait timer. It holds `CE_REBASE_TOKEN`, `CE_LOCK_APP_ID`, and `CE_LOCK_APP_PRIVATE_KEY`; none of the three may exist as a repository secret or variable, because a repository-level value reaches a workflow run from any ref. Every job that reads one of them declares `environment: ce-overlay-rebase` in `.github/workflows/rebase-ce-overlays.yml` and `.github/workflows/refresh-release-lock.yml`, and `.ci/check-ce-overlay-wiring.sh` fails when one does not. GitHub evaluates a dispatched workflow at the selected ref, so a branch can edit the owner check in the workflow file; the branch policy is the control that keeps the credentials out of that branch's run. Failure signal: a run from any other ref stops before its first step with GitHub's message that the branch is not allowed to deploy to `ce-overlay-rebase`. An environment that is missing or has no secrets shows as P1 `detail=token-missing`, because GitHub creates an empty environment on first use. A policy that admits other refs shows no signal, so check it when the environment is created.

Two vendored tools would otherwise fetch their own builds, so the lock is not the only thing that has to hold. Claude Code is the one that needs an explicit switch: `DISABLE_AUTOUPDATER=1` is declared twice, in `home/dot_config/environment.d/60-development.conf` for Linux and as the `env.DISABLE_AUTOUPDATER` leaf in `agents.claude.settings` for macOS, where that directory is not deployed. Both must keep the same value, and a Claude Code version moves only through a `home/.chezmoidata/releases.json` bump. This turns off the background updater alone — a deliberate `claude update` still works, and taking that away would need `DISABLE_UPDATES` instead. Verification is `.ci/test-claude-settings-reconcile.sh`, whose env-record type check is what stops the settings leaf being written as a JSON number the tool ignores. `home/.chezmoidata/agents.yaml` (`agents.claude.settings`) also pins `cleanupPeriodDays`, which turns transcript retention off so Tokscale keeps aggregating past the 30-day default; the price is that `~/.claude`'s `projects/`, `tasks/`, `shell-snapshots/`, `backups/` and tool-result files never shrink again, and the guard that keeps this leaf a JSON number — quoting it makes Claude Code reject the file and fall back to 30 days — lives in the same reconcile test. Orca IDE is the second, and it needs no switch at all: the app reads `resources/package-type` from its own tree and an `rpm` or `deb` marker makes its updater non-automatic by construction (`automatic: false, reason: manual-service-update-required`), where the AppImage build's `non-root` marker is what turns `autoInstallOnAppQuit` on. Installing the RPM is therefore the whole mechanism — do not add an environment variable for it. The app may still offer a package it asks the user to install by hand; that is a prompt, not a replacement, and a host moved above the lock that way re-converges once the lock overtakes that version, rather than being reverted.


## OS, desktop, and containers

Branch templates on `.chezmoi.os`; Fedora and Ubuntu 24.04 arm64 on a Jetson are managed Linux targets. Ubuntu support is only for the Jetson hardware profile. KDE/GNOME scripts use the desktop fact and soft-skip missing runtime/session tools. GNOME remains stock except data-driven listed exceptions, fonts, fcitx5, and password-only GDM. Do not turn runtime tool presence into a host fact.

A real container is `/run/.containerenv` or `/.dockerenv` without `/run/.toolboxenv`; the `facts.tmpl` and `.install-prerequisites.sh` `is_container`/`is_devbox` predicates MUST stay in lockstep. Containers skip package/system/auth/desktop provisioning, garden, and the GPG key, but keep CLI dotfiles, `00-tools`, and compound-engineering. No package installation occurs in a container. Change container skips only in the single gated `home/.chezmoiignore` block, never by editing scripts. `OP_SERVICE_ACCOUNT_TOKEN` is the CI secret path.

## Repository delivery

Remain on the current branch; the common branch/commit/CI rules apply and this supplement may be stricter. Before a commit, verify the branch and Git Flow prefix unless it is the default branch. Keep changes within the requested scope, use lowercase Conventional Commits, and after any push watch both `render-dotfiles.yml` and `ci.yml` to terminal success.

## omp runtime integration

`packages/omp-orca` builds the native `before_agent_start` extension. It resolves the current Orca role on every call and replaces its own system-prompt block. `packages/orchestration-hook` supplies the shared payload and the complete lead context. Native patch contents are data.

`packages/figma-auth` builds the on-demand Figma OAuth command. Authentication tests use isolated stores and never read live credentials. The ordinary Orca TUI default remains Claude; all eight Git actions use omp with its declared model policy.

`packages/ce-overlay-rebase` implements the pure state machine, dispatch decision, and failure classifier for the Compound Engineering overlay rebase workflow. It validates and updates `home/.chezmoidata/ce-overlay-rebase.json`, decides whether to dispatch or defer rebase jobs, and categorizes failures into structured classes.
