A step that a skill, command, or workflow the user invoked by name declares mandatory MUST be carried out without a confirming question, in an interactive run as much as in an unattended one. A step is mandatory when the invoked skill's protocol, lifecycle sequence, gate, or definition of done requires it, whether or not the skill uses the word. This authority is transitive: it reaches the mandatory steps of every skill the invoked skill itself invokes as part of its own mandatory flow, so a chain such as `ce-brainstorm` to `ce-plan` to `ce-doc-review` is covered end to end. It covers the step's dispatch scale — the worker count, the reviewer set, and the cross-model fan-out that the workflow's own rules produce — and not only the decision to delegate at all. An interactive run MAY still ask about an open product, design, or requirements choice the workflow leaves to the user, about an action a separate prohibition in this file already gates, and about a question the invoked skill directs for such a choice. That exception never licenses a question that confirms whether a mandatory step runs, or at what dispatch scale. During an `lfg` run the autopilot paragraph above governs and these exceptions do not apply. Before a mandatory step sends work outside the current session, the agent MUST state what it is about to do; unless a prohibition in this file gates that send, the agent MUST proceed past that statement in the same turn, because it is a disclosure and not a confirmation prompt. The standing prohibitions in this file — the secrets rules, the destructive-action rules, and the not-the-user's-repository ask-first rule — govern independently on their own terms, and they are not conditions that convert a disclosure into a confirmation prompt. The recipient's identity and the step's cost alone change nothing. No spend threshold reopens the question. The bounds on the step are the workflow's own dispatch definitions and, for a dispatch the review-and-peer contract above binds, that contract's per-worker deadline and wall-clock bound; the shared dispatch-target rule above still picks each recipient. When the step dispatches workers, the disclosure MUST name the resolved dispatch count, so the user can interrupt a fan-out they did not expect without being asked to approve it; for any other outside send it MUST name the recipient and what is sent. This rule authorizes no dispatch the invoked skill does not itself define, and the authority follows the skill chain inside one session rather than travelling to a dispatched worker, which takes its own authority from the brief it is given. It overrides the general ask-before-ambiguous, costly, or irreversible action guidance for the step it covers, and it is the workflow-required-step rule named in the precedence list above.
