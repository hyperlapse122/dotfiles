# Repository reference

## Project structure

This Nix flake configures the owner's two personal machines, one per directory under `hosts/`:

- `MS-7D91` (`x86_64-linux`, NixOS): bare-metal desktop workstation running KDE Plasma 6 on Wayland, `nixos-unstable`, LUKS2 + Btrfs via disko, Secure Boot via Lanzaboote, and the proprietary NVIDIA driver.
- `MacBook-Pro-Mac17-9` (`aarch64-darwin`, `nix-darwin`): Apple silicon MacBook Pro (M5 Pro, model identifier `Mac17,9`), combining `nix-darwin`, Home Manager, and `nix-homebrew`.

Key directories and files:

- `flake.nix`: assembles the host configurations, packages, checks, formatter, and development shell. Every directory under `hosts/` is a host named by the directory. A directory without `host.nix` is a NixOS host: `lib/nixos-host.nix` (`mkHost`) builds a production `<host>` and a `<host>-bootstrap` output under `nixosConfigurations` and sets `networking.hostName` from the directory name. A directory with `host.nix` setting `kind = "darwin"` is a macOS host: `lib/darwin-host.nix` builds `darwinConfigurations.<host>` and `<host>-bootstrap`, `nix-darwin` systems with Home Manager and `nix-homebrew` inside. Only `nixos` and `darwin` host kinds are supported.
- `hosts/<host>/`: one machine. A NixOS host has `hardware.nix`, `disko.nix`, and `default.nix`. A macOS host has `host.nix` (`{ kind = "darwin"; system = "aarch64-darwin"; }`; Intel Macs are not supported) and `default.nix` setting `my.user.name`, `my.user.home` under `/Users`, and traits. [Adding a host](adding-a-host.md) walks through both.
- `lib/`: `hosts.nix` splits host directories by kind, `nixos-host.nix` assembles a NixOS host, `darwin-host.nix` assembles a macOS host, and `host-facts.nix` builds the shared fact record passed to the user layer and instruction template.
- `modules/shared/`: `host.nix` declares the host options every assembly imports: `my.bootstrap`, `my.hostName`, `my.kind`, `my.user`, `my.locale`, `my.desktopSSH.publicKey`, `my.printing.queues`, `my.dock.hostApps`, and every trait's `enable` option. Both platforms use `wired-network.nix` for the encrypted profile path and the condition that enables the profile. `darwin-apps.nix` maps every NixOS-only package in the user environment to a macOS Homebrew cask, a Nix package, or an explicit exclusion reason, guarded by the `darwin-config` check.
- `modules/nixos/`: system modules by subsystem — `hardware/` (`bluetooth-audio.nix`, `dualsense.nix`, `iphone-restore.nix`, `nuphy-gem80.nix`, `nvidia.nix`, `sennheiser-btd.nix`, `yubikey.nix`), `system/` (`base.nix`, `boot.nix`, `boot-splash.nix`, `desktop-ssh.nix`, `nix-cleanup.nix`, `nix-ld.nix`, `agent-browser-deps.nix`, `secrets.nix`), `desktop/` (`desktop.nix`, `fonts.nix`, `user-avatar.nix`, `winbox.nix`), `services/` (`minikube.nix`, `ollama.nix`, `podman.nix`, `printing.nix`, `proton-vpn.nix`, `resolved.nix`, `ssh-server.nix`, `tailscale.nix`), `wifi.nix`, and `wired-network.nix` (with `my.wiredNetwork.enable` on production outputs, `nixos-wired-network.service` runs before NetworkManager and renders the encrypted `secrets/hosts/<host>/wired-network.yaml` into the `wired-static` keyfile under `/run/NetworkManager/system-connections/`, failing open to DHCP on any bad or undecryptable file). Every NixOS host imports `modules/nixos/profile.nix`, which imports every NixOS module and sets shared defaults with `lib.mkDefault`. Hosts differ only through traits (`my.*.enable`) and per-host values in `hosts/<host>/default.nix`. Modules, Home Manager (through `config.my.*`, never `osConfig`), and checks branch on traits, `my.kind`, and `my.bootstrap`, never on a host name; the `host-name-guard` check fails when any host directory name or fixture host name under `tests/fixtures/hosts/` appears in `flake.nix`, `lib/`, `modules/`, `home/`, `tests/`, `scripts/`, `packages/`, or `.github/workflows/`.
- `modules/darwin/`: the system layer of a macOS host. Every macOS host gets `modules/darwin/profile.nix`, which imports `nix.nix` (`nix-darwin` owns `/etc/nix/nix.conf` with `auto-optimise-store = false`), `host-marker.nix` (`/etc/nix-config-host`), `defaults.nix` (automatic light/dark appearance), `dock.nix` (ordered persistent Dock apps with `my.dock.hostApps` after personal apps and before Ghostty, T3 Code when `my.t3.desktop.enable` is on, `~/Downloads` folder, recent apps hidden, tile size 32), `homebrew.nix` (`nix-homebrew` installs Homebrew, the `aria2` and `container` formulae, and the casks from `modules/shared/darwin-apps.nix`, with cleanup `"none"`), `xcode.nix` (runs `macos-xcode` on production switches after Homebrew to install/select Xcode via `xcodes` using `secrets/hosts/<host>/apple-account.yaml`), `app-store.nix` (installs/upgrades KakaoTalk and Flighty via `mas`), `retired-casks.nix` (uninstalls retired casks `grok-bot`, `orca`, and `wifiman` via `brew uninstall --cask --force` without `--zap` and untaps `stablyai/orca`), `container.nix` (starts Apple's `container` runtime API when stopped, installs its recommended kernel, and enables the login service while leaving a running runtime untouched), `tls-inspection-ca.nix` (with `my.tlsInspectionCa.enable`, decrypts `secrets/hosts/<host>/tls-inspection-ca.yaml` into `/etc/ssl/nix-config/`, exports the six CA bundle variables across shells, `nix-daemon`, and GUI apps, and adds macOS admin SSL trust), `network-recovery.nix` (with `my.networkRecovery.enable`, runs `org.nixos.network-recovery` every 5 seconds and sets `CLAUDE_BYTE_STREAM_IDLE_TIMEOUT_MS=60000`), `wired-network.nix` (with `my.wiredNetwork.enable`, runs `macos-wired-network` at the end of production switches to apply the static IPv4, DNS, and IPv6-off settings in `secrets/hosts/<host>/wired-network.yaml` to the adapter with the declared MAC), `sudo-touch-id.nix` (Touch ID for `sudo` through `/etc/pam.d/sudo_local`, with `pam_reattach` for tmux), and `fonts.nix`.
- `home/h82/`: Home Manager domains (`agents/`, `desktop/`, `dev/`, `security/`, `shell/`, and `t3code.nix`). Active coding agents are Claude Code, Codex, Pi (built from pinned source, declaring the local Ollama model on production hosts alongside the Synthetic catalog and the OpenAI and Anthropic model lists in `models.json` and adding native question/Exa tools in `pi.nix`; `provider-models-watch` refreshes the lists `openai-models.json` and `anthropic-models.json` from each provider's list API and models.dev, and `pi.nix` declares only the listed models that Pi's compiled catalog lacks, computed from the catalog the Pi build pins), and OpenCode v2 (`opencode.nix`: the release binary pinned in `packages/opencode-release.json`, the Synthetic models Pi shows, the same OpenAI and Anthropic model lists, the OpenCode Go models of the committed `opencode-go-catalog.json` snapshot, and credentials seeded from the published keys by `opencode-auth-sync`), and omp (`omp.nix`: the release binary pinned with its tag's commit in `packages/omp-release.json`, installed through upstream's `programs.omp` Home Manager module from the `omp` flake input locked to that same release tag, with its `~/.omp/agent/config.yml` settings declared in the module and copied into place as a writable file on activation; no shared instruction or skill delivery yet). `xcode-skills.nix` exports the selected Xcode's skills on macOS production activation. `synthetic-models.nix` tracks the Synthetic models used for catalog watching. `fff.nix` installs `fff-mcp`, and `fff-server.nix` registers the `fff` MCP server for Claude Code (`~/.claude.json`) and Codex (`~/.codex/config.toml`). `tanstack-intent.nix` puts `intent` on `PATH`. Settings tiers and activation reassertion follow `CONCEPTS.md`.
- `crates/pinentry/`: Rust workspace for `dotfiles-pinentry` (`packages/pinentry-keyring.nix`), the GnuPG pinentry wrapper that stores per-card OpenPGP user PINs in Secret Service (`kdewallet`) on NixOS or the macOS Keychain under `dotfiles.pinentry.openpgp` (`yubikey:<serial>:user`) and falls back to `pinentry-qt` or `pinentry_mac`.
- `scripts/` and `packages/`: authentication and rebuild helpers (`nr`, `nr-darwin`, `prepare-age-identity`, `restore-age-identity`, `recover-age-identity`, `install-user-age-identity`, `host-secrets`, `publish-cli-auth`, `desktop-ssh`, `tls-inspection-ca`, `network-recovery`, `macos-xcode.py`, `macos-wired-network.py`, `nixos-wired-network.py`, `macos-container.sh`), the shared decrypt and validation module `wired_network_common.py` that both wired-network tools import (packaged with `packages/macos-wired-network.nix` and `packages/nixos-wired-network.nix`), agent helpers (`agent-instructions`, `agent-settings`, `agent-plugin-sync`, `opencode-auth-sync`, `pi-state`, `t3-instructions.py`, `xcode-skills`), and package release updaters, including `opencode-release`, which reads the release list because `releases/latest` points at OpenCode v1, and `omp-release`, whose new pin also moves the `omp` input's tag and lock in the same commit. `opencode-go-models-watch` rewrites the Go catalog snapshot on the 30-minute schedule.
- `packages/default.nix` lists the packages the flake exposes on Linux and macOS.
- `tests/linux-checks.nix` and `tests/darwin-checks.nix` register checks for each builder. Both import `tests/shared-checks.nix`. `tests/check-shards.nix` groups Linux checks for CI, and `tests/vm-checks.nix` registers the NixOS VM tests.
- [Project checks](agent-check.md) covers the dotfiles checker, the pre-commit hook, and CI registry policies. Home Manager also installs `agent-browser` for standalone render checks and `ctx7` with the pinned `find-docs` skill.
- `CONCEPTS.md`: shared domain vocabulary (verification, signing keys, desktop SSH, hosts, generations, coding-agent configuration).

## Local Ollama models in Pi

Pi starts with Synthetic. To use local inference, run `/model` in Pi and choose the Ollama entry for your host. The NixOS desktop uses `ollama/pi-qwen3:4b-instruct-32k`; the Mac uses `ollama/pi-qwen3-coder:30b-64k`. To start directly with the local model, run `pi --model` followed by its full name. This form also works when the staged Synthetic key is missing. Pi sends that model's inference requests to the local server. Network-backed tools such as web search still need a connection.

The first setup needs internet access to download about 2.5 GB on NixOS or 19 GB on the Mac. Run `ollama list` to see when the `pi-` model appears. It shares its weights with the downloaded base model. After that, it works offline and enters memory on demand. If a download fails, restore connectivity and the provisioning job will retry.

On NixOS the owner's systemd user manager starts at boot. Check `systemctl --user status ollama ollama-provision` for server or download failures. On macOS the official Ollama app starts at login. If macOS requests approval, allow Ollama in System Settings → General → Login Items & Extensions. If the app was already running when you first applied the configuration, quit and reopen it to pick up the local-only setting. Run `ollama list` after the app starts to check model availability.

## Full verification commands

For full verification on supported builders:

```sh
nix fmt -- --ci
nix flake check
nix build --no-link .#vmChecks.all
nix eval .#nixosConfigurations --apply builtins.attrNames
for host in $(nix eval --raw .#nixosConfigurations --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#nixosConfigurations.$host.config.system.build.toplevel"
done
nix eval .#darwinConfigurations --apply builtins.attrNames
for host in $(nix eval --raw .#darwinConfigurations --apply 'c: toString (builtins.attrNames c)'); do
  nix build --no-link ".#darwinConfigurations.$host.system"
done
```

## CI job routing

A `darwinConfigurations` output and `checks.aarch64-darwin.darwin-outputs` build only on `aarch64-darwin`. In CI (`.github/workflows/check.yml`), pull requests run `fmt`, `changes`, `markdown-lint` (on docs-only PRs), `flake-check` (`nix flake check --no-build`), and the `light-*` shards of `checkShards`. The heavy closure jobs (`host-checks`, `vm-checks`, `build`, and `build-darwin`) run on a push to `main`, a manual `workflow_dispatch`, and on a later push to or reopening of a pull request that has the `full-ci` label. Adding `full-ci` starts a separate run with only the closure jobs, beside the run already on the head; a run for any other label has no jobs. Label runs never cancel or get cancelled, so the run a pull request opens with never includes the closure jobs, and a push leaves the previous head's label run to finish.
