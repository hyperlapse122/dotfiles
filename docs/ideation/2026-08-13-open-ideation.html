Grounding Context

The candidates were generated against a scan of the repository, its institutional memory, and external research into the surrounding ecosystem, then re-verified file-by-file during filtering.

Codebase Context

  • Shape. chezmoi source state for github.com/hyperlapse122/dotfiles, provisioning a single Fedora workstation. Declarative data in .chezmoidata/ feeds shared partials in .chezmoitemplates/, which render 50 ordered scripts across nine numeric phases (00-tools → 90-src). Externals fetch release-locked binaries; system/linux/etc mirrors root-owned /etc; crates/ holds a Rust haptic daemon and packages/ a Bun/Vite+ TypeScript workspace.
  • Measured scale. Scripts 50 files / 6,238 lines · shared templates 22 / 2,008 · CI 34 / 3,923 · workflows 3 / 1,239 · .chezmoidata 13 / 2,392 · docs/ 129 / 28,561 (of which docs/plans/ is 112 / 27,287) · Rust 1,983 · TypeScript packages 63 / 5,890.
  • Cadence. 672 human commits and 68 bot commits in 90 days — one maintainer, heavily agent-assisted, no reviewer. Hot: the agent-policy stream (.chezmoidata/agents.yaml, releases.json). Cold: KDE, GNOME, Fedora and /etc provisioning.
  • Strongest existing machinery. Render-time fail-safe gates that abort the apply on an unknown fact name; comment-only dependency fingerprints that re-trigger a script when raw source changes; an hourly release-lock refresh that preserves last-good entries on partial failure; and behaviour-oriented CI that renders artifacts, drives a real tmux transport, and asserts .chezmoiremove canaries.
  • Recurring friction found. A soft exit 0 is recorded as a permanent success, so a script that skipped for a missing precondition never retries. Two first-apply defects on record were unrecoverable without chezmoi state reset. A build cache replayed stale binaries after a source-only change. Nineteen scripts tell the operator to recover with a repo-wide chezmoi apply --force.

Institutional memory

  • No CONCEPTS.md and no docs/solutions/. Durable knowledge lives in 112 dated implementation plans plus docs/residual-review-findings/, docs/decommission/ and docs/feedback-sweep/. Roughly 3.7 plans land per active day.
  • Conventions extracted from the newest plans: encrypted registry edits go through protected scratch with a byte-compared decrypt round-trip; prefer one existing declarative surface over adding a runtime variant; retirement is a clean cutover with isolated rendering and explicit secret-absence assertions; and a plan's own “Definition of Done” is never evidence that it shipped.

External context

  • chezmoi's run_onchange_ reruns on rendered-content change and run_once_ records a rendered-content SHA-256 in a state database; upstream explicitly warns that scripts break the declarative model and must be idempotent. Installed here: v2.71.0.
  • Cross-harness agent configuration is an unsettled category — agent-setup, agents-sync and dot-agents all exist, all are small, and none has become a standard. Codex layers AGENTS.md with a 32 KiB project-guidance cap.
  • MCP security guidance requires per-client consent and least privilege: syncing server declarations is not sufficient, because tool-approval policy is a separate surface no existing sync tool expresses.
  • Ansible contributes check mode, diff mode and Molecule's disposable scenario matrix; ansible-pull adds --only-if-changed and --verify-commit. GitOps pull-and-reconcile is the closest structural analogue, but a workstation is mutable, interactive, and holds irreplaceable state.

1

A skip must not lie — and un-lying it must be cheap

Confidence 92% Complexity Medium 5 of 6 lenses converged
Description

Four moves that share one root. Declare the fail direction. facts.yaml already carries a worked-out doctrine that every gate needs a per-fact harmless value, and that two facts are inverted so a uniform false would fail open. Every soft skip in the repo is an undeclared fail direction; make declaring it mandatory, so a script whose skip is not harmless cannot simply exit 0.

Render a rerun key. fingerprint.tmpl hashes file content only, so every non-file rerun input is hand-serialised differently — the phase-60 haptic script already invents one for itself. Extend the partial to accept declared value inputs alongside globs, and a transient skip self-heals when the value changes.

Stop printing the false promise. Route every skip through a shared partial that renders its own retry sentence from the script's filename prefix, and add a CI check banning the literal strings inside any run_onchange_ or run_once_ file.

Make remediation surgical. Ship a helper that resolves a script name to its state key and deletes only that entry, plus an optional last phase that re-triggers deferred work whose precondition has since appeared.

Basis

direct: run_onchange_after_config-gnome-app-grid-order.sh.tmpl contradicts itself 29 lines apart — :44-48 warns that “that skipped run is recorded as done and will NOT re-run on the next apply just because a live GNOME session appeared”, while :73 prints “skip (retries next apply)”. Verified: 10 such lines across 6 scripts. run_onchange_after_auth-gitlab.sh.tmpl:35-37 states the same rule a second time, and run_onchange_after_luks-tpm2.sh.tmpl:66 names the wrong prefix in its own comment.

direct: facts.yaml:76-95 carries the fail-direction doctrine verbatim, including the inverted virt/headless pair and the closing principle that a fact with no harmless value does not belong in the registry. facts.yaml:5-9 deliberately excludes momentary state from identity — correct for gates, and exactly why the rerun key must be a separate concept.

direct: run_after_build-mxm4-haptic.sh.tmpl:3 already hand-rolls a value-based rerun key consumed at :36-38. The remediation half is a chezmoi builtin: chezmoi state delete --bucket=scriptState --key=<sha>, with the entry value carrying the script name.

Rationale

This is the repository's most-documented failure class and it has already cost design freedom: the GitLab script's entire twenty-line argument for run_after_ over run_before_ exists only to dodge it. Fixing the lifecycle turns phase placement back into a performance choice rather than a correctness one. The doctrine half matters more than the mechanism — AGENTS.md:20 already states the rule, six scripts violate it in their own runtime output, and nothing checks. Remediation is the sharpest single number in the run: 19 scripts instruct the operator to recover with chezmoi apply --force, which re-fires a 612-line Fedora installer and a 448-line Rust build to fix three gsettings calls — so recovery gets deferred, and that is how a theoretical permanent skip becomes a practical one.

Downsides

A rerun key makes rendered content depend on something other than source, which sits uneasily beside the repo's determinism instincts — the key must be a declared, enumerable value, never an ambient probe, or renders stop being reproducible. The verifier refuted a nearby variant that wrote runtime deferral stamps and fed them back through the render: it stalls after two attempts unless a counter makes content change on every apply, at which point it is just run_after_ with extra machinery. Typing the shared guard partials is not the fix either — all 34 guard inclusions gate on permanent host identity, where exit 0 is already correct; the dishonest skips are inline below the guard.

2

Finish the data-driven collapse the KDE runner started

Confidence 90% Complexity Medium ~1,485 lines removable
Description

Add three fields to the desktop settings row schema — requires: for a file or command precondition, backend: to select kwriteconfig6 / gsettings / dconf, and apply: to distinguish an always-applied row from a once-applied one with a value-signature stamp. The existing 196-line runner then absorbs the twelve remaining desktop scripts as rows in two tables that already hold their values. Separately, replace the two GNOME Shell extension installers with one loop over the shellExtensions map the data file already declares as {uuid, egoId}.

Basis

direct: run_onchange_after_config-kde-settings.sh.tmpl:11-13 states the precedent verbatim — it “replaces eight scripts … that were each nothing but a guard, a command -v kwriteconfig6 skip, and a flat list of kwriteconfig6 calls”. run_onchange_after_config-kde-virtualkeyboard.sh.tmpl:10-11 names the exact blocker: “The file-existence PRECONDITION below stays here; it is why this script is not collapsible into the settings manifest.” That 52-line script is one requires: field away from being a row.

direct: Measured and independently re-verified: 536 KDE + 744 GNOME = 1,280 lines across twelve scripts. gnome.yaml:93-104 already holds mouse, terminal, app-grid and shortcut values purely as data while six scripts spend 744 lines applying them, and its header already names the missing semantic (“stamps the exact value it applied”).

direct: The two extension installers are 210 and 205 lines; after name substitution the diff reduces to two semantic hunks — a header paragraph and one closing sentence. The kimpanel script's own comment concedes it “mirrors” its sibling rather than eliminating the mirror.

Rationale

Two copies of an extensions.gnome.org API client means a shell-compatibility fix lands once and silently rots in the other. More broadly, this is the cheapest large reduction available: the architecture is already chosen, already validated on eight scripts, and the blockers were each written down as prose by the person who hit them. Collapsing turns roughly 2,100 lines of near-duplicate bash across the two coldest directories in the repo into validated tables with one injection guard, one render-time validator and one place a new setting is added — which matters precisely because those directories are cold and nobody is re-reading them.

Downsides

The verifier's caveat is real: the twelve residual scripts are not as flat as the eight already collapsed, so the schema will grow beyond three fields or a few scripts will legitimately stay hand-written. Decide up front which, rather than contorting the row schema to reach 100%. A generic runner also concentrates risk — the existing one already rejects shell metacharacters, and that guard has to hold for a wider input surface. The GNOME extension loop touches a network API client, so the shared version needs the compatibility check both copies currently carry.

3

Declare the dependency graphs the apply lifecycle only assumes

Confidence 75% Complexity High 3 lenses converged
Description

Three related declarations, shippable independently. The stage-0 seed: name in data the exact set of executables and PATH entries that must exist and be invocable before any later phase runs, each attributed to the external or installer that provides it, and have 00-tools end by verifying the closure it claims to establish — resolving through the PATH a script actually sees, not the operator's activated login shell. The phase relations: split the numeric prefix into two declared relations, requires: (capability) and isolates: (failure domain), and render the prefix from that graph so a script in phase N referencing a tool first provided at phase M > N fails the render rather than the host. The fingerprint closure: derive each component's dependency set from its component key instead of hand-enumerating globs, and prove completeness by mutation — perturb a source file, re-render, and assert the dependent script's hash moved.

Basis

direct: run_onchange_after_auth-gitlab.sh.tmpl:32-40 is a hand-computed topological sort with a correctness argument attached — it reasons in prose about glab arriving in the FILE phase, and about gh needing to precede the installers. That analysis is redone from memory for every new script.

direct: docs/plans/2026-08-04-003-fix-mxm4-haptic-clean-state-plan.md:28-34 records the same analysis failing: vp, node and cargo absent from an unactivated PATH, unrecoverable on first apply, needing an activated shell plus chezmoi state reset. AGENTS.md:52 then documents the per-script workaround rather than the structural fix.

direct: Fingerprint coverage measured at 10 of 42 run_onchange_ scripts. The haptic daemon's glob list names three of the crate's four .rs files individually, so a new module is silently missed; docs/plans/2026-07-23-002 records the realised cost of exactly this class, where a tracker that under-reported reads replayed stale binaries.

external: Compiler staged bootstrap (GCC / rustc stage0→1→2) supplies the mechanism: declare an externally-supplied seed that is sufficient by construction, then prove convergence. Where it breaks honestly — this seed involves network fetches and a distro package manager, so the assertion can only be “resolvable and executable through the phase's own PATH”, never the compiler's byte-identical stage equality.

Rationale

A first apply is the least-observed code path in the repository: it runs once per host, on the host where failure hurts most, and container CI cannot reach it because containers skip package, system and desktop provisioning by invariant. Every other authority here — facts, packages, /etc, agents, waveforms, release locks — is a declarative registry with a validator; the dependency graph that makes all of them runnable is folklore spread across one phase directory, six externals files and a handful of comments. The mutation half is the only technique that decides fingerprint completeness mechanically rather than by the author remembering, and the repo already owns both ingredients: deterministic renders and a hermetic scratch-destination harness.

Downsides

The largest item here by far. Rendering phase prefixes from a graph touches every script's filename, which is a wide, mechanical, and genuinely risky change for a benefit that is mostly preventive — consider shipping the declaration and its render-time check without renaming anything first. Mutation testing multiplies render count by the number of perturbed files, so it needs scoping to candidate inputs rather than the whole tree. And the stage-0 closure can only ever assert resolvability: it will not catch a tool that exists but behaves differently, which is a real class here (see idea 6's glab version pin).

4

Fetch what CI already built

Confidence 80% Complexity High 2 lenses converged
Description

Phase 60 resolves a build toolchain, stages, atomically installs, and validates units on the workstation. CI already compiles the same components on every push and throws the output away. Publish those artifacts keyed by the same content fingerprint the script already computes, and let phase 60 resolve an artifact by that key first, falling back to a local build only on a miss. The pinning machinery this needs — grouped externals, a generated lock with per-asset digests, and an hourly refresh that preserves last-good entries — is already the mechanism the repo has hardened six times over for every other binary it installs.

Basis

direct: ci.yml:131-133 runs cargo build --all-targets and cargo test and discards the result. run_after_build-mxm4-haptic.sh.tmpl:36-38 already computes PLUGIN_FINGERPRINT, DAEMON_FINGERPRINT and NOTIFY_FINGERPRINT — the content-addressed key exists today and is used only as a local stamp.

direct: run_after_build-mxm4-haptic.sh.tmpl:70-79 explains why the 448-line body is that long: “on a freshly provisioned host that shell has never sourced mise activate, so vp … node, and cargo … are invisible … the provisioner then died with preflight: vp is required.” That machinery exists only because the build happens on the target.

direct: docs/plans/2026-07-23-002-fix-vp-task-cache-stale-builds-plan.md:27-37 records the second failure of the same category: Vite+ auto-tracking missed reads performed by an external bun build --compile and replayed stale Figma and Kimi binaries after a source-only change.

Rationale

Both of the repository's documented unrecoverable first-apply defects and the entire stale-artifact class are properties of building on the destination host. This does not make them less likely — it removes the conditions under which they can occur: no toolchain resolution on a cold PATH, no staging dance, no independent component stamps to keep honest, and no requirement that a fresh Fedora workstation carry a Rust toolchain at all. It also reuses rather than invents: the fingerprint is already computed, the CI build already runs, and the fetch-a-pinned-artifact path is the single most exercised mechanism in the repo.

Downsides

Two real decisions this forces, and neither is small. Signing and provenance — a fetched binary from this repo's own release is a supply-chain edge that a locally-compiled one is not, so it needs the same digest discipline as every other external plus a view on attestation (this composes directly with idea 6). Offline apply — a host with no network can currently still build; after this it can only build on a fallback path that must therefore stay maintained, which partially undoes the deletion. Note also that the cold-shell CI job a nearby candidate proposed is already shipped for exactly these two defects at .ci/test-mxm4-haptic-provision.sh:416-439 — so the argument here is elimination, not detection.

5

Make a check cheap, then make every MUST name one

Confidence 85% Complexity Medium 3 lenses converged
Description

Three steps in order. Build the harness the .ci/lib convention was created for and then never extended: one file wrapping the verification protocol the repo already mandates — scratch destination, stub op, --source "$PWD" — plus render and assert helpers, and migrate the existing suite onto it. Aim the rule-loss detector at the root file: .ci/test-agent-instructions.sh already exists precisely because a line diff hides a silently dropped MUST, and it has never been pointed at the repository-root AGENTS.md, which is the file carrying every domain invariant. Give each load-bearing rule a stable ID and make every enforcing check declare the ID it enforces, failing in both directions: a rule with no check is unenforced prose, and a check citing a dead ID is an orphan defending a retired decision.

Basis

direct: Measured and re-verified: 17 of 18 .ci/*.sh scripts contain their own mktemp and trap; .ci/lib/ contains only render-gate-helpers.sh (79 lines) with exactly two consumers. The convention's origin is recorded in docs/feedback-sweep/state.yml:42 as work deferred from an earlier PR.

direct: .ci/test-agent-instructions.sh:5-13 states the failure mode verbatim — “A line-granular diff reports 'one changed line' whether an edit is correct or silently drops a neighbouring MUST, so the rules below are asserted by needle against the RENDERED target.” Its target is the deployed omp wrapper; the root AGENTS.md appears in no needle list in any .ci script or workflow.

direct: The bidirectional-proof pattern already ships for a different domain — facts-validate.tmpl fails the apply on an unknown fact name, on a declared name with no probe, and on a probe emitting an undeclared name. A live instance of the gap: AGENTS.md:20 states the soft-skip rule, six scripts contradict it in their own output, and nothing checks.

Rationale

The repository has already executed this conversion once and written down why: model policy was retired from prose “once its checkable half became render-time and CI failures”. What is treated as settled is that the conversion was a model-policy event rather than a general mechanism. The harness comes first because it is the enabler — while a new check costs roughly 40 lines of scaffold before its first assertion, converting a rule is more expensive than writing another paragraph, and the incentive points the wrong way. Flip that price and the default response to “this invariant matters” becomes a check. That matters more here than in a team repo: 672 commits in 90 days with no reviewer means prose invariants are enforced entirely by one person's memory, and increasingly by agents reading the file.

Downsides

Rule IDs are a maintenance surface of their own — an ID scheme nobody keeps current is worse than no scheme, so the bidirectional check has to land with the IDs, not after. Migrating 17 CI scripts onto a shared harness restructures currently-green tests, which is exactly the risk that deferred the original extraction. And one framing must be dropped: a nearby candidate argued a byte budget against Codex's 32 KiB cap, but verification showed the shared instruction core has exactly one consumer — the omp wrapper — so summing it against a Codex cap counts a file Codex never loads. The root file is 26,390 bytes; treat that as context worth watching, not as the driver.

6

Close the pinning boundary

Confidence 85% Complexity Medium 2 lenses converged
Description

Three moves on one boundary. Split the lock into lanes: the bot may write only candidates, recording digest, publisher and a first-seen timestamp; promotion into the applied lane happens by an explicit rule — a cooling-off age, an unchanged digest reconfirmed across N resolutions, or a human commit — and hosts render exclusively from the applied lane. Extend the rail to the unpinned surface: the same overlay-with-last-good-preservation machinery should continuously prove that the rolling unversioned TeamViewer RPM, the nine unpinned repository baseurl/gpgkey endpoints, and the hand-pinned mise toolchains still resolve. Audit the escape hatches: sweep for fallback paths that leave the pinning invariant and pin them to the lock the repo already maintains.

Basis

direct: refresh-release-lock.yml names its own step “Strict platform-vocabulary and source validation, fail-closed BEFORE any commit”, but the assertion at :63 is that each artifact carries an https:// URL and a ^[0-9a-f]{64}$ SHA-256 — well-formedness, not provenance. It then commits as github-actions[bot] and pushes unattended on an hourly cron.

direct: run_onchange_after_auth-gitlab.sh.tmpl:82 runs mise … exec glab@latest, duplicated in the deployed helper dot_local/bin/executable_auth-glab:115 — unpinned, on the first-apply path, inside a repo whose entire external story is digest-pinned. The same script's header at :43 pins its behavioural reasoning to a specific version, and :56-57 spells out the consequence of getting it wrong: “HTTP Basic: Access denied” on every clone, fetch and push.

direct: packages.yaml:368 pins TeamViewer to a rolling unversioned RPM URL with no recorded hash, alongside nine unpinned baseurl/gpgkey endpoints.

Rationale

This is the sharpest internal tension in the system: the automation that makes an unattended future viable is the same automation that makes a hostile-upstream future dangerous, and the two meet at exactly one file with nobody staffing the admission control. The lane split resolves both at once as a data-only change, without slowing the bot down. The availability half is separate and cheaper — today an upstream that vanishes or silently changes is discovered during a first apply on a real host, which is precisely the situation the repo's own incident record describes as unrecoverable. A fallback to an arbitrary future glab is a fallback to a version whose documented short-circuit behaviour was never verified, and the failure surfaces later as broken git auth, far from the apply that caused it.

Downsides

A cooling-off lane delays genuine security patches by exactly the window it protects against compromise — that trade needs a stated position, possibly a fast lane for advisories. Promotion by human commit reintroduces the manual step the bot rail exists to remove, so the age-and-reconfirmation rule has to be the default path or the lane will silently stop being promoted. And pinning the @latest fallback creates a chicken-and-egg on the first apply that the fallback exists to solve — the fix is likely a lock-derived version rather than a removal.

Give MCP declarations a permission dimension

Confidence 80% Complexity Medium agent surface
Description

The agent registry declares which MCP servers exist and delegates what they may do to the harness — the component most likely to be swapped. Add a permissions: block per server covering tool allow/deny and approval mode, and validate it with the same abort-on-unknown discipline the fact registry already uses, so least privilege becomes a render-time, fail-safe property rather than a downstream default. The check is bidirectional in the same way: a declared tool that the server does not expose is a typo, and a server with no declared policy is an unreviewed grant.

Basis

direct: No permission field exists anywhere in the agent registry; verification found agent-browser declared with --tools all. By contrast facts.yaml:57-62 describes a validator that “FAILS THE APPLY on an unknown name … also fails when a name declared here has no probe behind it, and when a probe emits a name that is not declared here: a fact never silently evaluates false because someone typo'd it.”

external: MCP security guidance requires per-client consent, exact redirect-URI validation and least privilege, and treats server enablement, tool allow/deny lists and per-tool approval mode as distinct configuration surfaces. None of the existing cross-harness sync tools (agent-setup, agents-sync, dot-agents) expresses a policy such as “this machine may load the server but never auto-approve write tools” — so there is no prior art to adopt, which is an argument for declaring it here rather than waiting.

Rationale

The repository derived a strong safety doctrine — declare the name, prove the probe, abort on a typo, make false mean skip — and applied it to host identity, where the worst outcome is a mis-installed package. It did not apply it to the surface where an over-broad default hands an autonomous agent a write-capable tool. That inversion is the point worth naming: registries received validators in the order they became painful, not in the order they became dangerous. This is also the only survivor on the agent-configuration surface, which is simultaneously the repo's hottest area by commit volume and its least-guarded by render-time validation.

Downsides

Expressiveness is bounded by what the harness's own settings surface accepts — a declared policy the harness cannot enforce is theatre, so this needs a concrete mapping before it is worth building, and it may cover only a subset of servers. It also adds a second place a new MCP must be described, which cuts against the repo's preference for one declarative surface; the mitigation is that the block lives in the same registry row, not a new file. Finally, tool inventories change upstream, so a strict allow-list will occasionally fail an apply for a benign upstream rename — that is the fail-safe direction working as designed, but it should be a deliberate choice.
