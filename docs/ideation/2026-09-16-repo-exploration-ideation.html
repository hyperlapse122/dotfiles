1. Position-Independent Script Rendering (PISR): Runtime $sourceDir Decoupling

Planned Confidence 96% Complexity S

Replace compile-time interpolation of {{ .chezmoi.sourceDir }} across .chezmoiscripts/30-linux/ and build templates with runtime environment resolution: SRC_ROOT="${CHEZMOI_SOURCE_DIR:-$(command -v chezmoi >/dev/null 2>&1 && chezmoi source-path || pwd)}/system/linux". Because fingerprint.tmpl already verifies dependencies using relative paths and content digests, decoupling script bodies from the absolute source path ensures that running checks or applies inside Orca feature worktrees (~/.local/share/worktrees/*) produces bit-identical script text, completely eliminating the false-positive invalidation of ~20 root-privileged sudo scripts. (Graduated to formal plan: docs/plans/2026-09-16-1136-refactor-position-independent-script-rendering-plan.md).

Basis (Direct Repository Evidence)
direct:docs/solutions/integration-issues/chezmoi-worktree-root-etc-file-deployment.md:92-116 notes: "48 script templates match grep -rl 'chezmoi.sourceDir' .chezmoiscripts/... The re-run set is therefore a property of the source-path switch, not of anything the change itself touched."
Rationale Solves the primary developer-experience friction and safety hazard in the repository. Once script bodies are position-independent, agents and operators can execute template checks and test applies inside feature worktrees with zero risk of accidentally triggering host-wide system reconfigurations.
Downsides & Tradeoffs Requires updating script templates to adopt the fallback variable syntax; scripts must cleanly handle invocations where Chezmoi environment variables are absent.

2. Content-Addressed Subtree Tree-Hashing in packages/release-lock

Confidence 94% Complexity S

Upgrade packages/release-lock's gitRef resolver to track Git tree object IDs for declared skillPath subdirectories rather than raw branch HEAD commit SHAs. For tagless monorepos (such as cursor/plugins, vercel-labs/agent-skills, and shadcn/improve), the resolver queries the GitHub Git Data API for the target directory's tree SHA and only updates .chezmoidata/releases.json when files inside that directory actually change.

Basis (Direct Repository Evidence)
direct:packages/release-lock/src/registry.ts:365-376 tracks cursor/plugins via refs/heads/main, while .github/workflows/refresh-release-lock.yml:49-61 commits unconditionally on any JSON diff, polluting git log history with ~20 commits weekly.
Rationale Eliminates automated commit noise and recurring rebase conflicts on active feature branches while preserving cryptographic pin guarantees and hermetic offline rendering.
Downsides & Tradeoffs Requires an extra GitHub API call (Git Trees API) during resolution for gitRef entries declaring a skillPath. Fallback handling needed if an API rate limit occurs.

3. Surgical Manifest-Aware System Dispatcher (dotfiles-apply-targeted)

Confidence 92% Complexity M

Introduce a dedicated developer CLI command (dotfiles-apply-targeted <path>) that maps modified files under system/linux/etc/** to their owning install-system-*.sh.tmpl script using .chezmoidata/system.yaml globs. It dry-run renders only that specific template against the active worktree, presents an interactive diff preview with deletion safety checks, and executes only that script under sudo without invalidating Chezmoi's machine-wide state bucket.

Basis (Direct Repository Evidence)
direct:docs/solutions/integration-issues/chezmoi-worktree-root-etc-file-deployment.md:58-88 documents the dangerous 4-step manual workaround (manual execute-template to /tmp, deletion inspection, isolated sudo execution) required to test single udev drop-ins without triggering 20 scripts.
Rationale Transforms an error-prone, hazardous manual shell ritual into a single verified command, reducing feedback latency for hardware driver, udev, and PAM development from 15 minutes to under 5 seconds.
Downsides & Tradeoffs Must maintain strict synchronization with .chezmoidata/system.yaml glob mappings and root deletion arrays to prevent accidental drift between targeted and full applies.

4. Unified Multi-Harness Declarative Settings Engine (packages/settings-reconcile)

Confidence 91% Complexity M

Expand packages/settings-reconcile from a Codex-only TOML reconciler into a universal, multi-format declarative assertion engine handling TOML (Codex config.toml), JSON (Claude Code settings.json), and YAML (oh-my-pi config.yml). It absorbs the ad-hoc bash/jq loops in run_after_config-claude-settings.sh.tmpl and custom yq scripts in run_after_config-omp-settings.sh.tmpl, providing unified path-leaf assertion, symlink defenses, owner verification, and atomic writes across all agent harnesses.

Basis (Direct Repository Evidence)
direct:packages/settings-reconcile/src/reconcile.ts:11-30 only parses TOML, while AGENTS.md:120-135 documents that Claude Code and omp settings are asserted via separate shell scripts with independent error modes and duplicated fail-open logic.
Rationale Eliminates fragile shell scripts, unifies allowlist validation, and guarantees identical atomicity, symlink defense, and non-destructive convergence semantics across all three agent harnesses.
Downsides & Tradeoffs Expands the bundle size of settings-reconcile by pulling in robust YAML and JSON parser dependencies into the package.

5. Active Agent Schema Drift & Deprecation Guard (dotfiles-agent-doctor)

Confidence 89% Complexity M

Implement an automated pre-apply and CI validation tool that introspects active agent CLI binaries (claude --help, codex features list, omp config show) to verify that all asserted leaves in .chezmoidata/agents.yaml remain valid and recognized. If an upstream vendor silently renames or deprecates a key (such as memory suppression flags, telemetry toggles, or sandbox switches), the doctor fails loudly with an actionable migration diff rather than allowing the assertion to succeed against an ignored key.

Basis (Direct Repository Evidence)
direct:AGENTS.md:131-137 warns: "Nothing validates that a declared path names a real Claude Code setting; no machine-readable settings schema is published, so a typo is asserted and reported as success while the product ignores it."
Rationale Directly protects the repository's core security invariants (disabling agent auto-memory, enforcing sandbox boundaries) against silent vendor degradation during CLI version updates.
Downsides & Tradeoffs Agent CLIs do not all provide clean machine-readable schemas, requiring robust regex/help-text parsing heuristics that must be defended against CLI formatting changes.

Build a pre-packaging transformation step into 00-tools or packages/release-lock that normalizes external skill archives for universal consumption across all harnesses. It automatically strips the root plugin.json for oh-my-pi while standardizing plugin manifest identifiers to prevent removal mismatches, completely eliminating the need for a secondary duplicate download archive (compound-engineering-omp) in agents.marketplaces.

7. Deterministic Garden Worktree Trust Seeding & Zero-Crawl Discovery

Confidence 95% Complexity S

Replace the recursive filesystem crawl in agent-trust-reconcile with deterministic, zero-crawl manifest discovery. Instead of running Python os.walk across all of ~/src (searching every subdirectory for .git) and ~/.local/share/worktrees on every apply, the reconciler reads repository checkout paths directly from dot_config/garden/garden.yaml in O(1) time and enumerates the single-level worktree directories under ~/.local/share/worktrees/*. This cuts trust reconciliation latency on large workspaces from ~3.5 seconds to under 40 milliseconds.

Basis (Direct Repository Evidence)
direct:dot_local/share/chezmoi-command-sources/executable_agent-trust-reconcile:23-33 uses "for dirpath, dirnames, filenames in os.walk(root_path): if '.git' in dirnames...", while .chezmoiscripts/90-src/run_after_trust-agent-worktrees.sh.tmpl:31 invokes "$reconcile --all" on every single apply.
Rationale Eliminates heavy filesystem crawling and disk thrashing during routine Chezmoi applies. Because garden already authoritatively owns checkout topology under ~/src, blind directory crawling is redundant and expensive.
Downsides & Tradeoffs Ad-hoc repositories manually cloned into ~/src without a garden entry would not be automatically discovered unless registered in garden.yaml or passed explicitly via CLI flag.

8. Cross-Harness Pre-Apply Skill Linter & Compatibility Verifier (dotfiles-skills-lint)

Confidence 93% Complexity S

Introduce a static validation tool (.ci/check-skills-compatibility.sh / dotfiles-skills-lint) that parses all personal skills in dot_agents/skills/**/SKILL.md and external skill archives declared in .chezmoiexternals/ai-agents.toml. It validates YAML frontmatter against the unified schema, detects keys that trigger omp plugin classification drops (the cb30ed4 bug), verifies that declared tool names map to valid harness capabilities, and warns on identifier collisions between personal and external skills.

Basis (Direct Repository Evidence)
direct:AGENTS.md:188-195 records: "With the root plugin.json present, omp classifies the tree as an agent-plugins package and rejects every SKILL.md carrying Claude Code or Codex frontmatter keys, dropping 30 of 33 skills (cb30ed4)." No automated check currently validates skills against this boundary before deployment.
Rationale Prevents silent skill disappearance across harnesses, ensures skill discovery parity between Claude Code, Codex, and omp, and catches schema incompatibilities before skills are placed into user environments.
Downsides & Tradeoffs Requires maintaining a unified frontmatter schema definition that must track updates if upstream agent CLIs add new experimental frontmatter properties.

9. Generation-Bounded Command Store Eviction & Managed Service Handoff

Confidence 91% Complexity M

Enhance packages/command-reconcile to coordinate with systemd user services during unit activation and quarantine pruning. Units in .chezmoidata/commands.yaml declare an optional systemdService property. When a new binary version is activated, command-reconcile invokes an asynchronous systemctl --user try-restart <service>. The daemon re-executes onto the new store path, releasing the open file descriptor on the old binary, enabling the subsequent quarantine prune cycle in prune.ts to cleanly delete older store versions without waiting for a machine reboot.

Basis (Direct Repository Evidence)
direct:packages/command-reconcile/src/prune.ts:53-70 scans process roots and retains versions in ~/.local/lib/commands/store/ whenever any running process holds an open file descriptor, stranding long-running daemons (such as antigravity-sidecar and gem80-rgbd) in quarantine indefinitely.
Rationale Prevents persistent disk leaks in command stores, ensures that long-running background services cleanly track newly deployed binaries, and automates daemon lifecycle handoffs cleanly within the existing reconciliation flow.
Downsides & Tradeoffs Requires systemd user session bus availability; must fail open safely when running in container environments or headless SSH sessions without an active user bus.

10. Structural Agent Instructions Compiler & Self-Auditing Fixture Generator

Confidence 92% Complexity S

Upgrade .ci/test-agent-instructions.sh from brittle line-granular text fixture comparisons to a structural invariant verifier with automated fixture synchronization (--update-fixtures). Instead of requiring developers to manually update 8 separate plain-text fixture files in .ci/fixtures/agent-instructions/ whenever shared instruction text (e.g. autonomy rules or waiting constraints) is edited, the compiler parses .chezmoitemplates/agents-instructions.tmpl, validates AST invariants (harness isolation, exact two-line spacing between autonomy paragraphs, needle integrity), and syncs fixture hashes automatically.

Basis (Direct Repository Evidence)
direct:.ci/test-agent-instructions.sh:18-37 compares rendered instruction paragraphs against committed text files (harness-runs-*, harness-is-*, lfg-autonomy.txt, workflow-required-autonomy.txt) and asserts: "the workflow-required-step paragraph must render exactly two lines below the lfg paragraph."
Rationale Removes tedious manual synchronization of static fixture files, prevents cosmetic formatting edits from breaking CI test runs, and makes maintaining shared agent instruction rules ergonomic.
Downsides & Tradeoffs The self-auditing compiler must enforce strict positive needle checks so that accidental omissions of critical security constraints or destructive command prohibitions cannot be silently auto-updated.

11. Inode-Fingerprinted Fast System Fact Cache in .install-prerequisites.sh

Confidence 94% Complexity S

Implement a fast inode/mtime-checked static fact cache in .install-prerequisites.sh. System facts (container detection, Jetson hardware detection, GPU configuration, authd integration, desktop environment) depend on static trigger files (/etc/os-release, /etc/nv_tegra_release, /run/.containerenv, /etc/systemd/system/). By hashing the stat -c %Y modification timestamps of these trigger paths into a single fingerprint, the script can validate the cached facts via a single stat syscall (~2ms) and bypass dozens of subshell command invocations on steady-state workstations.

Basis (Direct Repository Evidence)
direct:.install-prerequisites.sh:234-275 executes multiple subprocess probes on every chezmoi diff, status, and apply command, scanning /sys/bus/pci/devices/* and evaluating system state even when the underlying host hardware is static.
Rationale Shaves 250–400ms off every interactive Chezmoi command invocation, making local shell prompt latency and developer commands substantially snappier.
Downsides & Tradeoffs Cache invalidation must account for external hardware hot-plug events (e.g. dynamic Thunderbolt GPU docking); an explicit --refresh-facts flag must be supported.

12. Declarative Desktop Window Rule & Hotkey Parity Engine (KDE KWin & GNOME Mutter)

Confidence 89% Complexity M

Introduce a declarative desktop configuration schema in .chezmoidata/desktop.yaml that models window management rules (dialog placement, pin-on-top, focus stealing prevention, tiling exceptions) and global shortcuts platform-agnostically. Unified template renderers compile KWin rules (kwinrulesrc, kglobalshortcutsrc) and GNOME Mutter/dconf keybindings from the single declarative model, guaranteeing behavioral parity between KDE and GNOME workstations.

Basis (Direct Repository Evidence)
direct:.chezmoidata/kde.yaml:1-50 and .chezmoidata/gnome.yaml:1-50 manage window rules and keybindings through separate imperative configuration mechanisms, resulting in behavioral divergence (e.g. 1Password auth prompt always-on-top behavior requiring independent fixes in docs/plans/2026-09-01-0234-fix-kde-1password-window-rule-polkit-layering-plan.md).
Rationale Guarantees that critical desktop ergonomics (such as authentication dialogs remaining accessible and visible on top of full-screen terminals) behave identically across Fedora KDE and GNOME installations.
Downsides & Tradeoffs KWin and GNOME Mutter support different window-rule capabilities; the unified schema must restrict itself to the common denominator supported by both window managers.
